## Idempotency (S1–S4, S6): exactly-once holds on both endpoints

- **S1 (lost ACK):** first POST sent fire-and-forget (socket closed
  without reading the response; log row confirmed landed), then re-POST
  same key. Result per target: 2 POSTs → 1 log row, 1 bill PAID,
  1 `pemasukan` row, `applied_at` set; retry response `duplicate:true`
  with the stored `matched` decision. Customer masa_aktif 0→30, poin
  0→10 (UNPAID rate).
- **S2 (concurrent):** 12 parallel POSTs, same key, 3 rounds, spread
  over 4 PHP workers. Every round: 11 `duplicate:true` + 1
  `duplicate:false` responses, 1 log row, 1 bill PAID, 1 `pemasukan` row.
- **S3 (restart):** POST applied, then the whole test stack restarted
  (all PHP workers + scratch MariaDB stopped and started; ~5 s), then
  re-POST same key. Result: `duplicate:true`, still 1 log row, 1 bill
  PAID, 1 `pemasukan` row, `applied_at` intact. The dedupe key is
  durable in InnoDB, not in process memory.
- **S4 (negative control):** 2 keys, 2 different payments → 2 bills
  PAID, 2 `pemasukan` rows, 2 applied log rows. Dedupe is key-scoped,
  not over-broad.
- **S6 (warganet top-up branch):** POST + retry → payment PAID, mitra
  saldo credited exactly once (Rp50.000,00), 1 `saldo_history` row,
  1 `pemasukan_hotspot` row.

Mechanisms confirmed by execution (not just code reading): the
`UNIQUE(dedupe_key)` + `INSERT ... ON DUPLICATE KEY UPDATE id=id` gate
admits exactly one matcher run per key, and the atomic claim inside the
apply transaction (`UPDATE ... WHERE status<>'PAID'` +
`affected_rows===1`) admits exactly one settlement per bill even when
two different keys match the same bill (S5c warganet interleaving).

## Matching findings (S5): behaviour documented, not passed

- **C1 (S5a, both targets):** two candidates with the same nominal →
  `match_status='ambiguous'` (`candidates:2`), **neither settles**:
  0 PAID, 0 `pemasukan`. Retry under the same key returns the stored
  `ambiguous`; a second key with the same amount is `ambiguous` again
  (2 ambiguous log rows). The money is recorded but never settles
  without manual intervention.
- **C2 (S5b, both targets):** payment arrives while the bill has
  `kode_unik IS NULL` → `match_status='logged'`, no match. After the
  code is born (kode 123), retry under the **same** key returns the
  stored `logged` — **no re-match**; the original row is never applied.
  A **new** key with the same amount matches and settles (1 PAID),
  proving the payment would have matched had it arrived later. The
  original notification is effectively lost to auto-settlement.
- **C3 (S5c, both targets):** two senders (different keys, 6+6 parallel
  POSTs) racing on one candidate → exactly 1 effect (1 PAID,
  1 `pemasukan`, 1 applied row) and the loser never settles. The
  loser's `match_status` is timing-dependent — **both interleavings
  were observed in the same run**:
  - v2New: loser `logged` (its matcher ran after the winner committed;
    no UNPAID candidate left).
  - warganet: loser `matched` + `applied_at NULL` (both matched before
    either committed; the atomic claim let only the winner apply).
  In neither interleaving does the loser re-match to another candidate.
- **C6 (S5d, targets differ):**
  - v2New: matcher sees **only the latest bill per customer**
    (`JOIN MAX(id)`). Older-bill amount → `logged`, older bill stays
    UNPAID; newer-bill amount → matched + applied to the newer bill.
  - warganet: matcher sees **all UNPAID bills**. Older-bill amount →
    matched + applied to the **older** bill; newer-bill amount →
    matched + applied to the newer bill (2 PAID, 2 `pemasukan`,
    customer masa_aktif 0→60 over the two applies, poin 10 — the
    second apply adds 0 poin because the status was already PAID).
- **S5c-2 (race control, both targets):** two senders on two different
  candidates concurrently → both settle (2 PAID, 2 `pemasukan`).
  The race only bites when one candidate is contested.

- Setup's in-worker probe reproduced the warganet WhatsApp curl and
  got `http_code:0`, error `Failed to connect to 127.0.0.1 port 59999`
  — the call dies at the dead proxy before any packet leaves the box.
- Every warganet apply left exactly one `report` row per settlement
  with `FAILED: curl: Failed to connect to 127.0.0.1 port 59999 ...`
  (S1: 1 row; S4: 2 rows) — the attempts are recorded locally, never sent.
- v2New external steps (MikroTik, email, WhatsApp) were skipped by the
  code's own `file_exists`/empty-field guards; the `router`/`finance`/`wa`
  files were never copied into the scratch tree.
- No production database or endpoint was written to at any point; all
  writes went to the scratch MariaDB instance (port 3307) and scratch
  databases `paylist_contract_v2` / `paylist_contract_wg`.
