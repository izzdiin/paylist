## H1-A [BLOCKER] — negative reconciliation vs UNKNOWN (design §7.3B(5), §10.2 F43 B12/B21; file plan §D FallbackGate, §E)
- [x] Verified the contradiction before patching: §7.3B(5) said "a `found:false` answer with all other criteria met authorises the fallback" with no coverage/UNKNOWN/binding condition, while Resolution 4 (§9.2) requires COVERED writer state + no UNKNOWN hop for the key + recorded coverage before a negative is authoritative, and §8.7 E1/E2 authorisation already requires "an authoritative reconciliation record per §9 (D1 + D2 + gate resolution 4)". A bare `found:false` (advisory-only mixed-version negative, or one with an UNKNOWN hop for the same key) would have authorised a re-POST under §7.3B(5) alone.
- [x] Criterion 5 rewritten: authoritative means the full four-condition Resolution 4 test — (a) COVERED writer state (migration, locks on ALL writers, endpoints, F42 T1/T2/T6 green); (b) no UNKNOWN hop for the key anywhere in the sweep; (c) system/endpoint binding match (§9.5); (d) coverage state + reconciliation decision recorded durably. Any other negative (advisory-only coverage, UNKNOWN hop, binding mismatch, inconclusive answer) ⇒ criterion fails, delivery holds. Bold rule added: "A bare `found:false` never authorises a fallback on its own."
- [x] New fixture F43 B21: adversarial negatives — (a) `found:false` + UNKNOWN hop same key ⇒ HELD; (b) advisory-only coverage ⇒ HELD; (c) binding mismatch ⇒ HELD + configuration finding; (d) authoritative `found:false` + other criteria met ⇒ fallback authorised, `raw_lost: true`. Cross-referenced with F41/F42. B12(5) now cites the full test and points at B21. File plan: `FallbackGate.kt` criterion (5) restated; D→E gate gains B21; `PrivacyGateTest` row gains B21 (owned by `FallbackGate` unit tests).
- [x] Checked, no change needed: the `RAW_UNAVAILABLE` taxonomy sentence ("a `found:false` answer leaves it `RAW_UNAVAILABLE` until the operator decides") governs the operator's explicit leave-held choice (c) and is consistent with the fix — a negative alone does not authorise dispatch. ## H1-C [MAJOR] — raw revocation / output-stream TOCTOU (design §7.3A(e), §7.3B disclosure, §10.2 F43 B3/B20, §12.3 F23; file plan §A Sender.kt, §B RawSnapshotStore, §E ConsentTest/PrivacyGateTest)
- [x] Verified before patching: §7.3A(e) re-checked consent immediately before building/sending the body and named the first output-stream write as the point of no return, but the window between the check and the first write was unbounded and undisclosed — a revocation committing in that window could not stop the in-flight thread from transmitting raw.
- [x] Admission fence added to §7.3A(e): revocation bumps a per-route `sendFence` generation (`AtomicLong` in `RawSnapshotStore`, under the store lock with the epoch bump and snapshot drop); the claiming thread records the generation at the pre-send gate and re-reads it immediately before the single first-write call site (F40 case H) — plain volatile read, no lock held, no I/O, no suspension point between the read and the write (straight-line instruction sequence, body bytes already built). Generation changed ⇒ abort before any byte, drop snapshot, `BLOCKED`. Linearization stated: revocation before the final read prevents the send; revocation after the final read but before the first write is the only residual, bounded to that instruction sequence and disclosed. No lock held over network I/O. Parallel with the R35 SAF-export race treatment noted (no row started after an observed revocation; check/write pair not atomic).
- [x] §7.3B disclosure extended: a revocation taking effect after the final pre-send admission check but before the first write cannot prevent transmission of bytes already being written — bounded to the check-to-first-write instruction sequence, no I/O between them.
- [x] New fixture F43 B20 (fake transport with a latch between the final admission read and the first write): (a) revoke while latched ⇒ zero bytes, `BLOCKED`; (b) revoke after the first write began ⇒ POST completes, response stands, no further raw POST; (c) revoke between the pre-send gate and the latch ⇒ final read observes the new generation ⇒ zero bytes. Owned by `ConsentTest` + `PrivacyGateTest`. B3 scoped to pre-first-write revocation. F23 register line gains the fence race. File plan: `Sender.kt` gains the final admission read at the single first-write call site; `RawSnapshotStore.kt` gains the `sendFence` generation; `ConsentTest` owns the F23 fence race + co-owns B20; D→E gate gains B20.
