2. **B — Room:** event/delivery schema, transactions, lease, legacy import; tests for process death, import repetition, storage errors. `CutoverCoordinator` owns the lock, flag, and capture executor from Stage B. **P3 tables** (`order_registry`, `match_results`, `classification_results`, §4.6 of the design) land here with their DAOs. 3. **C — Delivery:** HTTP classification, WorkManager scheduling, legacy chain, ACK, heartbeat; mock endpoint tests; preserve single-sender ownership. **Interim arrangement (F-P1-06, explicit):** (a) Stage C ships the one-time secret migration (`SecretMigration.kt`, Stage C): at first launch it reads each existing plaintext secret from SharedPreferences exactly once, writes it to the Keystore via `SecretVault`, verifies by read-back, then deletes the plaintext value and writes the migration-complete marker (crash-safe ordering per §C; re-run idempotent). **Marker rule (R24 §5, corrected):** the per-route marker is written only after verification in the same run — either the full sequence with read-back equality, or on a re-run where the plaintext is already absent, a fresh Keystore read proving the entry is present **and** decryptable (read succeeds). Absence of plaintext alone never proves success. If the plaintext is absent **and** the Keystore entry is absent, unreadable, or mismatched ⇒ do **not** write the marker; the route is marked `DISABLED_MISSING_SECRET` (`BLOCKED`) with explicit recovery — the operator re-enters the secret; diagnostics record the route id only, never the value. **`commit()` failure is not success:** if the plaintext-delete `commit()` returns false, the plaintext is treated as still present: the marker is not written, and the delete is retried (one immediate retry, then on the next launch). The same applies to the marker write itself: a failed marker `commit()` ⇒ re-run migration on the next launch; the sequence is idempotent. A return value of `commit()` is checked everywhere it is used; an unchecked `commit()` is a defect. **Per-route state, not global:** migration state is one marker per route id, in a dedicated `paylist_migration` SharedPreferences file — independent of the routes/queue file, so the queue split (§7.8 option (iii)) cannot disturb it. A crash between routes leaves some routes migrated and some not; the re-run migrates only the unmarked routes. A route deleted mid-migration needs no marker; a route added after migration enters its secret via the vault directly and is born marked — there is no plaintext to migrate. After the marker, no Stage C code reads secrets from SharedPreferences; `TransportClient` reads secrets only through `SecretVault` via the `SecretProvider` interface. There is no plaintext-backed provider implementation and no ongoing plaintext fallback. (b) Stage C chain tests use fixture events + migration payloads (`legacy_payload_json`); events from the new parser are tested in Stage D; (c) `TransportClient` Stage C calls `EndpointValidator` (Stage C) — no inline minimal validation with an unregistered TODO. **Dual-run heartbeat during C–D** (C18): AlarmManager + WorkManager heartbeats run concurrently, safe via the server dedupe bucket; AlarmManager is disabled in Stage D after HeartbeatWorker is verified. **Activation gate (R30, M2):** F50 + F54 must PASS before any Stage C legacy import/cutover activation.
