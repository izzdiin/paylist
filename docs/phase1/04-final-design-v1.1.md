## 1. Scope, locked decisions, non-goals

### 1.1 Locked decisions (v1.0 §0, retained)

1. Legacy payment endpoints keep their existing payload and chain semantics; `X-QRIS-Secret`, `dedupe_key`, and `matched`/`ambiguous`/`logged` must not change without contract tests and approval.
2. New integrations use `structured` by default; raw text only through explicit opt-in and sanitisation. Legacy endpoints keep existing fields during transition.
3. Heartbeat is WorkManager best-effort with server-side monitoring; not an exact 15-minute SLA.
4. No foreground service in Phase 1 until device-test evidence and a separate decision.
5. Android Keystore protects secrets; SQLCipher is deferred.
6. Universal core; Android is the first source; payment is a parser/use case, not a core-schema obligation.
7. Routes and non-secret preferences stay in SharedPreferences; the queue moves to Room.
8. **At-least-once delivery; idempotent server record/settlement keyed by `dedupe_key`; apply outcome confirmed only by the first response or by server-side reconciliation.** "Exactly-once" is struck everywhere in v1.1 (R13 §5): duplicate POSTs cannot double-settle (verified, §5.4), but a lost first response leaves the apply outcome unknowable client-side, and "exactly-once" hid that.

### 1.2 In scope / out of scope

**In scope:** notification capture from allowlisted packages; compatible payment parser; universal event model; persistent outbox; WorkManager delivery/retry; legacy-queue migration; heartbeat; diagnostics; consent, redaction, Keystore; unit/instrumentation/manual tests; reproducible build; server reconciliation endpoints (P12, §9); pre-socket attempt protocol and sweep (§8); structured transaction reconciliation export (CSV, §7.7A — owner decision 2026-11-16).

**Out of scope:** multi-tenant portal, public REST ingestion production, inbound webhooks, a new settlement engine, visual automation, billing, SQLCipher, Play Store release, foreground service. A local mock HTTP endpoint for tests is permitted.

**Platform limits (stated, not solved).** Android does not guarantee every notification is captured. Room protects an event **after** its storage transaction succeeds, not a notification the listener never received. `force-stop`, OEM restrictions, and already-dismissed notifications cannot be fixed by WorkManager alone. The P0 audit finding (Doze capture gap, 8.5 hours, 4 Nov) is **not** solved by this design, and the design does not pretend otherwise.

## 2. Architecture

```text
NotificationListenerService -> Source allowlist & consent -> PrivacyGate (reject/redact before durable storage)
  -> NotificationNormalizer + optional PaymentParser -> capture staging (Room, post-PrivacyGate only)
  -> enqueue to exactly one store -> Room: Event + LegacyChainDelivery -> unique OneTimeWork
  -> SyncWorker claims due deliveries transactionally (short lease) -> TransportClient + LegacyPayloadMapper
  -> PHP endpoint / mock universal endpoint -> validate ACK -> transactional delivery state update
PeriodicWork -> best-effort heartbeat event + queue reconciliation
Listener connected/manual rescan -> activeNotifications via listener only
Diagnostics UI -> Room states + listener permission/connection timestamps
```

No HTTP inside the listener callback, no global lock across network I/O, no unbounded `Thread {}` per event. Room writes and parsing must not block the listener callback for unbounded time; use a bounded serial executor/coroutine scope with clear error reporting. A callback accepted into an in-memory executor is **not yet durable**; diagnostic counters must not report it as persisted before the Room commit.

**Modules.** Collector: `PaylistListenerService`, `NotificationNormalizer`, `SourcePolicy`, `PrivacyGate`, capture staging + sweeper. Parser: `EventParser`, `ParserRegistry`, `PaymentParser` (preserve current amount/keyword behaviour unless explicitly authorised to change). Persistence: `PaylistDatabase`, `EventDao`, `DeliveryDao`, `AttemptDao`, `CollectorStateDao`, `LegacyQueueMigration`, `CutoverCoordinator`, promotion receipts, sweep fences, drain intents. Delivery: `SyncWorker`, `SyncScheduler`, `TransportClient`, `LegacyPayloadMapper`, `LegacyResponseClassifier`, `HeartbeatWorker`. Security: `SecretVault` (Keystore), `EndpointValidator`, `SensitiveDataRedactor`. UI/diagnostics: status, blocked items, last ACK, listener permission, manual rescan/retry, review surface (`NEEDS_REVIEW`), onboarding consent, revocation, local deletion.

**Verified baseline facts (read-only).** `Sender.LOCK` is a `private companion object Any()`; `flush()` holds `synchronized(LOCK)` for the whole `flushLocked()` loop, which processes **all** queued items; `enqueueItem` also takes `LOCK` briefly. `post()` is synchronous inside `processItem()`; one POST ≤ 30 s (15 s connect + 15 s read timeout). `synchronized` cannot be waited on with a timeout — cutover needs a timed-acquire lock (`ReentrantLock(fair = true)`, `tryLock(45, SECONDS)`) or an equivalent in-flight counter + condition (C13). `AndroidManifest.xml` declares no `android:process` anywhere, so sender and coordinator share one process. **Design constraint (normative): v1.1 adds an `android:process` override to no component, ever.** `Store.saveQueue` uses `apply()`, not `commit()`; it stays `apply()` in normal operation, and the synchronous `saveQueueSync` (`commit()` + readback) is cutover-only hardening (C19). The only transport is `java.net.HttpURLConnection` — no OkHttp dependency; `Sender.kt:182–191` touches `conn.outputStream` directly, with no explicit `connect()`, no `setInstanceFollowRedirects(false)`, no proxy configuration.

## 3. Canonical event contract (internal, v1)

```json
{"schema_version": 1, "event_id": "UUIDv4", "source_event_id": "stable-source-key",
 "type": "payment.notification", "category": "payment",
 "source": {"type": "android_notification", "device_id": "device-installation-uuid", "package": "com.example.merchant"},
 "occurred_at": "2026-11-14T10:00:00Z", "captured_at": "2026-11-14T10:00:01Z",
 "data": {"amount": 150000, "currency": "IDR"},
 "metadata": {"parser_version": "payment-v1", "privacy_mode": "structured"}}
```

`data` may be empty; amount/currency optional. `event_id` identifies a stored event; `source_event_id` a source occurrence/update; `delivery_id` one outbound delivery job. Neither source key nor Android `postTime` proves a bank transaction's identity. Keep legacy `dedupe_key` **unchanged** for migrated entries; preserve the existing calculation for newly captured legacy entries until contract tests approve a change. Do not use a new UUID as legacy dedupe key.

> **(normative, C3).** The legacy `dedupe_key` is computed from pre-redaction transient input (raw title + text) on BOTH the live and rescan paths, before PrivacyGate; PrivacyGate must not alter the key computation input. Algorithm: `"$pkg|${sbn.postTime}|$amount|${combined.take(40).hashCode()}"`, `combined` = full raw `"$title $text $bigText"` (`PaylistListenerService.kt:182`). The PHP matcher reads `amount` only, so redaction cannot break matching — but a diverged key breaks identity: the same notification under two keys is treated as two notifications, and the second can settle a different system's proforma (double settlement across systems, F-P1-02). The sweep **never recomputes** a `dedupe_key` from a stored payload, for either class of copy (R19 (a′)): the stored payload truncates title/text to 500 chars and drops `bigText` when `text` is non-empty, so recomputation is a reconstruction, not a verification, and silently differs in two cases (empty `text` producing a double separator; short title+text reaching into a dropped `bigText`).

**Android update policy (normative).** Events are immutable. An updated notification with the same `dedupe_key` is the same event, not a new one. Inspect `StatusBarNotification.key`, package, postTime and content; document whether updates represent the same event or a revision. For legacy compatibility retain old key behaviour initially, record suspected updates in diagnostics, and add tests for updated notifications, group summaries, and repeated rescans. Filter `FLAG_GROUP_SUMMARY` in both live and rescan paths.

**Identity and collision (normative, R11).** Event and delivery identity are separate and DB-enforced, never query-then-insert. `events`: unique index on `dedupe_key`. `deliveries`: unique index on `legacy_qkey` (`dedupe_key|kind|route-set`), mandatory for v1.1. All inserts (live, rescan, import) use `INSERT OR IGNORE` in a transaction; rows-affected = 0 is a duplicate, counted, not retried, not an error. Dedupe at enqueue compares `legacy_qkey`, never bare `dedupe_key`. A second delivery for the same event is permitted only with a different `legacy_qkey`. The event row also stores `content_sha256` (SHA-256 of the full pre-redaction combined text, computed transiently, never the raw text). On INSERT conflict on `dedupe_key`: same hash = duplicate, expected; different hash = genuine collision/update — first event kept, no second delivery for the same `qkey` (legacy behaviour), counted as `identity_collision` and surfaced in diagnostics, never silently merged. Residual: two distinct events sharing `(package, postTime-ms, amount, first-40-hash)` are indistinguishable from an update; the first is kept.

### 3.1 Transaction identity — P3 fields, matching, classification (normative, owner-decided 2026-11-15, comment id 6903307191)

**Field model (normative).** One canonical event carries these structured fields, each with a confidence value and a source note; absent fields are omitted, never invented. This replaces the single `reference` token in the §7.1 confidence matrix:

| Field | Meaning | Source (in-memory, transient) |
|---|---|---|
| `bank_reference` | Bank-generated transaction reference/ID as labelled in the notification (e.g. `Ref`, `No. Ref`, `ID Transaksi`, `Kode Transaksi`) | Labelled span only, from the per-source confirmed vocabulary (§3.1.3) |
| `order_number` | Merchant-specified order number the payer was instructed to put in the transfer reference/description | Labelled or positional span matching a merchant-registered pattern (§3.1.4); never a bare-digit fallback |
| `sender_name` / `sender_account_masked` | Payer identity as stated in the notification; account masked to last 4 digits | Labelled span only; omitted when unlabelled or unverified |
| `recipient_name` / `recipient_account_masked` | Beneficiary as stated, where present | Labelled span only; omitted when absent |
| `purpose_text` | Transaction purpose/description span as stated (invoice linkage, donation program name, free text) | Labelled span only; never a paraphrase |
| `direction` | `in` / `out` / `unknown` | Existing two-list OUT-first scan over transient text (§7.1); never inferred from an ambiguous cue |
| `amount`, `currency` | Amount in rupiah; currency token as captured | Existing parser; multi-token ambiguity follows the §7.6 `NEEDS_REVIEW` rule |
| `source_account_masked` | Which of the user's accounts received/sent it, where the notification states it | Labelled span only, masked to last 4; stored in `match_results.source_account_masked` (§4.6, R35); the full verified identity is never persisted — it exists only transiently at P3 confirmation (R35) |
| `order_link` / `customer_link` / `program_link` | Resolved links to an order / customer / donation program, nullable | Resolution against the order registry via the integration contract (§3.1.5); null when unresolved |
| `match` | `{status, confidence, rule_id, order_id?, audit}` | Matching subsystem (§3.1.2) |
| `classification` | `{category, confidence, rule_id, audit}` | Classification subsystem (§3.1.2) |

`bank_reference` (bank-generated) and `order_number` (merchant-specified, embedded in the transfer reference/description) are separate fields with separate patterns and separate confidence — a bank reference is never treated as an order number and vice versa.

**3.1.1 Namespaces — three distinct uses of "matched" (normative).** The word `matched` appears in three namespaces that must never be conflated:

- `legacy_match.status` — the server response field in the §5.3 wire contract (`matched`/`logged`/`ambiguous`), read from `notify.php`/`catat.php` responses. It is the only value that may be written to `deliveries.last_match_status`.
- `advisory_match.status` — the client-side P3 attribution result (`matched`/`ambiguous`/`unmatched`/`manual_review`), stored only in the `match_results` table (§4.6). It is never transmitted to the server, never written to `last_match_status`, and never mapped onto `legacy_match.status`.
- `MATCHED_SETTLED` / `MATCHED_NOT_APPLIED` / `MATCHED_UNCONFIRMED` — the client §5.4 response-classification taxonomy for a legacy POST outcome. It classifies a server response; it is not an attribution result.

An `advisory_match.status = matched` result is attribution evidence only. It never settles anything, never marks an invoice paid, never triggers a `notify.php` apply, and never produces a `MATCHED_SETTLED` claim. Any code or text that reads "matched" without its namespace is a defect.

**3.1.2 Matching vs Classification (normative).** Transaction Matching answers *which order/invoice does this bank transaction belong to?* Input: `order_number` + `bank_reference` + amount + currency + direction + source account. Output: `advisory_match.status` ∈ {`matched`, `ambiguous`, `unmatched`, `manual_review`} with a numeric confidence, the `rule_id` that fired, and an audit row (inputs used, registry version, timestamp, operator overrides). Transaction Classification answers *what purpose does this transaction serve when one bank account serves multiple uses?* Input: `purpose_text` + sender/recipient + configured category rules. Output: `classification.category` with its own confidence, `rule_id`, and audit row, computed independently of the match result — a transaction can be `matched` to an order and still `UNCLASSIFIED`, or classified `donation` with no order match. Neither subsystem reads the other's output as an input; neither writes its conclusion into the other's fields. Both record their full input set in the audit row so a later reviewer can replay the decision.

**3.1.3 Per-source extraction patterns (normative).** Patterns are configured per source package (GoPay, myBCA, …), not one global regex: each source gets a pattern table (label → field) confirmed against real samples. Evidence bar (extends the R12 bar): a pattern ships only after **≥2 privacy-sanitised real samples per pattern per source**, from different days/amounts, showing the exact label string; samples are redacted before sharing (no account numbers, full names, or OTPs). Unconfirmed patterns stay OFF and their fields are omitted. **No bare-digit fallback, ever** (retained C-b6 rule): digits without a confirming label may be an OTP; no parser may treat a redacted span or a bare digit string as a `bank_reference` or `order_number`. "OTP is never a reference" (§7.1) applies to every new field. The constructed-text self-check (§7.1 gating) extends to the new tokens: any inserted token containing a `catat.php` direction-list word as a substring (server `mb_strpos` semantics; e.g. `REF BAYAR 9`) falls back to the no-cue form + review flag. An `order_number` that would flip direction is never inserted into constructed text.

**3.1.4 Per-merchant matching rules and the order registry (normative).** A merchant registers an order-number pattern (shape: prefix, alphabet, length — e.g. `INV-` + digits) plus the order registry it maps against. Patterns are explicit merchant configuration, registered manually by the operator; the design does **no auto-learning** of order-number shapes from free text in v1.1 (owner decision P3(a), comment id 6903307191). Canonical merchant identity: `merchant_id` is the registry key assigned at merchant registration (operator-entered, stable across source accounts); it is not derived from a notification span and never inferred from free text. **Uniqueness scope (owner decision P3(b), comment id 6903307191 — this supersedes the R27 proposal "per merchant within one source account"):** an `order_number` is unique **per `merchant_id` across all source/bank accounts**. Distinct merchants may reuse the same order number. Schema: the order registry enforces a unique constraint on (`merchant_id`, `order_number`); registry lookups are keyed by (`merchant_id`, `order_number`) with no source-account component in the key. A candidate match must agree with the registered order on amount, currency, and direction; any mismatch ⇒ `manual_review`, never auto-attribution. A match on the order number alone, contradicting the order's amount, is a mismatch, not a match. **Cross-account repeats:** an event arriving through another account for an already-attributed order is **duplicate evidence, not a new independent order or payment** — but only where the decision table below (case B) proves it is the same bank transaction; otherwise it is distinct or indeterminate evidence under case (C). Where case (B) applies, it is recorded against the existing attribution with its own audit row, and it produces no second attribution and no settlement signal. If the repeat disagrees on amount/currency/direction with the registered order ⇒ `manual_review`. A second event claiming the same (`merchant_id`, `order_number`) ⇒ `ambiguous` ⇒ `NEEDS_REVIEW`, never a second attribution and never a settlement. Cross-merchant collisions are out of scope for the matcher and resolve to manual review. **Concurrency:** at most one attribution with status `attributed` per (`merchant_id`, `order_number`) — enforced by a unique partial index on the attribution table (§4.6); a concurrent second attribution attempt conflicts and is recorded as `ambiguous`/`NEEDS_REVIEW` unless verified same-bank-transaction evidence proves it is the same underlying bank transaction, in which case it is recorded as `duplicate_evidence` linked to the first attribution; never a second attribution. A unique-index conflict alone does not prove duplicate-bank-transaction identity. Absent / ambiguous / mismatched references ⇒ `manual_review` on the operator review surface (package, time, token list, content hash — never raw text), same surface family as the §7.6 amount review. The operator picks the order, corrects the number, or discards the attribution; the pick is audited with the same protocol as an amount pick (original values immutable, pick re-validates route/consent epochs).

> **R29 event-identity decision table (normative).** Apply the following **in this order**; a notification copy is not necessarily a second bank payment. (A) Same legacy `dedupe_key` + same stored content hash: notification duplicate; no new event/delivery or advisory attribution. (B) Different `dedupe_key`, but **verified same bank transaction identity** (confirmed `bank_reference` together with its source/merchant scope, or authoritative external evidence): retain a separate capture audit and link it as `duplicate_evidence` to the existing attribution; never second-attribute or settle. (C) Different/unknown bank transaction identity claiming an already-attributed (`merchant_id`, `order_number`): **distinct or indeterminate financial evidence**, `advisory_match.status=ambiguous`, `attribution_status=none`, operator `NEEDS_REVIEW`; do not label it a proven duplicate and never second-attribute or settle. (D) Two concurrent eligible claims for a previously unattributed order: DB constraint chooses one `attributed`; losing candidate becomes `ambiguous`/`NEEDS_REVIEW` unless verified same-bank-transaction evidence proves `duplicate_evidence`. (E) Amount/currency/direction mismatch always yields `manual_review` regardless of apparent reference reuse. `NEEDS_REVIEW` here is the **advisory attribution review gate**, not permission to change the legacy delivery state or suppress legitimate legacy delivery without an independently justified §5/§7 gate. Preserve immutable evidence and reason codes for each branch. The previous broad “cross-account repeat ⇒ duplicate evidence” sentence applies only to case B, not every cross-account payment. **Identity-hash comparison (R30, Q2):** before import, compare against `capture_staging.content_sha256`; after a committed import, compare against the canonical `events.content_sha256`. The import preserves that hash and the original legacy `dedupe_key` atomically from the staging row (§8.1 item 3). Never depend on `match_results.audit_json` as the source of event identity.

**3.1.5 Integration contracts (normative).** A future external billing/order system supplies order/customer mappings through an explicit contract: a versioned registry (endpoint or import file) with schema `{order_number, merchant_id, customer_id?, amount, currency, direction, status}` and a stated freshness/ownership rule. The contract is the source of truth for whether an order exists; the bank notification is not. **Bank notification alone never proves payer identity.** A notification states a sender name; the match attributes the transaction to an order on the strength of the order number + amount + direction + registry lookup together. Where the registry cannot confirm the payer, the event carries `sender_name` as stated, with confidence marked unverified, and the match confidence is capped below the auto-attribution threshold — the operator decides. The contract itself is a Phase 1.3 deliverable with its own fixtures; v1.1 ships the client-side field model and the advisory match only (§3.1.7).

**3.1.6 What must never happen (normative).** No settlement, no `notify.php` apply, and no recorder-row completion follows from a `bank_reference` / `order_number` match alone. The §5 matcher and the §7 privacy, consent, `FallbackGate`, UNKNOWN-reconciliation, and dedupe safeguards are not bypassed by P3 in any form. No field is fabricated: an absent sender, recipient, purpose, or order number is omitted with a review flag, never filled from a guess, a neighbouring span, or a default. `dedupe_key` is unchanged by P3: it is still computed from the pre-redaction transient input identically for live and rescan. P3 fields never enter the key — otherwise a key computed from a parsed reference would diverge from the legacy key for the same notification and reopen the double-settlement hole F-P1-02 closed. **Advisory match/classification is admin/operator-only in v1.1** (owner decision P3(c)): the review surface is the operator surface; no customer-facing display of advisory results exists in v1.1. Optional customer-facing visibility may be designed later, only with separate owner approval and its own access/privacy rules.

**3.1.8 Legacy impact (normative).** `notify.php` / `catat.php` semantics are unchanged in v1.1. `notify.php` reads named keys only (`amount`, `dedupe_key`, …); no unknown-key rejection was observed in the read (`warganet/paylist/notify.php:81–87`), so the new structured fields in the payload are expected to be ignored — but that is a **contract-fixture gate, not an asserted fact**: a fixture proving extra fields are ignored ships before any v1.1 payload carries them. `catat.php` keeps its text heuristic; the structured `direction` field is advisory only in v1.1. **No new raw persistence.** The new fields are structured values derived in memory from transient text; they add no raw-text storage and no new class-(a) surface. Where a field cannot be verified it is omitted, so P3 adds no new PrivacyGate bypass.

**3.1.9 Registry limitation, stated plainly (normative).** The v1.1 registry is supplied as a versioned import for the MVP fixtures; there is no live contract endpoint in v1.1 (§3.1.7). Cross-account uniqueness (§3.1.4) is enforceable only against the imported registry version recorded on the attribution audit row. An order absent from the imported registry cannot be matched — the event is `unmatched`/`manual_review`, never matched by guessing. The freshness/ownership rule for the registry is part of the Phase 1.3 contract deliverable; until it exists, the registry version on each attribution is the audit trail, not a freshness guarantee. v2New routes: cross-account matching for v2New cannot be verified until P11 lands (§9.6); v2New copies stay `HELD` for attribution purposes until then.

> **R29 clarification — registry state, freshness, and immutable history (normative; implementation contract).** The registry import is a **complete, validated snapshot for a single canonical merchant** with `registry_version`, `imported_at_ms`, `source_owner`, and `valid_until_ms` (or an explicit `freshness=UNVERIFIED` state). Imports must validate uniqueness, schema, currency/direction, and merchant identity before one atomic swap of that merchant's active snapshot; an invalid or partial import leaves the prior version intact. Registry status must be explicitly `ACTIVE` before advisory attribution; missing, expired, unknown-freshness, cancelled, or ambiguous orders are held for operator review and are never auto-attributed. No automatic inference of customer/payer identity from notification text. The import format, expiry policy and operator ownership are acceptance-gate deliverables before enabling attribution; until approved/configured, advisory results may be `unmatched`/`manual_review` only. Each result retains the registry version and decision inputs. A later import may **re-evaluate only previously `unmatched` or `manual_review` events** through an explicit, audited operator action; never silently overwrite historical `attributed` rows, change a settled invoice, or delete an earlier result. Corrections append a superseding audit decision with old/new version and operator identity. A stale registry must not block ordinary legacy notification delivery, which remains governed by §5 and §7, not by advisory attribution.

### 4.5 `capture_staging`, `promotion_receipts`, sweep fences

- **`capture_staging`:** keyed by unique `dedupe_key`; carries `legacy_qkey`, `content_sha256`, `payload_sha256`, `consent_epoch`, `config_epoch`. Deleted only after a verified durable commit in the target store — never before, never in the same step (legacy path: after `saveQueueSync` commit + readback proving the item present; Room path: outbox insert + staging delete in one Room transaction). The sweeper re-promotes orphaned staging rows through the same lock/mode/consent gate; re-promotion is idempotent. **Invariant (normative): a staging row is deleted only after the target store proves the event is durable.**
- **`promotion_receipts`:** `legacy_qkey` PK, `state` (`PREPARING → READY → IN_FLIGHT → RESOLVED`), `promoted_at`, `resolved_at`, `outcome` (`dispatched` | `no_post`), `next_route_index`, `hop_outcomes[]`, `last_hop_outcome`. Creation in `PREPARING` in its own Room transaction; moves to `READY` only after the legacy enqueue is verified durable (`saveQueueSync`: `commit()` + readback proving `qkey` present); to `IN_FLIGHT` immediately before the sender releases `Sender.LOCK` to POST; to `RESOLVED` when the sender writes the resolution ack. The sender is the only code that moves a receipt out of `READY`. **Dispatch gate (normative):** the flush consults the receipt before any POST: `PREPARING` → never POST; `READY` → POST permitted, receipt to `IN_FLIGHT` first; `IN_FLIGHT` (after restart) → outcome unknown, re-POST permitted under at-least-once, counted as a possible duplicate; `RESOLVED` → drop without POST even if the item is still in the queue file. **Invariant (normative): a `qkey` leaves the legacy queue only after a durable resolution ack exists.** Residual window: POST succeeded, before the ack write (`IN_FLIGHT`) — a duplicate POST is possible. Irreducible without server-side idempotency; the ledger shrinks the duplicate window from "any time between legacy commit and staging delete" (unbounded) to "milliseconds between POST success and ack commit inside one flush iteration", the same window the baseline already has for every dispatch.
- **Sweep fences:** `{fence_id, event_id/dedupe_key, installed_at_ms, state: ACTIVE | RELEASED}` plus the awaited set captured in the same install transaction (see §8.6).

**Atomicity:** event and delivery creation in one Room transaction; claim/lease in one transaction; each ACK state transition in a transaction. Do not hold DB transactions during network I/O. If storage fails, expose explicit diagnostic failure; never claim the event was safely queued.

## 5. Delivery state machine and legacy contract

```text
PENDING --claim--> IN_FLIGHT
IN_FLIGHT --2xx valid matched/ambiguous--> ACKED (chain stops)
IN_FLIGHT --2xx valid logged--> persist next_route_index; continue chain
IN_FLIGHT --network/408/429/5xx/protocol invalid--> RETRY_WAIT
RETRY_WAIT --due--> PENDING (then claim)
IN_FLIGHT --nonretryable 4xx/missing route--> BLOCKED
IN_FLIGHT --lease expired--> PENDING (only when no unresolved attempt marker; see below)
BLOCKED --explicit operator action--> PENDING
RETRY_WAIT --TTL expired (heartbeat/test only)--> EXPIRED
```

A successful `logged` response for the last eligible route means chain **completed without match**: `ACKED` with `last_match_status=logged` (not payment settled). `ambiguous` is acknowledged but needs manual business review. Preserve route order; route deletion/disabling while queued must not silently discard an event: `BLOCKED` with actionable reason.

### 5.1 Lease (C7, normative)

> Lease duration is 5 minutes (longer than the 30 s total HTTP timeout + server processing margin). No renewal. Each claim sets `lease_owner` (fresh UUID per claim) and `lease_until_ms`. Every state transition is conditional on the stored `lease_owner` still matching the worker's token AND the lease being unexpired — a single conditional UPDATE. A worker that finds its lease lost or expired must discard its in-flight result and must not write any state for that delivery. An expired lease is not proof the server finished its side effects: the previous worker's POST may still be in flight or applied. Safety against double-apply comes from server dedupe (same `dedupe_key`), not from the lease — the lease only prevents double-claim. A reclaim-and-retry after lease expiry therefore receives the DUPLICATE response (no `apply` field); `last_apply_status` stays null and the delivery is covered by the reconciliation gate. **Qualification (R16, retained):** the diagram line "`IN_FLIGHT` --lease expired--> `PENDING`" holds only when no `ATTEMPT_STARTED` row for that delivery is unresolved; an unresolved marker holds the delivery in `UNKNOWN_PENDING_RECONCILIATION`.

### 5.2 RETRY_WAIT → PENDING actor (C8, normative)

> The transition is performed by the `SyncWorker` claim query, which claims `PENDING` or `RETRY_WAIT` rows with `next_retry_at_ms <= now` in a single transaction. There is no separate state-flip step; `SyncScheduler` only guarantees a work item is scheduled while due items remain.

### 5.3 Legacy wire contract

`type`, `device`, `pkg`, `amount`, `title`, `text`, `notif_time`, `dedupe_key` for payment. Heartbeat/test retain their existing field expectations. Preserve `X-QRIS-Secret`; add `app_version`/`schema_version` only after explicit contract tests demonstrate the server ignores extra fields. "Wire/semantic compatible" (C10): semantics and field values match; no byte-identical requirement. What is tested is JSON equality after parsing (T02/T03). The v1.0 term "byte-level compatible" is withdrawn. Advisory P3 fields (`bank_reference`, `order_number`, `advisory_match.status`) are never transmitted as a settlement signal: no wire payload carries an advisory `matched` as `match.status`, and no server apply follows from one (§3.1.1, §3.1.6).

### 5.4 Response classification (normative, C1/C2/C9, R16 taxonomy, R19 3xx rule, R23 H2 4xx halt)

| Result | Action |
|---|---|
| 2xx payment `matched` + `apply=ok` | `MATCHED_SETTLED` — settlement confirmed. ACK chain, chain stops |
| 2xx payment `matched` + `apply=skip` | `MATCHED_NOT_APPLIED` — match recorded, this attempt did not settle the bill. ACK chain, persist `last_apply_status='skip'`, flag for manual review, chain stops. Reconcile before any settlement claim (status query: is the payment row `PAID`? if paid by another path, settled-elsewhere; if unpaid, operator action) |
| 2xx payment `matched` + `apply=error`, or `apply` absent | `MATCHED_UNCONFIRMED` — chain stops, never continue to another route; reconcile before recording settled. `last_apply_status` stays empty/null on a duplicate ACK — never assume `'ok'` |
| 2xx payment `matched` on a response carrying `duplicate=true` | Apply is definitionally absent on a duplicate response — treat as `MATCHED_UNCONFIRMED` even if the endpoint echoes a stale `apply` value; never trust an `apply` value on a duplicate; chain stops; halt for reconciliation |
| 2xx `ambiguous` | `AMBIGUOUS` — ACK chain, flag for manual review, chain stops; never settlement |
| 2xx `logged` | Advance chain; ACK if last route. A `logged` response observed in-process proves the POST reached the server (the endpoint INSERTs the log row on every accepted POST) — the hop finished with a known outcome (no match on this route, no settlement) |
| 2xx missing/malformed `match.status` on payment | Retry same route, do not advance |
| 2xx heartbeat/test with `ok=true` | ACK, whatever the `match` block contains (`null` on fresh notify; `{'status':'logged'}` on catat and on notify duplicates). The `match` block is irrelevant for non-payment types. `catat.php` always returns `match.status='logged'` for all three types, so the "missing/malformed `match.status`" row never triggers endless retry on recorder routes |
| 2xx heartbeat/test without `ok=true` | Failed attempt, retry per backoff; heartbeat TTL still applies |
| 408 / 429 | Retry; parse bounded `Retry-After` if valid |
| 5xx / timeout / network | Retry with exponential backoff + jitter |
| 400/401/403/404/other nonretryable 4xx | `BLOCKED`, visible, chain halts. A 4xx proves the POST reached the server and was rejected *before* any recorder row (verified: auth and validation precede the INSERT in both endpoints). Diagnostic category recorded in the attempt row: 401/403 ⇒ auth/consent/config; other 4xx ⇒ payload/endpoint. No advance, no retry; operator re-approval retries the same hop |
| 3xx | Non-retryable: the hop is `BLOCKED` for operator review, surfaced with the `Location` header, never re-POSTed automatically. With redirects disabled, a 3xx is a route-configuration defect, not a transient failure. The baseline classifies 3xx as retryable (`Sender.kt:200–210`, the `else` branch), which would retry a redirected POST forever — v1.1 changes this |
| `matched` with `apply=error` | Persist ACK/claim state and flag business failure; **do not blindly replay to another route or retry settlement** |

**Why `matched` is not settlement (R16 §4, verified).** Warganet `notify.php` (`:134–165`): on first insert with exactly one candidate, `match_status='matched'` is UPDATEd *before* `paylist_apply_payment` runs, and the apply result is a separate field — `$match['apply'] = $applyRes['applied'] ? 'ok' : 'skip'`, or `'error'` if the call throws. `paylist_apply_payment` returns `applied=true` only after a single DB transaction commits (payment `PAID` + `pemasukan` row + `applied_at` set); `applied=false` covers already-`PAID`, already-applied, test-gate, and rolled-back failures — all pre-commit, no partial effects. On a *duplicate* POST the endpoint returns the stored `match_status` with **no `apply` field at all** and never re-runs apply. So a `matched` response with `apply` absent can mean the first attempt matched and applied, matched and did *not* apply, or a duplicate of either — and `matched` + `apply=skip` positively means the bill was *not* settled by that attempt. v2New parity is **not** verified (its `notify.php` is not in the repo — P11); the design must not assume v2New returns `apply` identically to warganet.

**Restated no-double-settlement basis (normative, R16).** The promise rests on three legs, *not* on "`matched` implies settled": (i) chain-stop on any `matched`/`ambiguous` response, so no second route is ever attempted after a match; (ii) server `dedupe_key` idempotency for the same endpoint; (iii) reconciliation before any second-route attempt after an unknown hop. What the client may claim: `MATCHED_SETTLED` ⇒ settled; anything else matched ⇒ the payment *may* already be settled, the bill's state is unknown from this response, and no settlement is recorded until reconciliation proves it.

**Redirects (normative, C9).** `TransportClient` uses `HttpURLConnection` with `setInstanceFollowRedirects(false)` (or OkHttp with `followRedirects(false)` if OkHttp is chosen — decide in Stage A). Any 3xx is classified BLOCKED without following `Location`; the secret is never sent to any host other than the route host. The Android `HttpURLConnection` default follows up to five redirects, across origins, re-sending request headers (including `X-QRIS-Secret`) to the redirect target — without the explicit `false`, the §5 policy does not happen.

**Server idempotency (verified basis).** `notify.php` (warganet): idempotent `INSERT … ON DUPLICATE KEY UPDATE id = id` over `dedupe_key VARCHAR(128) NOT NULL UNIQUE`; matcher + apply run only when `$inserted`; a duplicate POST returns the stored `match_status` with no `apply` field. `catat.php` (both copies): idempotent `INSERT … ON DUPLICATE KEY UPDATE id = id` over `dedupe_key … UNIQUE`; a duplicate is a no-op (first-write-wins, including on direction); no settlement side effect. Apply is already idempotent at the DB level for warganet: the `applied_at` guard returns "sudah pernah diterapkan"; the payment claim is `UPDATE payment SET status='PAID' … WHERE id=? AND status<>'PAID'` with `affected_rows` required to be 1; the pemasukan write is guarded by the G4 `idtrx` existence check; claim + pemasukan + `applied_at` commit in one transaction. A second apply attempt therefore cannot double-settle. This is the basis on which the sweep may treat `matched` + `applied_at` as terminal — and the reason the sweep still never triggers apply itself.

**Stale-read window (F-P2-01, residual risk).** Both `notify.php` files run INSERT, then — without a transaction/lock — SELECT candidates + UPDATE `match_status='matched'`. A concurrent duplicate arriving between INSERT and UPDATE reads `match_status='logged'` and returns it; the client then advances the chain although the first system already matched. The window is milliseconds wide and needs two concurrent senders; a single-sender replay after a ≥15 s timeout cannot hit it. Mitigation is client-side only (the server fix, a transaction/`SELECT FOR UPDATE`, is outside the Android scope and on the FILE_PLAN §G no-change list): verify before cutover that no second concurrent sender exists (C15/G8), and keep the worker lease longer than the HTTP timeout so replay cannot overlap a still-running request.

**Backoff:** start 1 min, multiply 2, cap 2 h, jitter ±25%; honor `Retry-After` with reasonable cap. No silent deletion on retry exhaustion: mark `BLOCKED`/needs attention after policy threshold, with manual retry. Preserve fairness: one failing item must not block others. Batch up to 20 due deliveries per worker invocation, configurable; unique work avoids unnecessary duplicate scheduling, while the DB lease prevents concurrent claim races.

### 5.5 Per-hop outcomes (normative, R15 §2 as revised by R16 §4)

After every POST returns, before the next hop is considered, the flush persists a per-hop checkpoint: attempt row + receipt's `next_route_index` + `last_hop_outcome` in one Room transaction (no Java lock held), then `saveQueueSync` of the queue item's `next` + `hop_outcomes`. Only after the checkpoint is durable does the flush evaluate the drain request.

| # | Situation | Outcome | Chain |
|---|---|---|---|
| 1 | First attempt, 2xx `logged` | `LOGGED`, advance | Next hop |
| 2a | First attempt, 2xx `matched` + `apply=ok` | `MATCHED_SETTLED`, terminal | Stops |
| 2b | First attempt, 2xx `matched` + `apply=skip` | `MATCHED_NOT_APPLIED`, chain stops | Reconcile before any settlement claim |
| 2c | First attempt, 2xx `matched` + `apply=error`, or `apply` absent | `MATCHED_UNCONFIRMED`, chain stops | Reconcile |
| 2d | First attempt, 2xx `ambiguous` | `AMBIGUOUS`, chain stops | Review |
| 3 | First attempt, 4xx | `REJECTED-4xx`, **halt** — delivery `BLOCKED`, visible, `next_route_index` unchanged; operator re-approval retries this hop | Held |
| 4 | First attempt, 5xx or `SocketTimeoutException` (request may have reached server) | `UNKNOWN_PENDING_RECONCILIATION`, halt — do not advance, do not skip | Held |
| 5 | First attempt, connect/DNS failure (provably nothing sent) | `NO_POST`, retry later, do not advance | Same hop |
| 6 | Hop entry, route null/disabled/empty URL/empty secret | `NO_POST` (skip), advance (baseline skip, provably no settlement) | Next hop |
| 7 | Hop entry, stamp mismatch — `consent_epoch`, `config_epoch`, or `url_sha256` differs | `BLOCKED_CONSENT` / `BLOCKED_CONFIG`, halt — do not advance | Held |
| 8a | Re-POST after unknown, 2xx `matched` + `apply=ok` | Resolves to `MATCHED_SETTLED`, terminal — the only in-band way an unknown hop clears as settled | Stops |
| 8b | Re-POST after unknown, 2xx `matched` + `apply≠ok` or absent | Stays `MATCHED_UNCONFIRMED`, chain stops; halt for reconciliation | Held |
| 8c | Any re-POST, response carries `duplicate=true` | Apply definitionally absent on a duplicate — treat as 8b even if the endpoint echoes a stale `apply` value; never trust `apply` on a duplicate; chain stops; halt for reconciliation | Held |
| 9 | Re-POST after unknown, 2xx `logged` | Stays `UNKNOWN_PENDING_RECONCILIATION`, halt (a duplicate `logged` is consistent with both "first attempt never committed" and "first attempt matched, duplicate now logged" — it proves nothing about the first attempt; also the F-P2-01 stale-read window) | Held |
| 10 | Re-POST after unknown, 4xx/5xx/timeout | Stays `UNKNOWN`, halt (a re-POST failure proves nothing about the first attempt) | Held |
| 11 | Any, reconciliation evidence (status-query response, server-log audit, operator confirmation) | Resolves to the evidenced outcome (`MATCHED`, `LOGGED`, or `NO_POST`), advance/terminal per evidenced outcome | Per evidence |

Row 4 is deliberately conservative: 5xx is grouped with timeout because the server may have committed the payment and then failed writing the response. Rows 8–10 are the only in-band ways an unknown hop can change state, and only row 8a can clear it in-band; row 11 is out-of-band. Cost: a payment with an unknown hop waits — not retried past the hop, not skipped, not settled elsewhere — until reconciliation resolves it. That stall is the price of no double settlement; the reconciliation mechanism is a pre-pilot gate (§9), not an afterthought.

## 6. WorkManager, heartbeat and rescan

- On a new persisted event: enqueue **unique OneTimeWork** with a network constraint; use a scheduler that avoids `KEEP` suppressing newly due work after the current worker finishes. The worker should schedule another run when due items remain.
- Periodic work (minimum 15-minute interval) is a **best-effort wake-up**, not guaranteed execution every 15 minutes. Heartbeat is a distinct event with existing legacy heartbeat dedupe bucket semantics (`hb-<routeId>-<bucket>`, 15-minute bucket; the sender drops a heartbeat when the bucket gap is ≥ 2, i.e. 30 minutes). An expired heartbeat can be dropped only under the documented TTL (30 min / 2 dedupe buckets → terminal `EXPIRED`, §4.2); payment deliveries are never silently expired.
- Monitor `last heartbeat ACK`, `last event ACK`, and `last collector connection` independently. Server alert thresholds must be tuned from real measurements; **do not assume a 20-minute threshold is safe** under Doze.
- `activeNotifications` rescan runs **inside a connected NotificationListenerService**, on connect or manual request, not directly in a generic WorkManager worker. Preserve the 24-hour rescan window, group-summary filtering, and stable legacy dedupe key. Rescan calls the same `processNotification` → same executor → same lock → same mode read as live capture, so C3 key consistency holds on both paths (C21(9)).
- Reboot: WorkManager reschedules work as allowed; a boot receiver can request reconciliation but must not launch unbounded threads. Force-stop cannot be reliably bypassed. No foreground service in this phase.
- **Dual-run heartbeat during stages C–D (C18, normative):** during stages C–D, the AlarmManager and WorkManager heartbeats run concurrently; this is safe because of the server dedupe bucket (15-min `hb-<routeId>-<bucket>` key), and AlarmManager is disabled in stage D after HeartbeatWorker is verified. Monitoring expectation during this period: duplicate heartbeat attempts with one stored row per bucket.
- **Single-item migration (C12, normative):** a legacy single item (heartbeat/test) maps to one `LEGACY_CHAIN` delivery with `route_ids_json=[route_id]` and `next_route_index=0`; absent `attempts`/`last_error` default to 0/empty. New heartbeat/test events also use a single-route `LEGACY_CHAIN` delivery while their endpoint is legacy.
- **Rescan cross-store rule (normative, R10 C21(4′)):** Room enqueue dedupes on `dedupe_key` inside the same transaction — before inserting, the executor queries for an existing PENDING/IN_FLIGHT delivery with the same `dedupe_key` and skips the insert if one exists. Rescan during DRAINING or BLOCKED_CUTOVER therefore cannot create a second Room row for an event already held in Room.

## 7. Privacy, secrets and network

### 7.1 PrivacyGate — the four-class rule (C4, final form R8/R9/R10 as amended by R23/R24)

> **(normative).** PrivacyGate runs before **any** durable write, on both the live and rescan paths. A confirmed secret must never appear in a stored raw payload, `legacy_payload_json`, local logs, diagnostics, or an extracted `reference`.
>
> - **(a) CONFIRMED** — OTP/PIN/password/password-reset/auth token: never **persisted** in raw form on any route, in any store. A separable span → replaced by `[REDACTED]`, the rest preserved, flagged `redacted: true`. A pure OTP/auth event (no financial record) → the whole event dropped, local diagnostic counter only. **Transmission** of a class-(a) span in raw form is prohibited by default and permitted **only** under the §7.3 Option B exception: on a route with a valid, unexpired, unrevoked per-route opt-in, for that route only, from an in-memory snapshot that is never written to disk (§7.3A), and only for a mixed financial+OTP event (a payment event that also carries a class-(a) span). A pure-auth event is never B-eligible on any route: it is dropped at capture with a diagnostic counter only, even on a B route. Every other route, and every route without a valid opt-in, transmits the A′ structured form only.
> - **(b) AMBIGUOUS** — credential-like spans with no confirming **local** context (bare 4–12 digit strings, unlabelled codes): classification binds each span to its local label/cue, never to cues elsewhere in the message. An unlabelled bare span stays AMBIGUOUS and is redacted even if an amount appears elsewhere. A financial cue elsewhere does **not** promote it. A local auth cue promotes it to (a); auth cues win over financial cues for that span.
> - **(c) FINANCIAL_IDENTIFIER** — structured amount, transaction reference/ID, partially masked account number, direction cue, sender/recipient name, transaction description, on any route: preserved. A labelled reference/ID (`Ref`, `No. Ref`, `ID Transaksi`, `Kode Transaksi`, …) is class (c) **whether or not an amount is present** — the label is itself the financial context. Direction-cue words are never redacted. Referral/promo codes (`Kode referral`) are NOT financial identifiers and NOT auth secrets: unlabelled, they stay AMBIGUOUS/redacted.
> - **(d) Legacy exception** — ordinary financial notifications on legacy routes preserve the payload verbatim under the explicit per-route exception (`legacy_text_exception: true`); the exception **never covers persistence of class (a)**. Final wording: "verbatim except mandatory credential redaction and agreed ambiguous-span redaction"; where (a) applies, the redacted text is what is persisted. Transmission of a class-(a) span is governed solely by §7.3, never by this exception. `dedupe_key` is computed from pre-redaction transient input in memory only (C3); raw text is never written to durable storage on structured routes. Amount is a structured field and cannot be redacted.
>
> **OTP is never a reference (normative).** PrivacyGate must not extract, store, or emit a `reference` from a class-(a) span; no parser may treat a redacted span as a reference.

**Supersession note.** R1 proposed fail-closed only for new routes; R3 replaced that with fail-closed for CONFIRMED on all routes; R5 said drop the whole event on any confirmed secret; R7 refined to span-redaction with the event preserved; R7's whole-message promotion was withdrawn in R8; R7's C-b3 (a labelled reference requires an amount) was withdrawn in R8; R8's F11 whole-event drop for inseparable spans was superseded by R9/R10 (§7.2). The R9/R10 form above is the final C4.

**Confidence matrix (normative, R11–R12).** Fields are derived in memory from transient raw text:

| Field | Source (in-memory, transient) | Confidence | If unverifiable |
|---|---|---|---|
| `amount` | First Rp/IDR token (`parseAmount`, verified baseline) | High for single-amount texts; two-amount texts can mis-pick — existing baseline behaviour, preserved | Sent as parsed, flagged `amount_ambiguous: true` when ≥2 currency tokens; flag is new diagnostics, value rule unchanged |
| `direction` | Same two-list OUT-first scan `catat.php` runs, in memory over transient raw text, common-subset vocabulary of both PHP copies | Medium-high when a list word is present; deterministic (OUT-first) when both sides match | No list word → `unknown` template (no-cue form) + review flag; never guessed |
| `bank_reference` | Labelled span only, from the per-source confirmed vocabulary (§3.1.3) | High only after per-source confirmation against real examples | Omitted. Never fall back to bare digits — in the C-b6 shape the digits *are* the OTP; a bare-digit fallback would forward the secret |
| `order_number` | Labelled or positional span matching a merchant-registered pattern (§3.1.4) | High only after the merchant pattern is registered and confirmed against real examples | Omitted when no registered pattern matches. Never a bare-digit fallback |
| `sender_name` / `recipient_name` / `purpose_text` | Labelled span only | Medium | Omitted when unlabelled or unverified |
| `masked_account` | Labelled account span, masked to last 4 digits | Medium — no baseline; masking rule (all but last 4 replaced) is new | Omitted when the label is unconfirmed or the span is <4 digits |

**Gating (normative).** `bank_reference`/`order_number`/`sender`/`recipient`/`purpose_text`/`masked_account` tokens ship only after their per-source pattern is confirmed (§3.1.3) and, for `order_number`, the merchant pattern is registered (§3.1.4); until then they are omitted. Option A′ ships day one with amount + direction only. The constructed-text self-check runs over the full constructed text including inserted tokens, against both PHP lists with server substring semantics (`mb_strpos`; e.g. `REF BAYAR 9` contains `bayar` and would flip direction to `out`). Any mismatch, and any inserted token containing any list word as a substring, falls back to the no-cue form + review flag. Constructed text is built purely from structured fields, never from a raw substring; OTP digits are never reused as a reference.

**Irreducible tradeoff (stated, R12).** Option A′ is designed so no auth secret is stored/forwarded — a security *objective*, not a proof: pattern classification can miss an unseen OTP format; the residual false-negative risk is stated, mitigated by adversarial fixtures (F19), the staging re-scan gate, and conservative quarantine (ambiguous → structured-only or dropped, counted `dropped_unclassified`). A′ does *not* guarantee recorder direction classification or a reference for inseparable spans: those degrade to `unknown`/omitted + review flag. If no trustworthy field exists beyond amount + package + time, the record is still preserved (D8) as a minimal record — amount, time, package, direction `unknown` — not a complete recorder row. A guaranteed complete recorder row for an inseparable span is only possible by forwarding raw text (Option B under P6, §7.3) — but B preserves *information* in raw text, it does not guarantee a correct recorder row (the server classifies with the same substring heuristic and can still misread), and it carries auth-secret exposure.

### 7.2 Inseparable spans — Option A′ (default)

> **(normative, R10 Option A′, final as the default rule).** Where a financial record and an OTP span cannot be safely separated, the financial record is preserved as structured fields extracted in memory — amount, direction (computed in memory from the same keyword lists `catat.php` uses), masked account, labelled reference — the inseparable raw text is dropped, never stored or sent, and the event is flagged `redacted: true, inseparable: true`. For recorder routes, the client constructs a minimal recorder text **purely from structured fields, never from any substring of raw text**, using only the common keyword vocabulary of both `catat.php` copies: `out` → `Transfer ke {masked_account} Rp{amount} Ref {reference}`; `in` → `Diterima Rp{amount} dari {masked_account} Ref {reference}`; `unknown` → `Rp{amount} {masked_account} Ref {reference}`. The `Ref` token appears only when a labelled, non-secret reference exists; `{masked_account}` is omitted when absent; `title` is sent empty. The client runs the same two-list heuristic (common subset) over the constructed text and asserts it yields the intended direction; on mismatch it sends the no-cue form and flags for review. The structured `direction` field is still attached as an extra JSON field (ignored by PHP today). **OTP digits are never reused as the reference** — in the C-b6 shape (`Kode OTP transaksi 482913`) the digits are the secret, so no `Ref` token is emitted.

**Recorder contract (verified 15 Nov 2026, R10).** Both `catat.php` copies: direction heuristic `$hay = strtolower(title.' '.text)`, OUT checked first then IN; v2New OUT: `terdebit, debit, keluar, pembayaran, bayar, tarik tunai, belanja, pembelian, transfer ke, kirim ke, pengeluaran, spent`; IN: `masuk, diterima, kredit, setoran, top up, topup, refund, pengembalian, pemasukan, received`; the warganet lists are subsets (OUT lacks `pengeluaran, spent`; IN lacks `pemasukan, received`); the common vocabulary is the intersection, and only words in it may appear in templates. Required: `device` + `dedupe_key` non-empty (else 400 `missing_fields`); `amount` int ≥0 (else 400 `bad_amount`); `type` ∈ {payment, heartbeat, test} (else 400 `bad_type`); `X-QRIS-Secret` auth (401). `title`/`text` optional (default `''`, truncated 500 chars). Extra JSON fields are ignored. The response echoes the computed `direction` + `match.status='logged'`; a duplicate returns `recorded: false`. The payment matcher reads `amount` only — text cannot affect matching. The keyword lists live in two PHP files and can drift — fixture F19 pins the lists as verified 15 Nov 2026; any PHP list change requires re-running the fixture and, if the common vocabulary changes, a client update; the drift check belongs in the contract-test gate.

### 7.3 P6 Option B — raw forwarding under granular informed opt-in (OWNER DECISION, 2026-11-15)

> **(normative, D6 — owner decision, preserved in substance).** The owner decided option B on 2026-11-15: forward the original notification without removing OTP, **only** after the user has explicitly accepted a prominent risk warning; preserve financial transaction details including transfer information, reference number, and partial account number; do not silently discard the financial event. This is a deliberate selection of B, not A′. Design consequences:
>
> - **(a)** Granular informed opt-in **before** any raw forwarding, scoped per destination/route, with a persistent auditable consent version/epoch.
> - **(b)** The opt-in disclosure names the categories that may be transmitted to third-party servers — authentication codes, transfer information, reference numbers, account numbers — in plain words, at the moment of consent, not buried in settings.
> - **(c)** Revocation behaviour is specified: revocation stops future raw forwarding for that route immediately; already-forwarded content cannot be recalled, and the disclosure says so.
> - **(d)** Fail-closed on missing, expired, or revoked consent — a route without a valid opt-in never forwards raw content.
> - **(e)** No raw OTP is transmitted before the opt-in exists and is validated.
> - **(f)** The release-time re-gating rule (§7.5) is extended: every manual release re-runs PrivacyGate and the per-route consent check **including the P6 opt-in** at release time, enforced in code on the release path.
>
> **Scope rule (normative, corrected R24, as amended by the owner P6 decision 2026-11-15).** Option A′ (§7.2) remains the default rule for every route. Option B is a per-route exception that applies only to a route with a valid, unexpired, unrevoked opt-in. A route's opt-in status is checked at capture, at promotion, at claim, and at release. **(a) Capture-time failure.** If no valid, unexpired, unrevoked opt-in exists at capture, no raw snapshot is retained and the delivery is A′ from the start — it was never a B delivery, so nothing is substituted. **(b) Post-capture failure.** If the opt-in expires or is revoked after capture, the delivery transitions to `BLOCKED` (`consent_expired` / `route_revoked`), the in-memory raw snapshot is dropped immediately, and **no dispatch follows automatically in any form**. A later dispatch requires explicit operator re-approval, which authorises A′ for that delivery and is recorded with the operator identity and timestamp; without it the delivery stays `BLOCKED`. Revocation is consent withdrawal, not a config tweak — the same reason §7.5 halts a chain on revocation rather than advancing it. **(c) Post-capture raw loss with a valid opt-in** is governed by §7.3B (guarded best-effort fallback), not by this scope rule: the delivery never silently becomes A′ by default, and never silently drops the financial record.
>
> **Platform/policy review — OPEN VERIFICATION GATE (normative).** Before implementation, the design must check the current Google Play policy on forwarding authentication codes and sensitive notification content to third-party servers, and the Android notification-listener permission/consent UX — against the policy text, not from memory. If a constraint blocks B, the design returns to the owner; B is never silently narrowed, and no policy conclusion is asserted in this document. This gate is a verification gate, not permission to substitute sanitisation for B.

**Supersession note.** R20 §5 "no release path forwards raw OTP content to any route" is superseded by the owner decision P6 option B (D6) for routes with a valid opt-in; the re-gating rule stands, extended with the opt-in check. R10's framing ("accept A′ as final, or authorise B? Default: A′") is superseded in substance: the owner has authorised B, per-route, under the conditions above. R23/R24: §7.1(a), §7.1(d), §7.4, and §8.3(2′) as previously worded are superseded by the corrected clauses in §7.1/§7.4/§8.3 and by §7.3A below; the §7.3 scope rule's "any check failing means the route falls back to A′" is withdrawn as written and replaced by the split rule above. R24 §1.3's strict default (raw loss always holds for an operator decision) is superseded by the owner P6 guarded-best-effort decision of 2026-11-15 (comment id 6896048588): raw loss is now governed by §7.3B.

### 7.3A Option B data-flow — ephemeral-only raw (normative, R23 as corrected by R24)

> **(normative).** The owner decision authorises *transmission* of raw text, not *storage* of it. The governing distinction, stated once and applied everywhere below: **A′ is the default, not a fallback. A delivery becomes a B delivery only at capture, under a valid opt-in; once a B delivery, it never silently becomes an A′ delivery.** The three cases map onto three different outcomes:
>
> - **(i) Opt-in invalid at capture** — no raw snapshot is retained; the delivery is A′ from the start (§7.3 scope rule (a)).
> - **(ii) Opt-in expires or is revoked after capture** — the delivery transitions to `BLOCKED` (`consent_expired` / `route_revoked`), the raw snapshot is dropped immediately, and no dispatch follows automatically in any form (§7.3 scope rule (b)).
> - **(iii) Opt-in valid but the raw snapshot is lost** — §7.3B governs (guarded best-effort fallback); if the fallback is not authorised, the delivery transitions to the held state `RAW_UNAVAILABLE`.
>
> - **(a) Capture-time consent.** At capture, the executor checks the route's P6 opt-in (valid, unexpired, unrevoked, epoch current) **before** retaining any raw snapshot. No valid opt-in ⇒ no raw snapshot is retained; the delivery is A′ from the start (§7.3 scope rule (a)).
> - **(b) The store.** Raw snapshots live in exactly one structure, `RawSnapshotStore`: a bounded in-memory map owned by the capture executor, in the application process, keyed by (`dedupe_key`, `route_id`, consent epoch). One dedicated lock guards the map; every operation — put at capture, take at claim, drop on revoke, evict on overflow/expiry — runs under that lock. Lock order is fixed: `Sender.LOCK` first, then the store lock; no path acquires them in the reverse order (the worker path never takes `Sender.LOCK`). The store is in-process only: if a future change moves the worker to a separate process (`:remote`), B is disabled until the handoff is redesigned — a cross-process snapshot would need disk, which B forbids. (File plan §B.)
> - **(c) Bounds.** Capacity 50 snapshots; TTL 2 hours wall-clock from capture (covers the first retry cycle; both numbers are Stage D measurement items, same pattern as §8.3(6′)). Eviction is LRU, oldest first. Each snapshot is at most ~1.5 KB (title + text, each truncated to 500 chars at capture, as in the baseline), so the map is bounded at ~75 KB — the bound exists to prevent leaks, not because of memory pressure. Overflow or TTL expiry ⇒ §7.3B applies (guarded best-effort fallback evaluation); if the fallback is not authorised, the delivery transitions to `RAW_UNAVAILABLE` — never spilled to disk.
> - **(d) Handoff — take, don't copy.** At claim, the claiming path **takes** the snapshot out of the map under the store lock — the snapshot moves into the attempt's private scope (a per-attempt holding slot), and the map no longer holds it, so no second claim can take it. The legacy flush takes the snapshot at its per-hop claim step; the Room worker takes it at its claim step; both paths use the same store. If the Room claim transaction fails after the take, the snapshot is returned to the map under the store lock (still within the live process). After the POST returns, whatever the outcome, the worker drops its reference. No component other than the claiming worker ever holds a reference.
> - **(e) Revocation race and the point of no return.** Revocation takes the store lock, drops the route's map snapshots, and transitions its PENDING deliveries to `BLOCKED` — atomic with respect to claims. A claim that already took the snapshot re-checks consent immediately before building/sending the body (the pre-send gate); if revoked, it drops the snapshot unsent and transitions `BLOCKED`. **The point of no return is the first write to the request-body output stream** (baseline: `OutputStreamWriter(conn.outputStream)`, `Sender.kt:192–194`). Everything before it — connection setup included — is still recallable by the pre-send gate. After it, the POST completes, the response stands (§7.5(c)), and the snapshot reference is dropped after the attempt. A revocation after that point cannot recall bytes already transmitted, and the consent disclosure says so (§7.3B).
> - **(f) Route isolation.** A raw snapshot is bound to exactly one `route_id` + consent epoch at capture. It is never fanned out to a second route, never copied to a second delivery, never attached to a retry for a different route. The claim transaction re-checks route + epoch before the POST body is built; a mismatch ⇒ the raw snapshot is discarded and the delivery goes `BLOCKED` (post-capture consent failure, §7.3 scope rule (b)) — never A′ by default.
> - **(g) Durable storage: none for raw.** The staging row, the event row, the delivery row, and every `delivery_attempts` row carry the redacted structured representation plus the marker `raw_ephemeral: true` and the consent epoch observed at capture. No durable row anywhere in the app contains raw class-(a) content for a B delivery. The marker records that the delivery was captured as B; it never authorises a substitution.
> - **(h) Migration.** Two different exposures, never conflated. **(1) Legacy preexisting plaintext.** The v2.3 queue file on disk contains raw title/text, including OTP spans, because v2.3 stored payloads verbatim (verified: one SharedPreferences file, `paylist`, holds routes, queue, and plaintext secrets — `Store.kt:60–61` — and `saveQueue` uses `apply()`). That exposure predates v1.1, cannot be undone retroactively, and persists until the queue is drained. **(2) Newly captured v1.1 data.** Never written to disk in raw form on any route — ephemeral-only per (b)–(g) above. **Cutover deletion.** A legacy queue entry is removed only via the §8.6 sweep protocol, after its disposition is recorded. A B-route legacy item's raw is held in memory only during the import window, for in-process dispatch; after import the queue entry is removed via `saveQueueSync` (`commit()` + read-back). Removal deletes the live entry; it does not erase `.bak` rotation residue or freed flash blocks — the §7.7 at-rest residue language applies here verbatim, and the design does not claim otherwise. **Rollback.** If cutover is aborted (intent `ABORTED`), unimported entries stay in the queue file and keep dispatching via the legacy sender; already-imported entries stay as Room deliveries, `HELD` until the next cutover attempt re-runs the import idempotently by `dedupe_key`. Invariant: at most one live copy per event — either the legacy queue entry or the Room delivery, never both, never zero without an audit record. No rollback deletes Room rows.
> - **(i) Backups.** The R23 claim "raw never enters a backup" is withdrawn as stated. Correct statement: backups taken by v1.1 builds exclude the queue file and the Room database files (`dataExtractionRules` + `fullBackupContent`, §7.8), so no raw captured or held by v1.1 enters a v1.1 backup; but backups taken by v2.3 builds — whose manifest sets no backup rules at all — may already contain the queue file with raw payloads, and the app cannot retract them; and until the legacy queue is fully drained, preexisting raw payloads remain on disk (excluded from backup, present on disk — the two are different claims). The design promises the v1.1 part only.
> - **(j) Eligible event classes.** Option B covers **mixed financial+OTP events only**: a payment event (amount parseable, type `payment`) that also carries a class-(a) span. A **pure-auth event** — no financial record (no parseable amount, not a payment) — is never B-eligible on any route: it is dropped at capture with a diagnostic counter only, per §7.1(a), even on a B route. B exists to preserve a financial record's fidelity; a pure OTP has no financial record to preserve, and forwarding it serves no billing purpose — it only exposes a secret. Baseline evidence: v2.3 capture already drops events with no parseable amount (`PaylistListenerService.processNotification` returns false; nothing is enqueued), so a pure-auth notification never reaches the queue today and B cannot forward what capture never enqueues.
>
> **Platform/policy gate — unchanged.** This data-flow does not prejudge the §7.3 verification gate: if Google Play policy or the notification-listener consent UX blocks forwarding authentication codes, B returns to the owner for a new decision. B is never silently narrowed, and no policy conclusion is asserted here.

### 7.3B Guarded best-effort fallback on raw loss (OWNER DECISION, 2026-11-15, comment id 6896048588)

> **(normative).** The owner explicitly chooses **best-effort with safeguards** rather than a strict-default manual hold for every lost raw snapshot. This section supersedes R24 §1.3's strict default. When the original notification is still available in memory and a valid per-route informed opt-in exists, the original is transmitted only under the §7.3/§7.3A B gate. When the raw snapshot is lost — process restart, in-memory map eviction, TTL expiry, or cross-process retry — an automatic A′ structured fallback is authorised **only if ALL of the following hold** (evaluated at claim time by `FallbackGate`, file plan §D, over the structured fields + reconciliation state; each criterion's outcome is recorded on the attempt row):
>
> 1. **Amount reliable.** The amount is reliably parsed and validated, with currency and sign where relevant. An amount-ambiguous event (§7.6, ≥2 differing currency tokens) fails this criterion until the operator picks an amount — see the precedence rule below.
> 2. **Direction reliable.** The transaction direction (incoming/outgoing) is reliably determined; direction is never inferred from ambiguous text. No direction cue ⇒ this criterion fails.
> 3. **Identity reliable.** The transaction identity is sufficiently reliable to deduplicate and reconcile, using the original stable `dedupe_key` and whatever verified identifiers are actually present; no account number, reference, or name is fabricated. A missing or unverified identifier that the endpoint requires ⇒ this criterion fails.
> 4. **Endpoint accepts the fallback.** The target endpoint accepts the fallback representation, with endpoint-specific semantics validated (not assumed). For `notify.php` the fallback is the structured fields under the same `dedupe_key` — the payment matcher reads `amount` only, so text cannot affect matching (verified, §7.6). For a recorder route (`catat.php`) the fallback representation is the §7.2 constructed text, which carries the direction cue — an empty-text fallback would lose direction, so it is not a valid fallback for a recorder route. For a recorder route, this criterion additionally requires **F43 B14 to pass against the actual recorder semantics** (the `catat.php` direction heuristic on the §7.2 constructed text, with the correct IN/OUT direction retained): **before B14 passes, automatic A′ fallback on a recorder route is NOT permitted — the delivery is held for review.** Passing B14 is a necessary condition for automatic fallback on a recorder route, not merely a planned test. Endpoint acceptance is a Stage C/D fixture obligation (F43), not a claim about current PHP behaviour.
> 5. **Prior outcome reconciled.** Before any retry/fallback, a prior uncertain POST outcome is reconciled using authoritative server evidence (§9 status query) and the existing UNKNOWN/HELD safety rules. A `found:true` answer resolves the delivery per §9; a `found:false` answer with all other criteria met authorises the fallback; an inconclusive answer (`in_flight:true`, 401/5xx/timeout, or no P12 coverage for the route) ⇒ this criterion fails and the delivery holds. No duplicate settlement and no duplicate recorder entry may follow from the fallback — the fallback re-POSTs under the original `dedupe_key`, and both endpoints dedupe by it (verified, §5.4).
> 6. **Consent and privacy re-checked.** Consent/revocation and privacy gates are checked again at fallback time: the opt-in must still be valid, unexpired, and unrevoked for the route, and the fallback sends structured fields only — never raw. A lost raw snapshot is not consent to send sensitive raw data, and raw is never transmitted after opt-in expiry or revocation.
>
> **Hold rule (normative).** If ANY criterion is ambiguous, unverified, incompatible, or reconciliation is inconclusive, the delivery holds in a distinct operator-review state — **never silently dispatched**. The fallback dispatch, when authorised, is flagged `raw_lost: true` on the attempt row and counted per route in diagnostics (`raw_lost_fallback_total`).
>
> **State taxonomy (normative).** Three held states answer three different questions; they are never conflated:
>
> - `RAW_UNAVAILABLE` — the payload-form question. A B delivery whose opt-in is still valid, whose amount is known, and whose raw snapshot is lost, with at least one §7.3B criterion unmet. The delivery is visible in diagnostics with the capture-time consent epoch and the flag `raw_lost: true`. The operator decision is explicit and recorded: **(a)** authorise an A′ dispatch for this delivery (structured fields only, re-stamped, flagged `raw_lost: true` on the attempt row) — permitted **only** for operator-correctable failures (amount, direction, or identity corrected after verified edits; consent with a new approval), **(b)** discard it — **local disposition only, never proof of non-settlement**: discard records that the operator chose not to pursue this delivery on this device; it asserts nothing about whether the server received or applied the transaction, and it never authorises a replay. The discard is a state transition with an audit record, per the quarantine-discard pattern; the financial-event audit record is retained together with the unresolved server-effect evidence (last known attempt state and reconciliation answers so far) for later reconciliation — or **(c)** leave it held — §9 reconciliation remains available in parallel and may still resolve it; a `found:false` answer leaves it `RAW_UNAVAILABLE` until the operator decides. **Hard stop (normative).** No manual override may authorise an A′ dispatch when the prior POST outcome is UNKNOWN/HELD without authoritative evidence — a re-POST could duplicate a settlement or recorder entry whose effect is unknown — or on endpoint incompatibility or B14 failure; for such cases the only operator options are (b) discard or (c) leave held.
> - `NEEDS_REVIEW` — the amount question (§7.6). The amount is ambiguous; the delivery is never `PENDING`, never claimed, never dispatched. **Precedence:** if an event is both amount-ambiguous and raw-lost, `NEEDS_REVIEW` takes precedence — the amount is picked first, and the pick re-runs the §7.3B evaluation with the chosen amount before any dispatch.
> - `BLOCKED` — the consent/config question (§7.5). The opt-in expired or was revoked, or the route config changed, after capture. No dispatch follows in any form without explicit operator re-approval.
>
> **Disclosure (normative).** The consent text states the best-effort branch in force: *"If the phone restarts or the app is closed before sending, the original text is lost; the payment is then sent using only the payment details (amount, account, reference), without the original text, only if the guarded fallback checks pass — otherwise it is held for your review."* The R24 strict-branch wording (*"the payment is then held for your decision and is never sent in a different form without your approval"*) is withdrawn as the default text; it describes a policy the owner did not choose. The disclosure also states the point of no return (§7.3A(e)): a revocation after the first write to the request-body output stream cannot recall bytes already transmitted. The fallback is conditional guarded best-effort: a raw-loss payment is sent in structured form only if all six §7.3B criteria pass; otherwise it is held (`RAW_UNAVAILABLE` / `NEEDS_REVIEW`) with operator notification and review per §7.9.
>
> **Operator alerting.** Every transition into `RAW_UNAVAILABLE` (and into `NEEDS_REVIEW`) alerts the operator promptly per §7.9 — high-priority notification with a 'Review transaction' action, plus a persistent in-app review queue/badge. The fallback itself (all six criteria met) dispatches without an operator alert; its `raw_lost: true` flag and the per-route `raw_lost_fallback_total` counter are the visibility mechanism.

Changing a recorder route's mode requires an explicit direction-contract test. (FINAL_DESIGN §7 `sanitized_text` opt-in for *new* destinations is unaffected.) Test T24.

### 7.5 Consent, revocation, config changes (C22)

> **(normative, C22(l)/(m)/(n)/(g), R10–R13).** Consent is persisted, not an in-memory flag: `route_consents(route_id PK, granted, epoch, disclosure_version, updated_at)`. Every revoke/re-grant bumps `epoch` in the same Room transaction that transitions the route's PENDING deliveries and staging rows to BLOCKED (revoke) or returns explicitly re-approved items to PENDING (re-grant — per item, operator action). Deliveries and staging rows store the per-route stamp map `route_id → {consent_epoch, config_epoch, url_sha256}` observed at capture/promotion. The claim transaction joins the delivery to `route_consents` and requires `granted = true AND delivery.consent_epoch = consent.epoch` for the route at `next_route_index`; a mismatch → BLOCKED (`consent_epoch_mismatch`), never dispatched, never auto-revived. Re-approval re-stamps the delivery's epoch to the current one. The claim re-evaluates the stamp for the route at `next_route_index` at *every* claim (Room worker) and every hop (legacy flush) — a route revoked after hop 1 returned `logged` is never entered at hop 2, even though hop 1 succeeded. The revocation sweep covers PENDING **and** RETRY_WAIT deliveries. IN_FLIGHT completes its POST, the response stands, then the gate re-runs before the next hop. Every POST attempt writes a `delivery_attempts` row with `route_id` + `consent_epoch` + `config_epoch` + `url_sha256` — the destination snapshot for that attempt, never the URL, never the secret.
>
> **Revocation (normative, C22).** (a) Revoking a route stops capture for that route immediately — the executor's mode/consent check rejects new snapshots for it. (b) PENDING deliveries for the revoked route transition to BLOCKED with reason `route_revoked` (visible in diagnostics; re-enabling returns them to PENDING by explicit operator action). (c) An IN_FLIGHT delivery in progress at revocation completes its attempt normally — aborting mid-POST would leave settlement state unknown; no further attempts after it. (d) Already-transmitted data cannot be recalled; the server keeps its copy. (e) Local deletion (per-record or per-category, in Settings) removes rows from this device only, never retracts transmitted data. (f) Opt-in is enforced per route in both capture and workers — a worker never claims a delivery for a route whose consent was revoked; the claim query joins the consent check in the same transaction. (g) The consent/revoke toggle handler runs the Room transaction (epoch bump + BLOCKED sweep) and awaits commit before updating the UI to show the route as revoked; if the transaction fails, the UI keeps the previous state and reports failure. The user is never told revocation took effect unless it is durable.
>
> **Route config changes (normative, C22(m)).** Route config splits into consent-relevant (destination URL) and non-consent-relevant (secret, keywords, packages, name). A URL change bumps the route's `config_epoch` and, in the same Room transaction, transitions its PENDING deliveries and staging rows to BLOCKED (`route_config_changed`); dispatch under the new URL requires explicit operator re-approval, which re-stamps the delivery's stored URL snapshot and `config_epoch`. Secret rotation does not change destination: allowed without re-consent, applied at claim time, recorded in diagnostics (never the value). Keyword/package changes are picked up at claim time. Disabling a route is consent-relevant: its PENDING deliveries and staging rows go BLOCKED (`route_disabled`); re-enabling requires explicit operator action to return them to PENDING. An IN_FLIGHT attempt always uses the config snapshot taken at claim. The claim transaction requires `delivery.config_epoch = route.config_epoch` for the URL, alongside the C22(l) consent check.
>
> **Legacy-path consent gate (normative, C22(p), R13).** Every legacy queue item enqueued in v1.1 carries a per-route stamp taken under `Sender.LOCK` at enqueue time: for each route in its route set, `{consent_epoch, config_epoch, url_sha256}` (SHA-256 of the URL, never the URL with credentials, never the secret). Before each POST — at the claim step for a chain hop, and before a single POST for a `single` item — the sender checks, for that route: `granted = true` AND stored `consent_epoch` = current epoch AND stored `config_epoch` = current epoch AND stored `url_sha256` = hash of the route's current URL. On mismatch the item is held (`BLOCKED`, reason `consent_epoch_mismatch` / `route_config_changed` / `route_revoked`), never POSTed, and — for a chain — the chain halts: it does **not** advance to the next route. Halting rather than skipping is deliberate: revocation is consent withdrawal, not a config tweak; advancing would let a lower-priority system claim a payment the revoked higher-priority route might own. Re-approval re-stamps the item for that route. **Pre-v1.1 items** (no stamp — enqueued before epochs existed) are held on first flush after upgrade until a one-time, per-route operator re-approval of the pending legacy queue, audited; treating an unstamped item as epoch 0 = auto-pass would launder items enqueued before revocation, and is rejected. **In-flight revocation:** a POST already in flight completes, its response stands; before the next hop the gate is re-evaluated for that route, and a revoked route is never re-entered in this chain. Receipts store `url_sha256`, route id, and epochs only; diagnostics log route name + URL host only, never the full URL, never the secret, never raw text.
>
> **Promotion-time consent (normative, C22(g)).** The executor enqueue step and the staging sweeper check route consent under the same lock hold as the mode read, atomically with the enqueue decision. On revocation, the coordinator — holding the same lock — transitions PENDING deliveries *and* staging rows for that route to BLOCKED, reason `route_revoked`, so no capture path can promote after revocation. Consent must also be checked at promotion, not only at capture and claim (R11 Blocker D): a staging row captured before revocation and promoted after must fail the epoch check at claim even if it slipped past the promotion check — the claim-time join is the backstop.

**Re-gating on manual release (normative, R20 (g′) as extended by D6).** A manual release is a new dispatch decision, not a continuation of the capture decision. Every manually released hop re-runs PrivacyGate and the per-route consent check **at release time**, against the consent epoch current at release — not the epoch at capture — **including the P6 opt-in check** for raw forwarding. The sweep intent records, per hop: the gate outcome, the consent epoch at release, and the operator identity. If consent was revoked after capture, or the payload contains OTP or financial content not approved for that route, the hop stays `HELD` and the release is refused by the release path itself — the gate is enforced in code on the release path, not by operator memory. "Operator reconciliation" is a decision recorded in the intent; it is never a bypass of PrivacyGate or of per-route consent. A manual release of a `RAW_UNAVAILABLE` delivery re-runs PrivacyGate, the per-route consent check including the P6 opt-in, **and** the §7.3B fallback criteria at release time; a release that would dispatch raw after opt-in expiry or revocation is refused, and a release that would dispatch A′ while any §7.3B criterion is unmet stays `RAW_UNAVAILABLE` until the operator explicitly authorises the A′ dispatch for that delivery (recorded with operator identity and timestamp) — subject to the §7.3B hard stop: no authorisation may re-POST when the prior POST outcome is UNKNOWN/HELD without authoritative evidence, or on endpoint incompatibility or B14 failure.

**Onboarding disclosure (proposed text, R10 as corrected — not final copy).** Paylist reads notifications to record payments; codes (OTP/PIN/password) are by default never stored/sent — removed before saving, only payment details kept; in the inseparable case only payment details are kept and the mixed text is discarded; payments are sent to [route URLs, per route]; **retention:** payment records are kept until the user deletes them, never deleted automatically; heartbeat/test records are deleted automatically 30 days after they finish (`terminal_at_ms`); records already sent stay on the server, the app cannot delete the server copy, and the server performs no automatic deletion; turning off a route / stopping Paylist in Settings: turning off stops new capture immediately, already-queued items are held (not sent, not deleted) until re-enabled or deleted, an in-flight item finishes that attempt, already-sent stays sent; deleting a record removes it from this device only; optional default-OFF "Forward unfiltered notification text, including any codes it contains, to [route]: OFF." Requirements: explicit opt-in per route (not a blanket checkbox); unfiltered forwarding default-off under its own opt-in (P6); the consent record is persisted (timestamp, disclosure-text version, per-route choices); revocation in Settings stops capture/forwarding for that route immediately; no capture before the onboarding opt-in completes; Settings offers local record deletion (per-record and per-category), local-only. The R9 draft was wrong twice (payment records are **not** "kept 30 days after delivery") and is withdrawn. The retention wording "payment records are kept until you delete them" is true only once the Settings deletion control exists and F16 passes; until then the onboarding wording is: *"Payment records are kept on this device. Deletion controls ship with this release; until then, records can only be removed by clearing the app's data."*

### 7.6 NEEDS_REVIEW — two-amount notifications (C22(o) series)

> **(normative, R13–R15).** Detection: capture counts all currency tokens (Rp and IDR) in the combined text, normalises each to rupiah, and compares values. If ≥2 tokens carry different values, the event is `amount_ambiguous`: the event row is written durably (token list with positions, package, time, `content_sha256`, `dedupe_key` from the first token for traceability only), and the delivery is created in state `NEEDS_REVIEW` — never `PENDING`, never claimed, never enqueued to the legacy sender, never fanned out to staging promotion — no automatic settlement occurs. Tokens agreeing on one value are not ambiguous. The on-device review surface lists the event (package, time, token list, `dedupe_key`, content hash — never raw text); the operator picks the correct amount or discards it. On pick, a delivery is created with the chosen amount and a recomputed `dedupe_key`; the `NEEDS_REVIEW` row is marked superseded with an audit record, never dispatched under the wrong key. On discard, the event is marked discarded with an audit record, counted. No per-route auto-rule ("balance always first") is permitted in v1.1 — a positional rule would need its own P3-style evidence per source package. Single-token events are unchanged; the rescan path applies the same rule. Enforcement is client-side. **Precedence (normative):** if an event is both amount-ambiguous and raw-lost, `NEEDS_REVIEW` takes precedence — the amount is picked first, and the pick re-runs the §7.3B fallback evaluation with the chosen amount before any dispatch.
>
> **Pick/discard (normative).** (a) Pick-time re-validation: the event row is immutable — token list, package, time, `content_sha256`, original `dedupe_key` never change. At pick time the route set and consent/config epochs are re-read — not the capture-time values. A review can sit for hours; a route revoked or URL-changed during review blocks the pick until the route is re-approved. The pick audit records: original `dedupe_key`, chosen amount, new `dedupe_key`, route set, consent epochs at pick time, operator, timestamp. (b) Prior-copy guard: before creating the picked delivery, the pick re-reads the route set + epochs (a revoked route blocks the pick); an undispatched legacy copy is superseded, a dispatched prior copy blocks with `prior_copy_dispatched`. Key analysis: if the chosen amount equals the first-token amount, the recomputed key equals the original key and server dedupe makes a second POST harmless; if it differs, the key differs and the guard is the only thing preventing a second settlement — the server cannot know two keys are the same event. (c) Discard keeps the record: discard is a state transition `NEEDS_REVIEW → DISCARDED` with an audit record; the event row, token list, content hash, and audit are retained. Discard never deletes. `NEEDS_REVIEW` and `DISCARDED` payment events are payment events for C11 retention: excluded from 30-day auto-cleanup, deleted only by explicit operator policy. Discarding does not cancel a prior legacy copy — the operator is warned at discard time if one exists, and the discard audit records whether a legacy copy existed at discard time (`qkey` + dispatch state when known). (d) Disclosure: the review surface states: "Review holds forwarding — this payment is not sent until you pick an amount or discard it." It shows the event age and warns that the bill may already have been settled through another channel while waiting — check the server log before confirming.
>
> **Ordered idempotent pick protocol (normative, R15 C22(o′′)).** "In the same transaction" across Room + SharedPreferences cannot hold — no transaction spans both stores. The protocol is ordered and idempotent: (a) Room transaction — pick and hold: in one Room transaction, supersede/cancel any non-terminal Room delivery with the same `event_id` or original `dedupe_key`; create the picked delivery in state `HELD_AWAITING_LEGACY_SWEEP` (not claimable by the worker); write the pick audit row. The delivery is durable but cannot be dispatched yet. (b) Legacy sweep — under `Sender.LOCK`: scan the legacy queue for the same `dedupe_key`: an undispatched copy is removed via `saveQueueSync`; a copy already dispatched (receipt `RESOLVED/dispatched`, or the item gone with a dispatched receipt) is not touched. Record the sweep outcome. (c) Room transaction — release or block: if the sweep removed the copy or found none, the delivery transitions `HELD_AWAITING_LEGACY_SWEEP → PENDING` (claimable) with the sweep record (`legacy_sweep: removed|absent`, timestamp). If the sweep found a dispatched prior copy, the delivery stays `HELD`, the pick is `BLOCKED` with `prior_copy_dispatched`, and the operator must reconcile against the server log before a new delivery is created. If the sweep found a copy whose dispatch state is unknown (item gone, receipt `IN_FLIGHT`, or receipt missing), the pick is held with `prior_copy_unknown` until the copy's dispatch state is reconciled. Crash recovery: each step is idempotent, commit points explicit. Crash between (a) and (b): the delivery sits `HELD_AWAITING_LEGACY_SWEEP` with no sweep record; on coordinator recovery it is re-swept — the sweep is idempotent. Crash between (b) and (c): the queue removal is durable but the release is not; recovery re-reads the sweep record — `removed`/`absent` advances the delivery to `PENDING`, no record re-runs the sweep. Crash during (b): `saveQueueSync` either committed (with read-back) or not; recovery re-runs the sweep with the same outcome. No window can create two live copies: the Room delivery is unclaimable until the sweep releases it, and the legacy copy is removed before release.

**First-token rule (normative, R13 §3, strengthened).** `parseAmount` returns the *first currency token* in the combined text (title + text + bigText), Rp or IDR, whichever starts first. "Saldo Rp500.000. Pembayaran Rp100.000 berhasil" parses to 500000 — a mis-pick also poisons `dedupe_key`, which embeds the parsed amount. The server match guard (verified): `notify.php` matches only on first insert, over `UNPAID` rows with `kode_unik NOT NULL`, matching only exact equality `expected === amount` where `expected = ceil(tagihan) + ceil(tagihan × 0.7%) + kode_unik`. A mis-picked balance settles a wrong bill only if some open bill's coded total is exactly that balance — narrow, but real; if it happens, the true payment can never settle under the correct amount (its `dedupe_key` is bound to the wrong one, and re-delivery reproduces the same wrong parse). If it matches no bill, the response is `logged`, the chain advances to the next route, which may match a wrong bill there instead. The matcher cannot detect wrongness. `catat.php` has no guard at all: every payment POST is recorded with the parsed amount and heuristic direction, and the `amount_ambiguous` flag is ignored — the server reads only known keys. **A flag ignored by PHP is not a guard.** The R12 claim "server match is guard" is withdrawn for both endpoints. Enforcement is client-side; it does not depend on server behaviour.

### 7.7 Pre-v1.1 queue privacy: reprocessing, quarantine, at-rest residue (P9)

> **R29 execution barrier (normative).** The per-item P9 classifier/redactor/quarantine operation is a **prerequisite to any post-upgrade legacy POST and to every Room import**, not merely a Stage D enhancement. Implement its minimal, production-enforced path before activating Stage C sender/cutover. Until the P9 gate and F50 pass, the new build must not enable cutover or release an uninspected pre-v1.1 item. Inspect each item separately; persist a clean-item inspection marker without changing the original payload bytes; redact confirmed sensitive spans in the item while preserving `dedupe_key`, amount, direction, route order, `next`, `hop_outcomes` and server-effect evidence; quarantine uncertain items with no POST/import/export. A quarantined item remains in the legacy holding pen, is **excluded from the importable set**, and cannot be cleared by a blanket queue delete. The cutover verifier must account separately for `importable`, `quarantined`, and `resolved/discarded` items, rather than requiring a raw total-count equality that would force quarantined items into Room. Clearing legacy queue after `WORKER_ONLY` is permitted **only for individually verified imported/resolved entries**; retain quarantined entries and their audit until operator disposition. No transition may silently strand or transmit a quarantined item. This is a change to the §8.2 count/checksum protocol, not permission to skip its verification.

> **(normative, R14 C22(q) / R15 C22(q′) / R16 C22(q′′)).** Holding does not sanitise. Holding an unstamped pre-v1.1 item until one-time per-route operator re-approval gates *whether* it is POSTed, not *what* is POSTed: the held item still carries unredacted title/text, and re-approval would POST it verbatim. Before the first post-upgrade POST of any pre-v1.1 queue item, and before its import at cutover, the sender runs the stored payload title + text through the PrivacyGate class-(a) span scan. On confirmed secret spans it writes the REDACTED payload back to the queue item via `saveQueueSync` (durable replacement, `commit()` + read-back), marks `privacy_reprocessed: true` with the redacted-span count (never content) and `privacy_reprocessed_at_ms`; only then may the item be POSTed or imported. After replacement the original raw title/text no longer exists on disk in the queue file. `amount`, `dedupe_key`, package, `notif_time`, and route set are unchanged; `dedupe_key` is never recomputed. If the scan is uncertain (fail-closed), the item is quarantined: marked `privacy_quarantine: true` with a reason, never POSTed, never imported, never exported; the review surface shows only a PrivacyGate-redacted preview plus span classes, never raw spans; the operator approves the redacted form (triggers durable replacement, clears quarantine) or discards it (a state transition with an audit record; the payload is deleted). Scope: a pre-v1.1 payload stores title (≤500 chars) and text (≤500 chars, `bigText` folded in only when text is empty) — `bigText` beyond that was never stored, so reprocessing scans exactly what will be POSTed. Recorder routes (`catat.php`) follow the same rule: direction keywords are not secret spans, so the server direction heuristic still classifies after redaction.
>
> **At-rest residue (stated plainly, not claimed away).** A quarantined item's raw text remains in the legacy queue file under the quarantine marker until the operator approves or discards it. The residue never leaves the device, is never POSTed, never imported into Room, never included in a diagnostic export, and never included in the reconciliation export (§7.7A) — but it is still on disk; this document does not claim otherwise. The guarantee is about sinks (POST / Room / export), not about the holding pen; the quarantine review surface is the mechanism that clears the pen. `SharedPreferences.commit()` rotates the file through `.bak` (old file renamed to `.bak`, new file written, `.bak` deleted): old bytes survive transiently in `.bak` and in freed flash blocks after deletion; deletion is not secure erasure. `saveQueue` uses `apply()` (async); `saveQueueSync` (`commit()`) goes through the same rotation. Redaction removes secrets from live sinks and prevents new exposure; it cannot retroactively erase bytes already written to flash or already backed up.
>
> **Diagnostic-export rules (superseded for v1.1; future-phase design only).** No diagnostic payload export or recovery export exists in v1.1 (P10 option C, §7.8, F35). These rules govern a future diagnostic export only. The v1.1 reconciliation export (§7.7A) is a separate capability with its own eligibility rules; it never includes payload content, and a recovery path must never masquerade as a reconciliation export. The following constraints apply only if a separately approved future export feature is designed: export may include payload content only for items with `privacy_reprocessed: true` or v1.1 staged items (already gated at capture); quarantined and unprocessed pre-v1.1 items may appear as metadata-only rows (reason, span count and timestamps; never `qkey`) — never content. `logLocal` never logs raw title/text spans. A future diagnostic export function would enforce this by construction (reading the `privacy_reprocessed` marker), not by call-site discipline — no such function exists in v1.1, so this sentence states a future requirement, not a current capability. A diagnostic export or log **never** contains `qkey` or `dedupe_key`, raw or hashed: Java `String.hashCode()` is 32-bit over a low-entropy input (known package, postTime in a narrow window, known amount, templated text) and is brute-forceable, so the hash is an oracle for the raw text; a SHA-256 of a low-entropy value is still an oracle. Exports carry only an opaque Room correlation id (`delivery_id`, UUID) plus metadata, and the operator resolves a `dedupe_key` only through the authenticated status query, never from an export. The export rule extends to `content_sha256`: it is a hash oracle, so it is never exported, never printed, never logged, and is deleted from the staging row after the sweep recovery comparison, or at import, whichever comes first. Exports carry only the post-redaction `payload_sha256` + metadata. The wire contract is unaffected: the POST body and the status query carry the real `dedupe_key` over the authenticated channel, as today.
>
> **Quarantine discard audit (normative).** Discarding a quarantined item deletes the raw payload (durable removal via `saveQueueSync`) but MUST retain a financial-event audit record (amount, `dedupe_key`, package, timestamps, span classes, decision, operator, reason) in Room. Discard is a state transition on an audit record, never a deletion of the event; the audit record never contains raw spans.

> **Owner approval — narrowed per-item form (owner decision 2026-11-15, comment id 6903307191).** The owner APPROVED the narrowed per-item strategy above (MUSE-R27 §4.2, now this section): no bulk action of any kind; clean items pass through byte-identical; confirmed secret spans are replaced span-level with a per-item audit; uncertain spans are quarantined for operator review; no silent bulk deletion/sanitisation/transmission. Three integration constraints apply and are normative here: (1) clean-item byte-identical passthrough remains subject to the existing per-route consent/privacy gates and to the uncertain-POST reconciliation gates (§9) — a clean item is not auto-released past a held hop; (2) span-level redaction must not corrupt the original `dedupe_key`, the stable amount/direction, the legacy chain cursor (`next`, `hop_outcomes`), or the server-effect audit — the audit records span classes + count, never content; (3) quarantine is non-destructive: a quarantined item is never POSTed, imported, or exported, and no automatic send/export of uncertain raw text exists. The disclosed residual at-rest risk and the explicit consent/revocation checks stand unchanged. Fixture F50 (§10.2) pins this form.


### 7.7A Transaction Reconciliation Export (v1.1 REQUIRED, owner decision 2026-11-16, comment id 6905797710; policy locked 2026-11-16, comment id 6905986632)

**Purpose and scope (normative, R31 as revised by R32/R33).** The user-initiated export of structured financial transaction records for manual reconciliation with bank statements, orders, invoices, and billing systems. CSV is mandatory for v1.1; XLSX and more advanced reports are deferred beyond v1.1. This export is **not** a diagnostic export, **not** a recovery export, and **not** the P10 option A export/restore: it cannot restore state, it cannot re-import, and it never carries payload content. The diagnostic/recovery export prohibition (§7.7, F55) stands unchanged alongside it; a recovery path must never masquerade as a reconciliation export. Format: RFC 4180 CSV (CRLF record separators, per RFC 4180 §2.1 — the R32 "LF line endings" wording was wrong; RFC 4180's record separator is CRLF), UTF-8 with BOM, one header row, rows in ascending `timestamp` order (then `row_id` for a deterministic tie-break). Suggested file name: `paylist-reconciliation-YYYYMMDD-HHMMSS.csv`.

**Row grain (normative, R32, MAJOR-3; revised R33, BLOCKER A).** One row per (event, route) pair with a recorded hop outcome, plus exactly one event-level row for an event with no recorded hop outcome (see zero-hop events below). The export reads the delivery's `hop_outcomes[]`: a route the event never reached produces no row, and a route reached produces exactly one row carrying that route's server outcome. A captured event therefore appears once per route it reached — never count a captured event twice: group rows by `event_ref` (§7.7A row identity) and count each distinct `event_ref` once as a captured event, not as a proven distinct bank transaction (see row identity). `route_label` and `route_kind` identify the route on every row; recorder and payment routes are never conflated (their outcome semantics differ — see `server_outcome`).

**Zero-hop events (normative, R33, BLOCKER A; consent rule revised R34).** An eligible event whose delivery records no hop outcome — never dispatched, held before its first hop, or pending with no attempted hop — is represented by exactly one event-level row: `route_kind` = `NONE`, `route_label` empty, `route_id` sentinel `none`, `row_id` = SHA-256 hex of `event_ref + "|none"`, `server_outcome` = `NOT_DISPATCHED`, `resolution_label` = `UNRESOLVED_NEEDS_REVIEW` where the hold reason is known and reviewable, otherwise `UNRESOLVED_UNKNOWN`. The zero-hop row exists only when `hop_outcomes[]` is empty: a partial chain (some hops attempted, later hops not reached) is represented by the rows of its reached hops only, never also by a zero-hop row (see partial chains below). **Multi-route consent (R34):** the zero-hop row carries capture-level fields only — no route-attributable data — and is exportable if and only if at least one of the event's target routes has current consent at export time, checked against the authorization snapshot's per-route epochs. If no target route has current consent (all revoked, or no consenting target), the event is excluded entirely: no zero-hop row. Data attributable only to a revoked route is never exported; per-route rows are gated by their own route's consent, and the zero-hop row carries no route-specific field. The audit records the per-route epochs (`export_audit.epochs_json`), so the authorization behind the row is auditable. A zero-hop row never implies dispatch, settlement, or recorder capture.

**Partial chains and downstream visibility (normative, R34).** The CSV is a reached-hop report: for a partial chain, only the reached hops are exported; later scheduled, held, or unreached hops are NOT represented — no row and no summary. A summary row would break the event×route grain and a summary column would break the stable 20-column schema, so both are rejected. Every export containing a partial chain shows an actionable UI warning: "This export shows only routes the event reached. Later routes in the chain may still be pending — check the delivery screen for the full chain status." The delivery screen, not the CSV, is the authoritative place for chain status.

**Stable row identity (normative, R32, owner decision 3).** Two opaque identifiers, both stable across repeated exports:
- `event_ref`: a random UUID v4 stored once per event in `events.export_ref` (§4.1), generated at event creation (live capture, rescan, or import) and never changed. It identifies one canonical captured event across all its rows. It does NOT by itself identify a unique bank transaction: under §3.1.4 case B, two distinct captured events (two `event_ref`s) can be verified evidence of the same bank transaction. `event_ref` grouping counts captured events only (route-level dedup) — never bank transactions. Distinct-bank-transaction counting from the CSV is expressly disallowed in v1.1 (see bank-transaction counting below); `bank_reference` is a manual reconciliation aid, never a grouping key.
- `row_id`: the lowercase hex SHA-256 digest (64 characters) of `event_ref + "|" + route_id`. It identifies one (event, route) row. It is deterministic (same inputs, same ID, every export), opaque (SHA-256 preimage resistance + 122 bits of entropy in `event_ref` make the inputs unrecoverable), and non-reversible. It exposes no internal `event_id`, `dedupe_key`, legacy `qkey`, content hash, secret, or raw content.
Privacy leakage limits: `row_id` and `event_ref` allow correlation across exports — that is their purpose — but reveal nothing about the event's content; the same IDs cannot occur for a different event (the `event_ref` is random per event per device). Collision handling: the exporter verifies `row_id` uniqueness within the export before writing; a SHA-256 collision is treated as an internal error (export FAILED, audit recorded) — it cannot occur in practice. Migration: legacy imported events get a fresh `event_ref` at import, preserved on idempotent re-import (the existing event row is kept). Row IDs are stable per device/database: a P10 option C device loss (database excluded from backup) means new IDs for any re-captured events — stated plainly, not hidden.

**Bank-transaction counting (normative, R34).** The v1.1 CSV does NOT support automated distinct-bank-transaction totals, and no consumer may compute them from the CSV alone. `bank_reference` is a manual reconciliation aid for matching rows against bank statements — never a grouping key: grouping by `bank_reference` string alone is prohibited, because two banks may issue the same reference, one payment may be notified to two source accounts, and merchant context may be missing. The CSV carries no bank-transaction grouping key and no issuing-bank scope column, and no such key may be fabricated from notification text. Distinct-bank-transaction counting happens only in verified external reconciliation (the operator's bank statement or billing system), where the issuing bank and account are known. This disallowance replaces the R33 counting rule (grouping by verified `bank_reference` + source/merchant scope), which is struck: §3.1.4 case B remains valid as advisory internal matcher reasoning, but it does not yield an exportable grouping key.

**Exact CSV column schema (normative, R32).** Columns appear in this order; no other column is permitted. Empty means absent or unconfirmed — never invent a value, never write a placeholder such as `null` or `N/A`.

**Amount decimal format (normative, R32, owner decision 4).** The `amount` column carries a currency-appropriate decimal string: no thousands separators, `.` decimal point only when the currency scale requires it, scale from a built-in ISO 4217 table (IDR scale 0 → `100800`; USD scale 2 → `1008.00` for 100800 minor units; JPY scale 0). The internal model stays integer minor units; the export converts with integer arithmetic and the round-trip (decimal string → minor units) uses integer arithmetic too — binary floating-point is never used. Unknown currencies use scale 0 (documented default). The currency-scale table's coverage beyond the common currencies is a Stage D implementation detail.

**Never in the export (normative).** No raw notification title/body or raw payload reconstruction; no OTP/PIN/auth tokens; no `qkey`, `dedupe_key`, `content_sha256`, or internal `event_id` (`row_id` and `event_ref` are the only identifiers, and both are opaque by construction); no unverified quarantine content; no secrets; no log/diagnostic content.

**Spreadsheet formula-injection safety (normative, R32, MAJOR-1).** RFC 4180 quoting alone does not prevent formula execution when a spreadsheet opens the file. Untrusted text fields — `bank_reference`, `order_number`, `sender_id`, `recipient_id`, `category`, `source_application`, `source_account`, `route_label` — that start with `=`, `+`, `-`, or `@`, or with leading whitespace/control characters preceding such a prefix, are serialised with a single-quote (`'`) prefix. The effect is reversible and documented: a machine consumer strips exactly one leading `'` when the remainder (after trimming leading whitespace/control characters) starts with a trigger character; the exact original structured data is preserved internally in Room and the strip rule restores it. The original field value (including any leading whitespace) is otherwise exported unchanged — the guard adds a prefix, it never trims, alters, or drops data. System-generated fields (timestamps, amounts, enums, IDs) cannot start with a trigger character and are never prefixed. Embedded quotes, commas, and CR/LF are handled by RFC 4180 quoting. **Residual risk (R33, MODERATE G).** The `'` prefix is a mitigation, not a guarantee across every spreadsheet import path: pasted values, some CSV-import wizards, and locale-dependent formula evaluation may still interpret cell content as a formula. A machine consumer MUST parse the file with a real CSV parser and MUST NOT evaluate cell content as formulas; the residual risk is documented in `docs/operations.md`. This document claims no absolute injection guarantee for the prefix alone.

**Privacy eligibility (normative).** A record is exportable only if all of these hold: (a) every included field passed the PrivacyGate class-(a) span scan with no unresolved sensitive span — a field with an unresolved sensitive span is omitted and named in `excluded_fields`, never exported; (b) consent is current at export time — per-route rows require their own route's consent (records from a revoked route are excluded); the zero-hop event-level row requires at least one consenting target route (see zero-hop events above). Consent revocation cannot recall a file the user already exported; that is a stated limitation, not a silent gap; (c) the record is not quarantined — quarantined items live in the legacy queue, outside Room, and are excluded by construction plus an explicit check; (d) the record is a financial transaction — heartbeat/test events are excluded. The export is gated on route consent, not on the P6 raw opt-in, because no raw content is ever exported. Recorder-route records (myBCA) are included: they are bank-statement records the user reconciles; their `server_outcome` uses the recorder values above.

**Filters (normative).** The user filters by date range, source account, direction, and advisory matching/reconciliation status. The source-account filter matches the internal verified account key (`events.source_account_key`, §4.1), never the masked display value (blank key = unattributed); it never treats two accounts sharing one application as one account. After a Keystore key loss, all stored keys are NULL until new captures re-derive them (§4.1, R35); historical rows stay unattributed — the design never re-derives a key without a fresh verified identity. Two verified accounts whose masked display values collide (same last four characters) appear as separate filter entries distinguished by their P3 source-pattern label; where no distinguishing label exists, they are presented as one explicitly-ambiguous bucket that includes both accounts, never silently one of them — the ambiguity is visible in the confirmation dialog. The source-application filter (where offered) matches `source_application` separately. The filter is applied to the Room read, not by post-filtering an unfiltered dump; the confirmation dialog shows the filter and the resulting row count before anything is written.

**Permissions and access control (normative).** Export is a deliberate foreground user action only: an explicit tap, then a confirmation dialog showing the filter summary, the row count, the excluded-row count, and the identifiers choice. No background, automatic, or scheduled export; no export via share intent, deep link, or another app. The file is written via the system file picker (Storage Access Framework) to a user-chosen location; the app never picks a destination silently. Sender/recipient identifiers require an explicit opt-in checkbox in the confirmation dialog, **default OFF** — and the choice is never persisted across exports: every export starts with the toggle OFF and requires a fresh opt-in. v1.1 has no in-app user accounts; the actor is the device user (`export_audit.actor` = operator) and the foreground confirmation is the authorization record. **Device authentication gate (R32, MODERATE-2):** an export that includes sender/recipient identifiers additionally requires device authentication (BiometricPrompt with device-credential fallback) immediately before writing. If the device has no secure lock configured (no PIN/pattern/password/biometric enrolled), identifier export is DISABLED (fail-closed) with an in-app explanation. Documented threat model: the device lock is the primary boundary and an unlocked device in the user's hands is trusted; the auth gate exists because identifiers are the most sensitive exported data, and the fail-closed rule exists because without a lock there is no gate to enforce.

**Authorization snapshot and revalidation (normative, R33, MAJOR E).** The confirmation dialog, SAF picker, device authentication, and the (potentially long) streaming write can outlive a consent or configuration change, so the export does not rely on the preflight check alone. After device authentication succeeds and immediately before the first byte is written, the exporter captures an authorization snapshot: the per-route `consent_epoch` + `config_epoch` for every included route, the identifiers opt-in, the filter, and the frozen eligible row set (row count + the ordered `row_id` list). The snapshot is revalidated immediately before the first row write AND before every row write: the authorization check is per row (an epoch comparison against current state), while the flush remains periodic for I/O. If any included route's consent or config epoch has changed, or the identifiers opt-in no longer holds, the write aborts at the next row — no further row is written — the audit records FAILED with the truthful rows-written count and a `notes` entry naming the epoch change, the app attempts best-effort deletion of the partial file, and the UI warns as in the write protocol. Residual exposure is disclosed explicitly: rows written before the abort remain in the file, cleanup is best-effort, and the exporter never claims an already-written file is retractable — a mid-export revocation limits exposure to the rows written before the abort, it does not recall them. **Precise guarantee (R35):** no row is STARTED after a revocation is observed — the per-row check gates each row's write start. The check and the SAF `OutputStream` write are not atomic: a revocation that lands between the check and the write of one row cannot prevent that row from completing (the row already in the write window may complete), and previously written bytes may remain despite best-effort cleanup. The design claims no instant revocation and no retraction. Rows that arrive or change after the snapshot are never added mid-export; they appear in the next export. The audit row records the snapshot epochs (`export_audit.epochs_json`, §4.7), so the exported fields always correspond to the authorization that actually governed the write. Consent revocation cannot recall a file already exported; that limitation stands as stated.

**Storage, deletion, audit (normative).** The app writes directly to the SAF URI and keeps no copy of the exported file: no cache, no retained temp file (no temp file is used at all; the SAF `OutputStream` is the only destination). The app never re-reads the exported file; deletion of the user's copy is the user's action. **Write protocol (R32, MODERATE-1):** the exporter writes the header and rows incrementally with periodic flush; COMPLETED is recorded only after a final flush + close with the final row count. If writing fails (IO error) or the user cancels after writing began, the audit records FAILED or CANCELLED with the truthful rows-written count, the app attempts best-effort deletion of the partial SAF file (the attempt and its outcome are recorded in the audit `notes`), and the UI warns the user that a partial file may exist at the chosen location and should be deleted manually if cleanup failed. A cancellation before any write records CANCELLED with row count 0. Every export writes one audit row to `export_audit` (§4.7): actor, timestamp, the applied filter (including the identifiers choice), row count, excluded-row count, file name, status, authorization method, and notes. The audit row never contains exported content.

**Zero side effects (normative).** Export is read-only: no POST, no retry, no server apply, no order status update, no settlement, no delivery state change, no queue mutation. The export reads Room only (`events`, `deliveries`, `match_results`, `classification_results`). The only write the export performs is its own `export_audit` row.

### 7.8 Secrets, network, backup (P10, owner-decided)

- **Keystore-backed AES-GCM envelope** for route secrets; ciphertext and IV stored in app-private preferences. Handle invalidated/unavailable keys as BLOCKED requiring re-entry; never fall back to plaintext. Exclude secrets from backup/restore or design recovery explicitly (see below). Mask secret input and avoid echoing the secret in diagnostics.
- **New endpoint URLs HTTPS-only**; validate scheme, host, credentials, and redirect policy. Existing HTTP routes are flagged and require explicit operator action, not silent conversion. TLS verification enabled; no trust-all certificates. Do not log raw sensitive payloads.
- **SQLCipher not included.** The Room database remains in the app sandbox; document the local-device threat model and retention. Default ACKED retention 30 days (heartbeat/test only, §4.2), subject to available storage and user settings; blocked/pending events must not be silently purged.

> **(normative, D7 — P10 option C, owner-decided 2026-11-15).** The owner decided option C: exclude the transaction database and pending queue from Android backup/device transfer; clearly warn that unsent/unreconciled transactions can be permanently lost on device replacement, reset, or loss; route metadata restoration and missing-secret handling remain as specified, subject to the final backup-rules audit; no recovery-export feature is authorised for v1.1. This bars a recovery export (restoring transactions to a new device); it does not bar the reconciliation export (§7.7A), which is read-only reporting and cannot restore state. This is an explicit, conspicuous owner choice — not a silently applied default against the preserve-financial-record objective. The loss warning must be **conspicuous** — shown in-app where backup/restore is configured and at first run after a restore, and stated in plain words in `docs/operations.md` — naming exactly what is lost (unreconciled queue copies and Room deliveries; the operator's only recourse is the server logs of the routes they reached, if they reached any). The device-loss limitation is disclosed in plain words in `docs/operations.md` and in the decision text itself: "a device replaced or factory-reset before its pending payments are reconciled loses those pending records from the device; they survive only in the server logs of the routes they reached, if they reached any". Plan A remains a post-pilot design item with its eight gates (authenticated, versioned, encrypted backup; integrity validation; access controls; duplicate-safe import; explicit residual-risk disclosure; plus an eighth — the archive's handling rules are written before it is built); option B remains unavailable until P12; the diagnostic-export prohibition stands unchanged in v1.1 with no exception; F35 asserts statically that no diagnostic/recovery export function exists in the v1.1 tree — the only export function is the gated reconciliation export (§7.7A).

> **(normative, R17/R18 C22(q′′′) backup rules).** Two API bands, both named. `dataExtractionRules` governs API 31+ only. With `minSdk 28`, the design must also ship `fullBackupContent` for API 28–30 — `dataExtractionRules` alone leaves those devices on the default (included). The exclusion of `shared_prefs/paylist.xml` is written in **both** files, and in `dataExtractionRules` in **both** sections (`<cloud-backup>` and `<device-transfer>`), unless the owner decides otherwise per section (P10). The device-to-device behaviour on API 28–30 is a verification item in F35 (confirm against the platform documentation and a device test), not an assumption. The recommended default is option (iii) — split the preferences file: routes in one file, queue in another, so the routes file can restore on a new device while the queue file is excluded. Option (iii) is the only one that preserves route restore without restoring the queue; it is a small code change (two `SharedPreferences` names).
>
> **(normative, R18 restore semantics).** Secrets are never restored, in any form. Whether the owner picks (i) `dataExtractionRules` exclusion, (ii) `android:allowBackup="false"`, or (iii) the prefs split, the rule is identical: a restore carries route **metadata only** — route id, display name, endpoint URL, enabled flag, mode — and no secret, neither plaintext nor Keystore ciphertext. The v1.1 vault (Stage C, `SecretVault`) moves secrets out of the routes file into Keystore-backed storage — the one-time migration of stored plaintext secrets into the vault runs in Stage C (`SecretMigration.kt`); the backup rules then exclude the Keystore material by construction, because Keystore keys do not survive backup/restore to a new device or after uninstall (a premise to confirm in F35). On first boot after a restore, a route whose `SecretVault` lookup misses is durably marked `DISABLED_MISSING_SECRET`: it never claims a hop, never POSTs with an empty or missing secret, and is never silently re-enabled. The operator re-enters the secret per route, which clears the flag. A route restored with its secret present (same device, key intact — the in-place upgrade case, not a restore) is unaffected. The Room database is excluded too: the backup exclusion covers `shared_prefs/paylist.xml` (or the split queue/routes files) **and** the Room database files (`databases/*.db`, `-wal`, `-shm`): the Room rows carry `dedupe_key`/`qkey`, which are sensitive derived material, and a restored database without restored routes/secrets would be an inconsistent state (deliveries referencing routes that do not exist). A restored device therefore starts with an empty delivery store and metadata-only routes — a fresh-install state, not a resumed one. Staged-held deliveries from before the restore are not recovered from backup; that loss is stated here, not discovered later.

**Supersession note.** R19's P10 options (A) export/restore, (B) server reconciliation after restore, (C) explicit acceptance — the owner decided (C) on 2026-11-15; (A) is a post-pilot design item, (B) is unavailable until P12. R20's "P10 option C as the v1.1 default, recommended" is superseded: option C is now owner-decided, not a recommendation. The baseline manifest sets no backup rules at all (verified: no `android:allowBackup` / `fullBackupContent` attribute), so the v1.1 exclusion is new behaviour the owner consciously adopts, not a restatement of what the app already does.

### 7.9 Operator-review alerting for held deliveries (normative, OWNER DECISION 2026-11-15)

> **(normative).** Every transition into a held operator-review state — `RAW_UNAVAILABLE` (§7.3B) or `NEEDS_REVIEW` (§7.6) — alerts the operator promptly. The alerting rules are:
>
> - **(a) Notification.** An Android high-priority notification is posted at the transition, with a 'Review transaction' action that deep-links to the appropriate in-app review screen for that delivery (the `RAW_UNAVAILABLE` queue or the `NEEDS_REVIEW` surface). The notification uses a dedicated channel created at first run (importance HIGH, user-controllable); it carries no sound or vibration beyond the channel default.
> - **(b) Summary only.** The notification and the queue/badge show only a non-sensitive summary: the amount **if reliable**, the source (route/package), the time, and the reason for the hold. No OTP, PIN, auth token, account number, or raw text ever appears in a notification, a badge, or a queue row.
> - **(c) No forced launch.** The app never force-launches an Activity from the background. Full-screen intents are inappropriate for a review prompt — they interrupt the user and are reserved for time-sensitive alarms and incoming calls — and are not used here. The notification action opens the review screen only when the user taps it; if the app is already in the foreground, the hold is surfaced in-app (banner/dialog on the review queue) instead of posting a notification.
> - **(d) Permission and fallback.** Posting requires the `POST_NOTIFICATIONS` runtime permission (Android 13+) and the channel enabled. If the permission is denied or the channel is disabled, the hold is **not** silent: the persistent in-app review queue/badge is the fallback, surfaced on the next app open and on the home-screen badge count, and the hold is recorded in diagnostics (`review_alert_fallback_total`). The design never assumes background launch rights or notification delivery.
> - **(e) Persistence.** The review queue/badge is persistent until every held delivery is resolved (authorised, discarded, or reconciled) — it is not cleared by dismissing a notification. Dismissing the notification never resolves the hold.
>
> - **(f) Hard-stop cases and dual reasons.** The review surface (§B `AmountReview.kt`) does **not** offer the authorise-A′ action for a `RAW_UNAVAILABLE` delivery whose hold reason is a §7.3B hard stop (prior POST outcome UNKNOWN/HELD without authoritative evidence, endpoint incompatibility, or B14 failure); only discard or leave-held are offered, with the reason shown. The discard action is labelled on the review surface as a local disposition — it asserts nothing about whether the server received or applied the transaction — and the discard audit retains the unresolved server-effect evidence for later reconciliation. When a delivery is both amount-ambiguous and raw-lost, the review surface shows **both** review reasons (the amount question and the raw-loss question), in the `NEEDS_REVIEW` precedence order (§7.6).
>

## 8. Migration and cutover specification

### 8.1 Preflight and additive deployment

> **R29 P7 resolution (normative).** P7 owner decision defers **automated reverse migration** from the v1.1 MVP. The only supported recovery for `BLOCKED_CUTOVER` in MVP is fail-closed preservation of both stores, an operator-led retry of idempotent import, and a **documented, tested manual recovery runbook** with preflight snapshots, per-item inventory, authoritative server-effect reconciliation, explicit approval, copy-before-delete, and post-action counts. A manual recovery is not an app feature, must never automatically switch mode back to `LEGACY_ONLY`, and must not invent new `dedupe_key` values to evade server idempotency. If no safe recovery can be proven, remain `BLOCKED_CUTOVER` and escalate rather than force a downgrade. The older reverse-migration implementation language in item 6 below is **historical/deferred** and does not authorise an MVP reverse-migration code path. The pre-pilot recovery rehearsal is mandatory; the legacy F17 automatic-reverse fixture is deferred, replaced in MVP by an operator-runbook rehearsal fixture `F53`.

> **R31 Q1 recovery-export boundary (OWNER DECISION 2026-11-16, comment id 6905797710 — locked).** The manual recovery / migration procedure (§8.1 items 1/6, G10, §13) may export only sanitized route/configuration information, inventory, and non-sensitive operational metadata, subject to consent and secret-handling controls. It must NOT export raw notification bodies, transaction payloads, quarantined content, authentication secrets, or sensitive identifiers. A recovery/export procedure must never become a backdoor around the v1.1 diagnostic-export prohibition (§7.7, F55). The reconciliation export (§7.7A) is a separate capability governed by its own rules; a recovery/migration procedure must never masquerade as a reconciliation export. The R30 "recommended, pending owner confirmation" status is superseded by this owner decision.

1. **Preflight:** inventory legacy `routes`, `queue`, `log_entries`, `device`; export sanitized backup/config where appropriate; confirm signing key/update path and available storage. Run migration tests with synthetic queue fixtures.
2. **Additive deployment:** introduce the Room schema and migrations without enabling the new sender; the old sender remains the only active sender until cutover.
3. **Idempotent import:** map each legacy queue item using the existing `qkey` as the unique import key; preserve exact payload, route IDs/order, `next`, attempts, and last error; preserve `content_sha256` and the original legacy `dedupe_key` atomically from the staging row into `events` (R30, Q2); import in transactions. Persist import progress and verify count/checksum. Keep the legacy queue snapshot until verified.
4. **Single-owner cutover:** durable mode flag with migration state; prevent the legacy sender and the worker from claiming the same queue. Account for in-flight requests: stop/synchronise old dispatch before enabling the worker. Replaying uncertain in-flight requests relies on server-side idempotency.
5. **Verification:** validate counts, payload mapping, queue draining, chain decisions, 429/5xx/2xx-malformed, reboot, app process death, privacy. Do not remove the legacy queue snapshot prematurely.
6. **Rollback:** a downgraded APK cannot necessarily read Room; no assumption of automatic rollback. Specify a tested fallback release/migration-export procedure. Production device upgrade only after pilot. **Cutover is monotonic (normative, R10):** once `DRAINING` is durably committed, the mode never returns to `LEGACY_ONLY` automatically. The import retries idempotently from the frozen legacy queue; the legacy queue is retained unmodified until `WORKER_ONLY` is committed and the import is verified; only then is it cleared (per the §7.7 R29 barrier: individually verified imported/resolved entries only; quarantined entries retained). If the import cannot complete after bounded retries, the coordinator enters the durable `BLOCKED_CUTOVER` state (mode stays `DRAINING`, flagged blocked with a reason): delivery stays paused, diagnostics show the legacy-item count, imported-row count, and Room captures during DRAINING, and there is no automatic rollback. Recovery is explicit operator action only: (a) retry the import; or (b) reverse migration — a manual, confirmed, logged procedure moving Room PENDING rows (imported + DRAINING-captured) back into the legacy queue under fresh `qkey`s and then setting mode `LEGACY_ONLY`. Reverse migration is never automatic, must be rehearsed before pilot (fixture F17), and is crash-safe only up to server dedupe: its two stores cannot be updated in one transaction, so the procedure inserts into the legacy queue (commit + read-back) *before* deleting the Room row, and a post-migration reconciliation count is mandatory — a crash between steps leaves the event in both stores, which the server dedupes by `dedupe_key` but which must be counted, not assumed away. Whether reverse migration is required at all is P7 (default NO for MVP — see §12).

### 8.2 Bounded handoff and crash-safe import (C13/C19/C21(6), normative)

> **R29 P9 cutover override (normative).** Wherever this section says “all legacy queue items” or “clear the legacy queue”, read **all P9-inspected importable items** and **clear only the individually imported/verified or explicitly discarded entries**. Quarantined/uninspected entries are not copied to Room, not POSTed, not deleted by cutover, and remain inventoried in a durable legacy holding pen. The cutover marker records `snapshot_total`, `importable_count`, `quarantine_count`, `resolved_count`, `imported_count`, and separate canonical checksums of the importable set and quarantine metadata; verify `importable_count = imported_count` and exact `qkey`/payload/cursor equality for that set. Before committing `WORKER_ONLY`, verify quarantine remains inaccessible to the worker and has a functioning operator-review path. If this cannot be demonstrated, remain `DRAINING`/`BLOCKED_CUTOVER`. This override takes precedence over the older unqualified count-equality and whole-queue-clear wording below.

Definitions: a POST is "in-flight" from `post()` entry to `post()` return. A flush between queue items, or a chain item between routes after a `logged` response, is NOT in-flight. New POST dispatch is permitted only while the mode flag is `LEGACY_ONLY`.

The sender lock is `ReentrantLock(fair = true)` with timed acquire, replacing `synchronized(LOCK)`; only entry points are `enqueueItem` and `flush()` (verified `Sender.kt:59,73`); both use the same lock, released in `finally`; an interrupted acquire restores the interrupt flag and aborts that operation. Fairness is normative: `enqueueItem` spawns a flush thread on every enqueue, so without a fair lock a continuous notification stream could starve the coordinator.

**Handoff, in order, inside a single sender-lock hold:** (1) the coordinator acquires the sender lock (timed, fair, 45 s); on timeout it FAILS CLOSED — the system remains `LEGACY_ONLY`, the stall is logged/surfaced as a diagnostic, and the drain is retried after a 5-minute backoff (the timeout now occurs before any state change). (2) Durable flush: write the current in-memory queue with synchronous `saveQueueSync` (`SharedPreferences.commit()`), then read it back from disk and verify count + checksum against the in-memory snapshot; on mismatch FAIL CLOSED before any state change — remain `LEGACY_ONLY`, log a diagnostic, retry the flush. (3) Commit the mode flag to `DRAINING` via `SharedPreferences.commit()`; snapshot the queue from the verified state; release the lock. The linearisation point is the `DRAINING` commit: every `post()` start requires the lock plus a flag check of `LEGACY_ONLY` performed under the lock, so after the commit no POST can start; the per-route flag check before each POST inside the chain loop is retained as defence-in-depth. Committing under the lock cannot deadlock — the sender never blocks waiting for a flag change while holding the lock; `post()` is pure network I/O; `commit()` is a short synchronous disk write on the coordinator's background thread (never the main thread).

**Import, in order, each step durable before the next begins (freeze + verify + commit, then clear):** (1) Enter `DRAINING`: stop new legacy enqueues (captures go to staging/Room) and stop the legacy sender — `flush()` returns without dispatching while the mode is `DRAINING`. **No legacy flush runs during `DRAINING`.** (2) Freeze: under `Sender.LOCK`, copy the legacy queue read-only into Room import-staging rows (one per item, keyed by `qkey`, with exact payload, route IDs/order, `next`, attempts, last error) and checksum the ordered `qkey` set + payload hashes. The live legacy queue is not modified, not emptied, not moved. (3) Import idempotently from the staging copy into the Room outbox (`INSERT OR IGNORE` by `qkey`). (4) Verify: outbox count, `qkey` set, and checksum equal the snapshot; every item's payload/route/`next` mapping is validated — on failure, stay in `DRAINING` and retry from the staging copy. (5) Commit `WORKER_ONLY` durably (mode flag + migration state in one Room transaction). Only then, (6) clear the legacy queue (delete the SharedPreferences queue key), delete the import-staging copy, and record the clear with counts + checksum in the migration audit. The Room outbox is the durable copy from step (3) on; clearing the source after step (5) destroys nothing not already verified in Room. **No step clears, moves, or mutates the legacy queue before step (6).**

**Checksum definition (normative).** SHA-256 over the canonical per-item serialisation `qkey + '|' + payload JSON (keys sorted) + '|' + route_ids + '|' + next + '|' + attempts + '|' + last_error`, items sorted by `qkey`, joined. Count equality alone is not sufficient verification. Canonical JSON, defined recursively: object keys sorted lexicographically (Unicode code point order) at every depth; arrays keep order; strings escaped per RFC 8259 minimal set (only `"` `\` and U+0000–U+001F as `\u00XX`); numbers as plain decimal (integral, no fraction/exponent; non-integral via shortest round-trip decimal, no exponent); fixtures pin nested objects/arrays, a Unicode string, and a non-integral number.

**Phase marker (normative).** `collector_state` key `cutover_import` records `{phase: IMPORTING | IMPORTED_VERIFIED, snapshot_count, snapshot_checksum, imported_count}`. It lives in Room (transactional with the import), not in SharedPreferences; no SharedPreferences mirror is required. Crash recovery: no record → resume the drain, then import; `IMPORTING` → re-run the import (idempotent by `qkey`, already-imported rows skipped); `IMPORTED_VERIFIED` with the flag still `DRAINING` → re-verify, then commit `WORKER_ONLY`; crash after `WORKER_ONLY` but before the legacy queue is cleared → the worker already owns the Room rows, the old sender cannot dispatch (flag check), recovery clears the legacy snapshot. Import crash rows: before/during snapshot → partial/no staging copy, queue untouched → discard the partial copy (by snapshot id), re-snapshot. After snapshot, before/during import → staging copy complete, outbox partial → retry the import from the staging copy (`INSERT OR IGNORE`). After import, before verify → outbox complete, unverified → run verification; on mismatch, re-import from the staging copy. After verify, before `WORKER_ONLY` commit → verified outbox, mode still `DRAINING` → commit `WORKER_ONLY` (idempotent flag write). After `WORKER_ONLY`, before/during queue clear → mode `WORKER_ONLY`, queue present or partially cleared → (re-)run the clear (step 6); the worker already owns dispatch, the queue is inert; the outbox is unaffected.

**Bounded guarantee (normative, replacing the withdrawn R5 sentence "In no crash interleaving is an item lost or dispatched twice").** For any cutover attempt that reaches the `DRAINING` commit, no item enqueued before the coordinator's lock acquisition is lost, and no item is dispatched twice, in any crash interleaving. Before the `DRAINING` commit the system behaves exactly as legacy (the `apply()` write window).

**Enqueue freeze (normative).** `Sender.enqueueItem` checks the flag under the lock: if the flag is not `LEGACY_ONLY`, it does not append to the legacy queue (diagnostic log only). New captures during `DRAINING` go to Room via the refactored listener path; a legacy AlarmManager heartbeat enqueued during `DRAINING` is skipped — diagnosed (diagnostic counter + local log + `collector_state` entry), `HeartbeatWorker` is scheduled in the same coordinator step as the `WORKER_ONLY` commit, no heartbeat coverage is claimed for the `DRAINING` window, and the status card shows the gap explicitly.

**Old sender vs Room worker after `WORKER_ONLY` (normative, R14).** Three independent preventions, any one of which suffices: (i) the sender gate — `flush()` returns without dispatching when the mode is not `LEGACY_ONLY` (checked under `Sender.LOCK` at entry; the mode can only change via the coordinator, which waits for quiescence, so no mid-flush change is possible); (ii) the worker gate — the claim transaction reads `collector_state.cutover_state` and claims zero rows unless the mode is `WORKER_ONLY`; (iii) the Room `legacy_qkey` unique index — a second delivery for the same `qkey` is ignored as a duplicate. Between the `WORKER_ONLY` commit and the step-(6) queue clear, the queue file is inert because of (i).

**Supersession note.** R3's invariant ("the old sender dispatches iff `LEGACY_ONLY` or `DRAINING`") contradicted its own drain rule and was unimplementable; R5's "commit NOT under the lock / 45 s wait for quiesce" was withdrawn in R6 (Blocker A: a POST could start after the commit; `synchronized` cannot be waited on with a timeout). R12's import rows 8–9 (snapshot + "queue move" under the lock; clear the queue before the outbox insert is verified) are withdrawn in R13: they contradict C13/C19/C21 and "keep the legacy queue snapshot until verified".

### 8.3 Capture handoff gate (C21, normative, R10 as revised by R11–R13)

- **(1′) Capture callback never acquires the cutover lock, never touches a store.** It reads `key`, `packageName`, `postTime`, `flags`, `title`, `text`, `bigText` synchronously from the posted notification, builds an in-memory snapshot, hands it to a dedicated single-thread capture executor, and returns immediately. (`key` = update identity, §3; `flags` = group-summary filtering, applied on the live path too.)
- **(2′) On the executor thread, in order:** PrivacyGate runs in memory (classification/redaction, no I/O); the post-PrivacyGate snapshot is written to a durable staging row (the `capture_staging` table, keyed by `dedupe_key`, unique) in a synchronous Room transaction — no raw secret ever reaches disk, staging is strictly post-PrivacyGate; **for a §7.3 Option B delivery the raw snapshot is additionally held in a bounded in-memory map owned by the capture executor (§7.3A), keyed by `dedupe_key`, and is never written to staging, the outbox, or any log**; then the executor acquires the fair timed lock (5 s — the commit hold contains no network and no import, so 5 s is generous), reads the mode, and enqueues the snapshot to exactly one store (the legacy queue while `LEGACY_ONLY`, the Room outbox once `DRAINING` is committed); on successful enqueue the staging row is deleted in the same transaction. A periodic sweep (SyncScheduler reconciliation) re-promotes orphaned staging rows — e.g. after process death between staging and enqueue — through the same lock/mode gate, so promotion is idempotent by `dedupe_key`.
- **(3) Commit sequence under one short lock hold:** `saveQueueSync` + verified read-back (count + checksum) → commit `DRAINING` via `SharedPreferences.commit()` → take an immutable snapshot copy of the legacy queue → release. The Room import runs **outside** the lock, from that snapshot only.
- **(4) While the mode is `DRAINING`, new captures enqueue directly to Room** via a synchronous Room transaction on the executor thread (never the main thread); imported legacy rows are distinct from new Room captures by unique key (`qkey`/`dedupe_key`, unique constraint); the worker does not claim any row until the mode is `WORKER_ONLY` — the claim query itself is gated on the mode flag read in the same transaction. **(4′) Rescan cross-store rule:** Room enqueue dedupes on `dedupe_key` inside the same transaction (§6).
- **(5′) Import accounting:** the import checksum covers snapshot rows only — correct by construction. Room captures during DRAINING are tracked separately (diagnostic counter `room_captures_during_draining`) and, at the `WORKER_ONLY` commit, the coordinator asserts all of them are PENDING: none claimed early, none lost. The checksum's silence about them is a defined boundary, not a gap.
- **(6′) If the lock acquisition times out or the Room insert fails, nothing is skipped, nothing is enqueued blindly:** the staging row is already durable, so the executor retries with backoff on its own thread; an in-memory retry list exists only for the case where the staging write itself fails. Bounded capacities (proposed values, confirm against memory measurement in Stage D): executor work queue 500 pending snapshots, in-memory retry list 200 entries. Overflow policy on either: drop the oldest entry, increment `dropped_overflow`, surface in diagnostics — never block the callback thread, never grow unboundedly.
- **(7′) A failed Room insert rolls back, the staging row is retained, and the failure is surfaced;** a failed insert never silently drops a capture.
- **(8′)/(8″) Monotonic cutover** — see §8.1.
- **(9) Live capture and `rescanActive` share this gate:** rescan calls the same `processNotification` → same executor → same lock → same mode read, so C3 key consistency holds on both paths.
- **(10) Delivery pauses for the DRAINING import window** (the old sender stopped, the worker not yet claiming); the window is a local Room transaction, expected milliseconds to seconds, surfaced in diagnostics.

**No-loss scope (normative, R10, replacing R9 §3).** *Durable* = the capture reached the legacy queue (commit + read-back) or the Room outbox (transaction committed) or the staging table — from any of those points at-least-once chain holds and the event lands in exactly one store. *Best-effort* = everything before the staging write — the callback-to-executor handoff — can be lost on process death, is directly unmeasurable (no record exists), and must be described as such in disclosure/diagnostics. Durable staging narrows the loss window from "until enqueue completes" to "until the staging write completes" (milliseconds under normal contention); it cannot eliminate the handoff window without a disk write on the callback thread, which stays forbidden (main-thread ANR risk — `onNotificationPosted` runs synchronously on the callback/main thread; a 45 s lock wait there would block the main thread / stall system notification dispatch). That residual is accepted explicitly. *Measured, not assumed:* `capture_accepted`, `capture_staged`, `capture_enqueued`, `capture_parked` (staging-write failures held in RAM), `dropped_overflow`, `capture_recovered_rescan`. Unrecovered-before-enqueue loss has no counter by construction — the spec must say so, and must not claim a number it cannot produce. Short-lived/dismissed notifications vanishing before rescan are unrecoverable and uncounted; rescan reads `activeNotifications` only (still-active, <24 h) and runs only on listener connect or manual request. Out of scope: a notification callback in flight at process death before any durable enqueue. Stage B/C vs Stage D: the coordinator owns the lock, flag, and capture executor from Stage B; the Stage D listener change is routing only — `onNotificationPosted` hands the snapshot to the coordinator's executor instead of calling `Sender.enqueueChain` — through the same lock/flag; no interim release loses notifications because the legacy queue remains the capture store until the DRAINING commit, the single cutover point.

**Staging gate (normative, R11, defence in depth).** The staging writer re-runs the class-(a) span scan before writing; if any class-(a) span survives, the text is dropped and only structured fields are staged; if no structured field can be produced, the snapshot is dropped and counted (`dropped_unclassified`). Staging never holds raw text for an inseparable event. **The §7.3A in-memory raw snapshot is exempt from this paragraph only in the sense that it exists at all; it is never staged, and the staging writer never sees it.**

**Staging fan-out (normative, R12 C22(j)).** One notification snapshot fans out to staging rows exactly once, at capture, in a single Room transaction. The executor runs one PrivacyGate classification over the snapshot, derives the delivery set from the same classification and the same route-config snapshot — a chain `legacy_qkey` over the matched route set, plus any additional single-route deliveries the design requires — and writes the event row, the classification record, and one staging row per delivery (each keyed by its own `legacy_qkey`, carrying `dedupe_key`, `content_sha256`, `consent_epoch`, `config_epoch`) atomically. Either all rows land or none; a failed transaction means the event is not durably captured (the same loss window as above, recoverable by rescan while the notification is active). No second classification runs for the same snapshot; the sweeper and the claim path read the stored classification, never re-classify.

**Flush restructure (normative, R13 C21(5′′)).** The baseline flush (network inside `Sender.LOCK`) is not acceptable for v1.1. The restructured flush: (i) under `Sender.LOCK`, claim a bounded batch — snapshot the items to attempt, leave the queue file untouched; (ii) release the lock; (iii) POST outside the lock, writing each receipt transition (`READY → IN_FLIGHT → RESOLVED`) with synchronous Room writes; (iv) re-acquire `Sender.LOCK`, drop the resolved items, persist the remainder with `saveQueueSync`. A single-flight guard (`AtomicBoolean`, compare-and-set; a second `flush()` while one is in progress returns immediately) prevents two flushes POSTing the same item concurrently. Promotion now waits only for the brief claim step, never for network. Until this lands, the baseline blocking behaviour is a known limitation (promotion latency unbounded in queue depth × chain length × 30 s), and F23 must test the restructured flush, not the baseline. **Lock graph correction (R13):** "No lock is held across a network call" (R12 C22(k)) is withdrawn as false against the baseline: `Sender.flush()` takes `Sender.LOCK`, `flushLocked()` loops every queued item calling `processItem()` → `post()`, a blocking HTTP call with 15 s + 15 s timeouts per POST. **Single-flight guard (R14):** the guard is an in-memory `AtomicBoolean`, set by compare-and-set at flush entry; a second `flush()` sets a `flushRequested` flag and returns immediately. The guard brackets the *whole* flush including the terminal `saveQueueSync`, released in `finally` — so guard-clear implies the queue file is consistent with the receipts. Across a process restart the flag re-initialises to `false` by construction; that is not a hole, because no post-restart decision reads the flag — the durable truth is the receipt states + the mode flag. `flushRequested` rule: after the drop step, if `flushRequested` is set, exactly one more claim pass runs (the flag is cleared at pass start); a pass claiming nothing exits. Items failing retryable wait for the next trigger, as in the baseline; periodic reconciliation is the backstop.

**Lock ordering (normative, R12–R14).** Two Java locks exist in v1.1: the CutoverCoordinator lock (mode, consent, staging gate) and `Sender.LOCK` (legacy queue). Global order: Cutover → Sender → Room transaction (leaf: a Room transaction never acquires a Java lock). The promotion path is the only path acquiring both, always in that order, via `tryLock` with a bounded timeout; on timeout it fails closed (the staging row is left, retry later). The sweep acquires Cutover → Sender, in that order. `flushLocked` acquires `Sender.LOCK` only, never the Cutover lock; its ack write is a Room transaction inside `Sender.LOCK`, leaf-ordered. No path acquires Sender → Cutover. No lock is held across a network call in the restructured flush (the POST phase holds no lock at all). Deadlock-freedom follows from the acyclic order; the proof obligation is F23. The R12 sentence "the revocation sweep acquires the Cutover lock only, never `Sender.LOCK`" is withdrawn; the sweep runs under `Sender.LOCK` to read the queue file.

### 8.4 Mode/intent state table (C21(10), normative, R18)

Mode and drain intent are two separate durable fields in `collector_state`; the sender's fenced/unfenced state is derived from them plus the startup fence. The legal combinations are exactly these — every other combination is a defect, and the coordinator asserts it never observes one:

| # | Mode | Drain intent | Sender | Meaning |
|---|---|---|---|---|
| 1 | `LEGACY_ONLY` | `NONE` | unfenced | Normal operation. Legacy sender claims; captures dispatch. |
| 2 | `LEGACY_ONLY` | `PENDING` | fenced | Drain requested, quiescence awaited. No admission of any kind; captures are staged-held in Room; an in-progress flush finishes its current POST and exits at the hop boundary. The coordinator retries the quiescence check on its tick. |
| 3 | `DRAINING` | `QUIESCED` | fenced for legacy | Quiescence proven, legacy sender stopped, migration/import running. Captures are staged-held; the Room worker claims nothing yet. |
| 4 | `WORKER_ONLY` | `QUIESCED` | unfenced for worker | Cutover complete. The worker claims; the legacy sender never claims again. Staged-held captures are dispatched by the worker. |
| 5 | `LEGACY_ONLY` | `ABORTED` | unfenced | Cutover abandoned by operator action. The sender resumes normal claiming; unknown attempts stay held per §5.5 row 11. |

**Illegal combinations (normative).** `DRAINING` with intent `PENDING` does not exist: the mode transition and the intent's `PENDING → QUIESCED` transition commit in one Room transaction (transition rule below), so no observable state has the mode committed while the intent is still pending. `WORKER_ONLY` with intent `PENDING` or `ABORTED` does not exist. `LEGACY_ONLY` with intent `QUIESCED` does not exist outside the committing transaction. `DRAINING` with intent `ABORTED` does not exist — abort is defined only from `PENDING` (row 2 → row 5); aborting a committed cutover is a separate, unplanned operator procedure, not a design transition.

**Transition rule (normative).** There is no such thing as "committing `DRAINING` while the intent remains `PENDING`". `PENDING` is precisely the pre-commit state: the drain has been requested and quiescence has not yet been proven. The commit is one Room transaction, under the Cutover lock, that (i) re-checks the quiescence conditions as its linearisation point — zero unresolved `ATTEMPT_STARTED` rows owned by the current `boot_id`, the in-memory in-flight set empty, the queue file re-read under `Sender.LOCK` agreeing with the Room attempt record — and (ii) writes `mode=DRAINING` and `intent=QUIESCED` together. A crash before the commit leaves row 2 (`LEGACY_ONLY`/`PENDING`); a crash after it leaves row 3 (`DRAINING`/`QUIESCED`). The two writes are never observable separately, so no recovery path ever has to reconcile a half-committed cutover. "Drain requested" is row 2; "`DRAINING`" is the mode name for row 3 only. Any earlier text that uses "draining" for row 2 is loose wording, corrected here.

**Restart rules (normative).** On process start the coordinator reads `collector_state` before the sender starts: intent `PENDING` ⇒ re-fence, resume the drain from row 2, captures staged-held; intent `QUIESCED` with mode `DRAINING` ⇒ resume migration/import from row 3, captures staged-held; intent `QUIESCED` with mode `WORKER_ONLY` ⇒ normal worker operation, row 4; intent `ABORTED` ⇒ row 5, normal claiming resumes. In every case a fresh capture is staged durably in Room at capture time — staging is never fenced — and whether it is dispatched depends only on the row the restart lands in.

**Supersession note.** R17 §2(g)'s last sentence and F37 assertion (5) — "a fresh capture in the new process is admitted and dispatched normally" — were withdrawn in R18 as written; the correct assertion is conditional on the drain-intent state (F37a/F37b, §10). R18's F37a wording "the coordinator enters `DRAINING` per R17 §2(d) as applicable" was corrected in R19: `DRAINING` requires the atomic `PENDING → QUIESCED` commit, which cannot occur without a drain having been requested.

### 8.5 Atomic admission, pre-socket states, orphaned attempts (C21(8), C21(9), C21(11), normative)

**Atomic admission (R17 C21(8)).** (a) One transaction: admission is a single Room `@Transaction` that (i) reads, in this order, `collector_state` mode and drain generation, the sweep fence for the event's `dedupe_key`, and the route's `consent_epoch` and `config_epoch`; (ii) refuses, with a durable reason code (`FENCED` / `DRAIN_PENDING` / `EPOCH_STALE` / `MODE`), if any check fails; (iii) otherwise inserts a `delivery_attempts` row `{attempt_id` (UUID, single-use), `delivery_id`/`qkey`, `hop_index`, `route_id`, `consent_epoch`, `config_epoch`, `url_sha256`, `dedupe_key`, `started_at_ms`, `state=ATTEMPT_STARTED`, `owner_boot_id`, `drain_generation` and `fence_generation` observed at admission} and returns `ADMITTED`. The read and the insert commit together or not at all. (b) Serialisation: the admission transaction and the fence/intent installation transaction both acquire the Cutover lock first (`tryLock`, bounded 5 s, fail closed: admission refused, installation retried later) and then run the Room transaction; the global order stays Cutover → Room transaction (leaf). The linearisation point is the commit order of the two transactions: whichever commits first wins, and the loser's outcome is fully determined. Room's single-threaded transaction executor is a second, redundant serialisation guarantee, not the one the design relies on. No admission path takes `Sender.LOCK`. (c) Fence/intent installation (same shape): installing a drain intent or a sweep fence is a single Room transaction under the Cutover lock that writes the intent/fence row and, in the same transaction, snapshots the awaited set: every unresolved `ATTEMPT_STARTED` row for the affected scope. The awaited set is closed at install time: no attempt for a fenced event, and no attempt at all once a drain intent is `PENDING`, can be admitted afterwards. (d) Admission is a commitment: once `ADMITTED` returns, the sender proceeds to open the socket; it does **not** re-read the fence or intent between the marker commit and the socket open. A barrier installed after admission never invalidates an admitted attempt — it awaits it. The only refusal is at admission time. (e) Attempt identity: `attempt_id` is single-use, bound to exactly one socket open by the thread that admitted it. If the process dies between admission and socket-open, the attempt is orphaned — its outcome is `UNKNOWN`, never "never sent". (f) Legacy-path admission: the legacy flush's hop entry is the same transaction; a flush finding a hop refused exits at the hop boundary with the item durably queued; it does not fall back to an unrecorded POST. The Room worker's claim is the same transaction with the same checks. One admission rule, both paths. **Interleaving proof (F36):** (1) *marker commit → fence/intent commit → POST*: the installation transaction observes the unresolved marker, adds it to the awaited set, and the release waits for it; the POST proceeds. (2) *fence/intent commit → admission → POST*: admission returns `REFUSED` (`FENCED`/`DRAIN_PENDING`); no marker row exists, no socket opens. There is no third interleaving: the two transactions are serialised, so one of the two orders holds.

**Durable drain intent (R16 C21(6⁗) + R17 C21(9)).** The coordinator commits the drain intent in `collector_state` in one Room transaction BEFORE any in-memory flag is set: `{generation` (monotonic), `requested_at_ms`, `state: PENDING, requested_by}`. The intent is the single source of truth; `drainRequested`/`senderPaused` are in-memory caches of it. Every claim path — legacy flush entry, legacy per-hop entry, Room worker claim — reads the intent before claiming. While the state is `PENDING`, no new claim begins: the legacy flush exits without claiming (items stay queued durably), the Room worker claims nothing. A flush already in progress when the intent lands finishes its current POST, writes its per-hop checkpoint including the attempt completion, and exits at the hop boundary. Enqueue still accepts and durably stores new captures — the listener must never drop a notification — but they are staged-held, never dispatched while the intent is pending. Timeout: the intent stays `PENDING`; the mode stays `LEGACY_ONLY`; `senderPaused` is set so a resumed flush exits at the next hop boundary; the coordinator retries on the next tick or operator action. No mode is ever committed over a live or unknown attempt. Abort: the operator may mark the intent `ABORTED` at any time (durable); the sender resumes normal claiming; unknown attempts stay held per §5.5 row 11. Restart: on process start the coordinator reads `collector_state` before the sender starts: a `PENDING` intent re-fences the sender (no claims), the drain resumes from the intent; new captures during a pending drain are staged-held in Room; the legacy queue file is re-read as the snapshot source. Residual, stated plainly: if the legacy queue file itself is lost/corrupt, unattempted items in it are unrecoverable — a pre-existing baseline property (a single SharedPreferences file, no redundancy), not introduced by v1.1. Attempted hops are recoverable from the Room attempt rows.

**Process-lifetime ownership (R17 C21(9)).** (a) Single-process premise (verified): the manifest declares no `android:process` on any component. (b) Boot identity: at every process start, before any sender claim, the coordinator writes a fresh `boot_id` (UUID) + `boot_started_at_ms` into `collector_state` in one Room transaction. Every `ATTEMPT_STARTED` row carries its `owner_boot_id`. A row whose `owner_boot_id` differs from the current `boot_id` is `ORPHANED`: its process is dead, no live HTTP can be owned by it, and no live thread will ever complete it. The row's outcome stays `UNKNOWN_PENDING_RECONCILIATION` — orphaned is a statement about the owner, not about the server-side effect. A POST from the killed process may still have committed server-side; the client can never observe it, which is exactly what `UNKNOWN` means. (c) Startup fencing: the sender is born fenced: the boot transaction also sets `sender_fenced=true` in `collector_state`, and no admission is granted while it is set. The coordinator's boot scan runs before the sender starts: it classifies orphaned rows, re-installs fences from the durable drain intent (a `PENDING` intent re-fences the sender), and only then clears `sender_fenced` in one Room transaction. If the process dies mid-scan, the fence stays set and the next boot re-runs the scan — fail closed, never fail open. Staging (capture → Room) is not dispatch and is never fenced. (d) Quiescence, redefined: the coordinator commits `DRAINING` only when, in one Room transaction that re-checks the row count as its linearisation point: (i) zero unresolved `ATTEMPT_STARTED` rows with `owner_boot_id` equal to the current `boot_id`, (ii) the in-memory in-flight set empty, (iii) the queue file re-read under `Sender.LOCK` contains no copy whose event has no Room delivery in a known state. Orphaned rows do **not** block quiescence: "no live HTTP" is a claim about this process, and an orphaned row's process is dead. A concurrent completion checkpoint either commits before the `DRAINING` transaction (seen as resolved) or after it (the transaction sees one unresolved row, fails closed; the coordinator retries on the next tick). (e) In-flight set: the sender maintains an in-memory set of `attempt_id`s owned by live threads in this process: added on `ADMITTED`, removed only after the completion-checkpoint transaction commits. The set and the Room rows can disagree transiently — the coordinator then waits and retries; it never proceeds on the guard alone, and never treats the guard as evidence about the last attempt. (f) Completion on every exit path: the POST call site writes a completion checkpoint for **every** exit — response returned, observed exception, gate refusal — in a `finally`-style path catching `Throwable`. A live thread never leaves its own row unresolved except by process death, precisely the orphaned case. (g) Orphaned deliveries: a delivery whose hop has an orphaned unresolved row imports as `HELD_AWAITING_RECONCILIATION` (never dispatched, never re-POSTed as if new): the next hop requires a reconciliation record first (§9). The drain proceeds to `DRAINING` with such deliveries held; the hold is per-delivery, the mode is global, and the two do not block each other. A fresh capture in the new process is admitted normally under the new `boot_id`.

**The single transport state machine (R18 C21(11), normative).** `ADMITTED` — the marker transaction written before `openConnection()`, the only durable truth that a hop was entered. `ADMITTED → SOCKET_OPENING` — a claim transaction, succeeding only while the row is still `ADMITTED`, immediately before `connect()` is invoked. `SOCKET_OPENING → SOCKET_OPEN` — a checkpoint transaction immediately after `connect()` returns and before the output stream is touched. `SOCKET_OPEN → COMPLETED` — after the response returns and the completion checkpoint commits. Lease: the coordinator may abandon an `ADMITTED` attempt only (`ADMITTED → ABANDONED_PRE_SOCKET`, 60 s `ADMISSION_LEASE_MS`); it never abandons `SOCKET_OPENING` or `SOCKET_OPEN` while the owner lives. Recovery (owner `boot_id` dead): orphaned `ADMITTED`/`SOCKET_OPENING` ⇒ `NEVER_SENT` **(conditional — see the gate below)**; orphaned `SOCKET_OPEN` without completion ⇒ `UNKNOWN_PENDING_RECONCILIATION`. `NO_POST` is a classification, not a row state: an exception from `connect()`, DNS, or output-stream acquisition — observed in-process, before the first request byte — is `NO_POST`; once the first byte is written, any failure is `UNKNOWN`. A crash is classified from the durable state, never from the crash point.

**The bytes invariant (normative, the load-bearing rule; test assumption until F40 passes).** No request byte is written before the `SOCKET_OPEN` checkpoint commits. The `post()` call site is ordered: `connect()` → checkpoint transaction → `getOutputStream()`/write. If the checkpoint write fails (storage error), the POST does not start — fail closed. Before the `SOCKET_OPEN` checkpoint commits, the client causes zero HTTP request bytes to reach the origin and zero handler invocations on the origin. TCP/TLS handshake bytes and a proxy `CONNECT` carry no application payload and are classified as non-effect only when both (a) no HTTP request bytes reached the origin and (b) the handler log shows zero invocations; otherwise the attempt is "a POST may have happened" and stays `UNKNOWN`.

**Lease — abandonment (normative).** The coordinator may abandon an `ADMITTED` attempt whose `admitted_at_ms` is older than `ADMISSION_LEASE_MS` (60 s): one Room transaction, `ADMITTED → ABANDONED_PRE_SOCKET`, succeeding only if the row is still `ADMITTED`. The owning thread, on claim failure (its `ADMITTED → SOCKET_OPENING` transaction finds the row no longer `ADMITTED`), exits without opening a socket and removes itself from the in-memory in-flight set. The claim transaction and the abandon transaction are mutually exclusive on the row state — whichever commits first wins; the loser observes the row state and acts accordingly. There is no interleaving in which both the abandon and the socket-open happen. The coordinator never abandons a `SOCKET_OPENING` or `SOCKET_OPEN` attempt while its owner process is alive, and never treats lease expiry as evidence of non-send. An `ABANDONED_PRE_SOCKET` attempt counts as resolved for the awaited set — a durable terminal state, not a timeout inference.

**Bounds on the remaining wait (normative).** After a successful claim, the thread's next steps are `connect()` (bounded by the 15 s connect timeout) and then the checkpoint and write. The only unbounded element is thread scheduling itself (a thread suspended by Android scheduling/Doze between claim and `connect()`), and that is bounded by process death: a dead process's `SOCKET_OPENING` row is orphaned **(classification conditional — see the gate below)**. The coordinator therefore waits for `SOCKET_OPENING` while the owner lives, and raises an operator alert if one persists beyond `OPENING_ALERT_MS` (5 min) so the stall is visible, never silent. The operator runbook for a stuck `SOCKET_OPENING` is: restart the app (the process dies, the row orphans to `NEVER_SENT`, the hop is re-admitted) — never "assume unsent and re-POST in parallel". **The restart is a disruptive manual recovery, not a bounded automated liveness guarantee (R19):** the restart kills in-flight work and re-fences the sender. What the design guarantees for a paused post-claim thread is visibility (the alert) and a safe post-restart classification, not a bound on how long a live paused thread may wait.

**One live attempt per hop (normative).** Admission refuses a hop while an `ADMITTED`/`SOCKET_OPENING`/`SOCKET_OPEN` attempt for the same delivery and hop is unresolved. A new attempt for the hop is admitted only after the previous one is terminal: `COMPLETED`, `ABANDONED_PRE_SOCKET`, or `NEVER_SENT` (recovery-written).

**Crash matrix, revised (normative, replaces R16 F31 cases (1)–(2); cases (3)–(5) retained).** Kill (1a) after the marker write, before `connect()` ⇒ `NEVER_SENT`; (1b) after `connect()` returns, before the `SOCKET_OPEN` checkpoint ⇒ `NEVER_SENT` (socket open, zero bytes — the socket dies with the process); (2a) during `connect()` ⇒ `NEVER_SENT`; (2b) during the write, after the checkpoint ⇒ `UNKNOWN`; (3) during the read wait ⇒ `UNKNOWN`; (4) after server commit, before the response ⇒ `UNKNOWN`; (5) after the response, before the completion checkpoint ⇒ `UNKNOWN`. The R16 rule "a kill after the marker write is always `UNKNOWN`" is narrowed to the post-checkpoint kills (2b)–(5). In-process observed connect/DNS/output-stream failure (no crash) stays `NO_POST`. **All `NEVER_SENT` entries in this matrix are conditional on the F40 gate below.**

> **CONSOLIDATION-GATE RESOLUTION 3 — D5 `NEVER_SENT` is CONDITIONAL on F40, not unconditional (normative, supersedes the unconditional reading of R21 D5).** The orphaned `ADMITTED` / `SOCKET_OPENING` ⇒ `NEVER_SENT` classification, and the crash-matrix entries (1a), (1b), (2a), apply **only after F40 cases E1/E2/E3 (+ I, J) have PASSED on the actual stack**, proving zero HTTP request bytes and zero handler invocations before the `SOCKET_OPEN` checkpoint. Until F40 passes, those orphans classify `UNKNOWN_PENDING_RECONCILIATION`. If E1 fails (headers sent on `connect()`), the checkpoint moves earlier — before `openConnection()` — or the transport changes, and the failure is recorded as a finding, not worked around by rewording the assertion. **F40 is labelled a test assumption until run**, and F40 is a pre-pilot acceptance gate for the `NEVER_SENT` rule: the rule must not be relied on by the sweep, the drain, or any release decision before F40 passes. The bytes invariant above is therefore stated as a test assumption in this document, not as established behaviour of the stack.

**Supersession note.** R20 §3 ("the v1.1 code path therefore never calls `connect()`") is withdrawn by R21 D5: it contradicts R18 C21(11), which specifies explicit `connect()` in the production path. The baseline calls `conn.outputStream` directly with no explicit `connect()` (verified again in R21: the only `connect()`-shaped call in the app is `conn.disconnect()`); v1.1 adds the explicit `connect()` call. This machine supersedes the R16-era C21(7)(d) blanket rule ("a crash at any point after the marker write is `UNKNOWN`") — already superseded by R18 C21(11); restated here so there is exactly one crash-classification rule in the register.

**Per-hop quiescence boundary (normative, R15 C21(6‴)).** (a) Drain request: the coordinator sets the durable drain intent (§8.4) before committing `DRAINING`. A flush already in progress is not interrupted mid-POST: the HTTP in flight runs to its own outcome (success, 4xx, 5xx, or timeout — bounded by construction, 15 s connect + 15 s read). (b) Per-hop checkpoint: after every POST returns, before the next hop is considered, the restructured flush persists the per-hop checkpoint (§5.5). Only after the checkpoint is durable does the flush evaluate the drain request. (c) Stop at the hop boundary: if the drain is requested, the flush runs the drop step for the items it touched (persisting resolutions and updated `next` values with `saveQueueSync`) and exits without starting the next hop and without starting the next claimed item. The drain interrupts the chain at the hop boundary, and the snapshot carries the durable `next`. (d) Bound: the coordinator waits on the single-flight guard with a timeout of one POST (30 s) + 60 s margin. The bound is structural — it does not depend on reading a hop count from the queue item. (e) Snapshot precondition: the snapshot runs only after the guard clears AND the queue file is re-read under `Sender.LOCK` — the read-back proves the file reflects every per-hop checkpoint the flush made.

**Drain timeout (normative, R15/R16).** If the guard does not clear within one POST + margin, the coordinator does *not* commit `DRAINING` and does *not* enter BLOCKED_CUTOVER. A POST is bounded by construction at 30 s, so a drain wait beyond 30 s + margin means the flush thread is stalled (scheduler suspension, Doze), not the network — waiting longer cannot help, and committing the mode over a live request would be exactly the error named. Instead the coordinator: (1) sets an in-memory `senderPaused` flag (`AtomicBoolean`, checked by the flush at entry and after every POST before the next hop; cleared only by the coordinator after successful quiescence), so if the flush thread resumes it finishes the current POST, persists the checkpoint, and exits without starting the next hop; (2) records `drain_state=timeout` with the in-flight `qkey` and hop index in `collector_state` as a durable diagnostic (not a mode); (3) leaves the mode `LEGACY_ONLY`; (4) surfaces a diagnostic for the operator, and retries the drain on the next coordinator tick or operator action. There is no force path: no mode is ever committed over a live flush. If the process dies in between, the in-memory flags are gone by construction, and recovery re-derives quiescence from the guard (`false` after restart) plus the receipt states — the R15 sentence that treated the guard state as evidence about the last HTTP attempt is withdrawn in R16 (the guard state is never evidence about the last attempt). BLOCKED_CUTOVER is entered only after quiescence is proven (guard clear) and the snapshot then fails on a durable, proven fault (e.g. an unresolvable receipt) — never while a request is live. If the guard never clears, the mode stays `LEGACY_ONLY` with the durable `drain_state=timeout` diagnostic; the operator options are wait/retry or restart the app (process death clears the guard; recovery proceeds from the receipts). No force path exists by design.

**Revoked consent during drain (normative, R15).** The per-hop gate re-checks the route stamp (`route_id → consent_epoch, config_epoch, url_sha256`) before *every* hop, including the hop after the drain was requested. If the next hop's route was revoked or its URL changed while the drain was waiting, the hop is not entered: the hop outcome is `BLOCKED_CONSENT` (or `BLOCKED_CONFIG`), the chain stops at the boundary, `next` is not advanced, and the snapshot carries `next` + the blocked reason. The worker never claims a revoked route; a later re-approval resumes the chain from the same `next`. The drain does not force a hop past revoked consent, and does not skip a revoked hop to try the next route — halt, not skip.

**Snapshot import rule (normative, R15).** An item imports as terminal *only* if the per-hop record proves a chain-terminal outcome (row 2a, or every hop terminal per rows 1/3/6 with none unknown, or the chain exhausted). Otherwise it imports as `PENDING` with the persisted `next_route_index` + `hop_outcomes`. If the per-hop record is absent for a hop that was attempted (a crash between the POST return and the attempt-row write), the item imports as `PENDING` with that hop `UNKNOWN_PENDING_RECONCILIATION` and `next` at the last durable index — never terminal, never advanced on unknown evidence. No item is ever imported as `PENDING` when the receipt proves `RESOLVED`-terminal, and no item is ever imported as terminal on an unknown hop. **No-lost-hop / no-duplicate-settlement proof sketch (invariants):** (i) a hop advances only on a positively-observed terminal outcome for that hop with no unknown flag (rows 1/3/6); (ii) `MATCHED`/`AMBIGUOUS` stops the chain, idempotent at the server via `dedupe_key` — a re-POST after a crash returns the same claim, and the client treats any matched/ambiguous response as terminal regardless of attempt number — qualified by §5.4: only `matched + apply=ok` is settlement; (iii) an unknown hop never advances without out-of-band reconciliation (rows 4, 9, 10, 11); (iv) `next_route_index` is durable per hop, and the snapshot join prefers Room attempt rows over the queue file. Crash windows: between the POST return and the attempt-row write → the attempt is unrecorded; on recovery the hop is re-POSTed under at-least-once; if the first POST matched, the re-POST returns matched (terminal, correct) or a duplicate `logged` (row 9 → stays unknown, reconciled out-of-band) — no second settlement, because the chain never advances past an unknown hop. Between the attempt-row write and `saveQueueSync` → the Room row wins the snapshot join. Between `saveQueueSync` and the next POST → consistent by construction. During the drain wait → per-hop boundary + checkpoint. During the drop step → the drop re-reads the queue file under `Sender.LOCK` and removes only resolved `qkey`s. A lost hop would require advancing `next` past an unproven hop, forbidden by (i); a duplicate business action would require entering a second route after a matched first hop, forbidden by (ii)/(iii).

### 8.6 Two-store sweep protocol and fence lifecycle (C22(o′′′′′), normative, R18/R19)

**(a) Stores and their guarantees.** Room is the durable record of decisions and evidence. The queue file (`SharedPreferences`) is the legacy store being drained; its replacement is atomic at the file level (write-temp + rename), so after a crash the file is either the old version or the new version, never half-written — but a single `commit()` returning does not by itself prove which version is on disk, which is why the readback in (b)(3) exists. The baseline has no synchronous queue write (`Store.kt:252–255`, `saveQueue` uses `apply()`), so v1.1 adds `saveQueueSync` — `commit()` plus a readback of the queue key — as a file-plan item. **Readback, corrected (R19):** `commit()` is a synchronous disk write; the getter readback afterwards reads the in-memory cache and confirms only that the in-memory view agrees — it is a sanity check, not crash-proof persistence evidence, and no sweep decision treats it as the latter. The crash-proof evidence is the Room sweep intent (step (b)(2)), a durable write-ahead record written before the queue is touched. Recovery after a crash re-reads the queue from a fresh process — a new `SharedPreferences` instance, the pre-crash cache gone — so a post-restart readback *is* a disk read, and it is the post-restart readback, together with the intent, that drives the recovery decision. The pre-crash in-memory view is never consulted after a restart, because it no longer exists.

**(b) Ordered protocol.** For each copy, under the `ACTIVE` fence and holding `Sender.LOCK` for the queue steps: (1) await/reconcile — the awaited set for the event is empty, or the copy's decision rests on a reconciliation record already durable (§8.7 table); (2) write the sweep **intent** to Room, durably, *before* touching the queue: `{sweep_intent_id, event_id/dedupe_key, decision (remove | keep), basis (attempt outcome / E-case + reconciliation record id + query result summary), queue_snapshot (the copy's `qkey`, `attempts`, `last_try` as observed at scan time)}`; (3) remove the copy via `saveQueueSync` under `Sender.LOCK` and read back the queue key — the removal is confirmed only if `commit()` returned true **and** the readback shows the copy absent; any other outcome ⇒ removal failed, the sweep record stays unwritten, the fence stays `ACTIVE`, retry later; (4) write the Room sweep record `VERIFIED` — in the **same** Room transaction as the fence release and the pick transition (fence `→ RELEASED` + pick `HELD → PENDING/BLOCKED` commit together or neither does) — recording `{sweep_intent_id, removal_confirmed_by_readback_at_ms, basis}`.

**(c) Crash points and recovery (normative).** Crash after (1), before (2): fence `ACTIVE`, no intent ⇒ recovery re-runs the sweep from the attempt record; idempotent. Crash after (2), before (3): intent present, copy still in the queue ⇒ recovery re-runs the removal from the intent (the intent is the evidence; the queue state is re-checked, not assumed). Crash during (3): the queue file is old or new (file-level atomicity) ⇒ recovery readbacks: copy present ⇒ re-run the removal; copy absent ⇒ proceed to (4) **from the intent's evidence**, not from the absence. Crash after (3), before (4): copy absent, no `VERIFIED` record ⇒ recovery does **not** infer a successful sweep from the absence. It re-reads the sweep intent (the decision + basis, durable since step (2)) and the attempt record, re-verifies the queue by readback, then writes `VERIFIED` from the intent's evidence and releases the fence + pick in the same transaction. If the intent is missing or its basis is incomplete (corrupt intent) ⇒ the pick stays `HELD` for operator review — never auto-released. Crash after (4): fence `RELEASED`, pick transitioned ⇒ done; a re-run finds the fence released and the copy absent ⇒ no-op.

**(d) The absence rule (normative).** For pre-v1.1 copies in particular, queue absence is never evidence of anything by itself: absence + a durable intent whose basis is a reconciliation record ⇒ complete `VERIFIED` from that record; absence + no intent ⇒ `HELD`, re-sweep from the attempt record; absence + an intent whose basis is "the copy was not there at scan time" is not a decision at all — a copy the scan never saw gets no intent and no removal. The sweep's evidence is always the attempt record or the reconciliation record, carried in the intent; the readback only confirms the removal landed.

**(e) The release transaction's re-check.** The transaction in step (4) re-checks the awaited set as its linearisation point: every awaited attempt resolved — by completion checkpoint, reconciliation record, or `ABANDONED_PRE_SOCKET` — never by timeout alone and never by queue absence.

**(f′′) The fence invariant (normative, new in R19).** Between fence installation and Room `RELEASE`, the fenced copy cannot be dispatched even if the SharedPreferences write fails. Dispatch requires the fence to be `RELEASED` — the sender checks the fence before claiming any hop — and `RELEASE` commits only in the step-(4) Room transaction together with `VERIFIED`. A SharedPreferences write failure aborts the sweep before step (4): the intent stays, the fence stays `ACTIVE`, the pick stays `HELD`, and zero POSTs follow for that copy. The invariant is enforced by the ordering, not by the write succeeding. F38 asserts it.

**Fence lifecycle (normative, R17 C22(o′′′′)).** (a) States: a sweep fence is `ACTIVE` from install until release; there is no other terminal state. `RELEASED` is written only by the release transaction in (c). (b) Install: one Room transaction under the Cutover lock: the fence row `{fence_id, event_id/dedupe_key, installed_at_ms, state: ACTIVE}` plus the awaited set captured in the same transaction. The fence is a barrier for future admissions of that event (C21(8)(c)) and an await-list for admissions that already happened. (c) Release: one Room transaction that atomically (i) checks the awaited set is empty — every awaited attempt resolved by a completion checkpoint or a reconciliation record, never by timeout alone — (ii) checks the sweep record for the event is committed (`removed` | `absent` | `dispatched-known`, §8.7), and (iii) writes `fence → RELEASED` and the pick transition (`HELD_AWAITING_LEGACY_SWEEP → PENDING` to continue the chain, or `→ BLOCKED` per §8.7) together. A crash cannot split the fence release from the pick transition: they commit in one transaction or neither does. (d) Crash recovery: on boot, the coordinator re-reads every `ACTIVE` fence with its pick and sweep record: fence `ACTIVE` + pick already terminal (`PENDING`/`BLOCKED`) + sweep record present ⇒ re-run the release transaction (idempotent — the record already exists); fence `ACTIVE` + pick `HELD` + copy removed + awaited set empty ⇒ release; anything else ⇒ the fence stays `ACTIVE` and the pick stays `HELD`. A fence with an orphaned awaited attempt stays `ACTIVE` across the reboot until that attempt is reconciled — the pick is held, the drain is not (§8.5(g)). (e) Stale admission: a pre-fence admission cannot POST after release, because release requires the awaited set empty, and an admitted attempt leaves the awaited set only by resolving: either its POST completed and checkpointed before release (the POST already happened — there is nothing stale left to send), or it was reconciled (the delivery is `HELD`/`BLOCKED` and any later POST is a new attempt with a new `attempt_id`, gated by a fresh admission). An `attempt_id` never opens a second socket. The release transaction's re-check of the awaited set is its linearisation point: a completion checkpoint committing after the re-check leaves the fence unreleased and the coordinator retries.

**Supersession note.** R17 §4 ("Remove always means removal via `saveQueueSync` with the sweep record written in the same release transaction") was withdrawn in R18: a SharedPreferences removal cannot share a Room transaction. The two-store protocol above replaces it. R18 §3(a)'s "`commit()` + readback" characterisation was corrected in R19 (readback is a sanity check, not crash-proof evidence). R16 §3(c) ("completed `LOGGED` / `NO_POST` / `BLOCKED` ⇒ undispatched ⇒ remove") was withdrawn for `LOGGED` and for `BLOCKED`-with-observed-4xx in R17 §4 (see §8.7).

### 8.7 Sweep decision table (normative, R17 §4 as revised by R19/R20/R21/R23/R24)

The sweep runs under the fence (§8.6), reads the queue file under `Sender.LOCK`, and decides each copy from the durable attempt record — never from presence alone. "Remove" always means removal via the §8.6 protocol.

| # | Attempt history for the copy | Sweep decision | Pick release |
|---|---|---|---|
| 1 | Completed `MATCHED` + `apply=ok` | Dispatched, settled — remove | `BLOCKED` with `prior_copy_dispatched` |
| 2 | Completed `MATCHED` + `apply=skip`/`error`/absent, or `AMBIGUOUS` | Dispatched, outcome per §5.4 rows 2b–2d — remove only after the hop outcome is recorded on the Room delivery; chain stops | `HELD` until the outcome is recorded, then per §5.4 (reconcile before any settlement claim) |
| 3 | Completed `LOGGED` (2xx, `match.status=logged`, response observed in-process) | **Dispatched, outcome known, no settlement** — remove; record the hop outcome `logged` on the Room delivery | Release to `PENDING`: the chain continues at the **next** hop (or `ACKED` with `last_match_status=logged` if it was the last route, §5) |
| 4 | `NO_POST` (observed in-process: connect/DNS failure before request bytes, or pre-flight gate refusal) | Undispatched — remove | Release to `PENDING`: the chain resumes at **this** hop |
| 5 | `BLOCKED` with observed 4xx — **evidenced by a durable per-hop record**: a Room `delivery_attempts` row recording the 4xx for that route, or the queue item's `hop_outcomes` as written by the v1.1 flush checkpoint (§5.5) | Dispatched-rejected, no recorder row (verified) — remove; record `rejected-4xx` on the delivery | Release to `PENDING`: the chain advances past the route **only because the durable record proves this hop was refused with a 4xx and the legacy sender already advanced the cursor past it** |
| 6 | `BLOCKED` by gate (route disabled/missing/secret empty, no POST sent) | Undispatched — remove | Release to `PENDING`: the chain resumes at **this** hop (the route state is re-evaluated; a re-enabled route is retried, a still-disabled route is skipped by the normal chain rule) |
| 7 | Unresolved `ATTEMPT_STARTED` or `UNKNOWN` completion | Dispatch unknown — do **not** remove, do **not** release | Pick stays `HELD` with `prior_copy_unknown` until the attempt resolves by checkpoint or reconciliation |
| 8 | No attempt record and no promotion receipt (pre-v1.1 copy) | Outcome unknown — see the evidence matrix below; never remove on local absence alone | Pick stays `HELD` until a reconciliation record exists |

**Row 5 guard (normative, R24).** Row 5 never applies on cursor evidence alone. If no durable per-hop 4xx record exists for the hop, row 5 does not apply: the copy is unknown for this hop, row 7/8 (or the pre-v1.1 evidence matrix) applies instead, the copy stays `HELD`, and attribution is to the operator — never an automatic advance. A legacy cursor that advanced without a per-hop record is not evidence of a 4xx, of a `logged`, or of anything else about that hop. The §5.4/§5.5 row 3 halt rule for the v1.1 worker is unchanged by this guard: the guard governs what the sweep may infer about a legacy copy, not what the worker does on a live 4xx.

**Pre-v1.1 evidence matrix (normative, R17 as revised by R19/R20/R21).** A pre-v1.1 copy has no Room attempt row and no promotion receipt — the baseline kept no dispatch record at all. The only local evidence is the queue item's own fields (`attempts`, `last_try`, `last_error`, written by `markFail` only after `post()` *returns* a retryable outcome) and the server-side status query by `dedupe_key` (§9, P12). Missing attempt history is not evidence of never-dispatched: a crash inside `post()` leaves `attempts` unchanged and no record anywhere.

| Case | Local evidence | Server query by `dedupe_key` | Meaning | Sweep action |
|---|---|---|---|---|
| E1 | `attempts==0`, no `last_try` | No row | Never sent, **or** crashed before arrival, **or** sent and rejected 4xx (no row either way) — locally indistinguishable | Record the reconciliation (query result, durably) → remove → release to `PENDING` with the hop marked **retry-same-hop**: re-POST under at-least-once with the **same** `dedupe_key`. **Per-route prior-effect assessment (normative, pre-pilot deliverable, R17).** Before the pilot, the design records one row per route endpoint — warganet `notify.php` (verified), warganet `catat.php` (verified from the reference copy in this repo), v2New `notify.php` (unverified, P11): for each, what a POST causes server-side when it does *not* settle (recorder row? which table? deduped by what key?), the 4xx behaviour (row or no row?), and the duplicate-response shape. A route whose row is unverified keeps its copies `HELD` (case E4-equivalent: no sweep release) until its row is verified. The status query (P12) is the mechanism the sweep calls inline for E1–E3; the server-log audit (R16 option (b)) resolves a hold out-of-band but cannot be called by the sweep — a hold that can only be resolved by (b) waits for the operator runbook, it does not auto-release.

**Pre-v1.1 evidence model (normative, R19 (a′)–(d′)).** (a′) Identity is the stored opaque key, never a recomputed one: for every copy, the identity is the `dedupe_key` stored inside the queue item's payload JSON. The queue preserves it verbatim — `Sender.kt:45,55` build the `qkey` from `payload.optString("dedupe_key")` and the queue file stores the payload as-is — so the stored key is available without any computation. (b′) Destination is never substituted from the current URL: a pre-v1.1 copy is auto-released only on a reconciliation record keyed by its stored opaque `dedupe_key` — a server-side lookup keyed by that key — or by an operator decision recorded in the sweep intent. The route's current URL is not evidence of the copy's destination and is never substituted for the missing stamp. If no reconciliation record exists and no trustworthy route snapshot exists — in the baseline, none exists — the copy stays `HELD` for operator reconciliation. It is never auto-released, and it is never re-dispatched to the route's current URL on the sweep's authority; re-dispatch to a current URL requires the operator to confirm the route is the same billing system, recorded in the intent. (c′) Route-deleted: a copy whose `route_ids` reference a route id that no longer exists is `HELD`, never silently dropped. The baseline drops it silently (`Sender.kt:125–131`, `routeById` null → `next++` until the chain ends), which is exactly the loss the sweep exists to prevent; v1.1 must hold it for the operator instead. (d′) E4 vacated for pre-v1.1 copies — see the matrix above.

R18 C21(12)(e) (two concordant answers ≥ 30 s apart prove non-insertion) is withdrawn in R19: two `found:false` answers 30 s apart can both predate the INSERT of a POST that timed out client-side but is still running server-side, and a positive `logged` cannot distinguish "matching finished, zero hits" from "INSERT committed, matching still running". R19 (b′) ("a server-side lookup in `paylist_log`") is replaced by R20 (b′′) in §9: a positive row never releases or advances a hop by itself. R17 E1/E2's "retry-same-hop on no row" authorisation now requires the completion protocol (§9), not two wall-clock answers.

### 8.8 Reconciliation (operator audit, C14, normative)

> Reconciliation (pre-production gate; the P12 status endpoint is the sweep-time mechanism, §9): the OPERATOR runs a read-only audit joining server rows to client events on `dedupe_key` per route. The audit covers all server `matched` rows with `applied_at IS NULL` or `apply_note` non-success, plus all client events with `last_apply_status` in {`skip`, `error`} or null-after-ACK (`unknown`). Cadence: daily during the pilot, weekly in steady state. Escalation: any item in the audit set is an unresolved reconciliation item owned by the operator for manual resolution; the pilot (G9) cannot conclude with any unresolved item. An `unknown` item is not automatically a failed settlement — it is an item requiring the audit to determine the server-side outcome. Raw totals are not sufficient evidence: `matched count == settlement count` does not prove zero duplicate settlements where other channels (e.g. manual payment) can also settle invoices; the per-`dedupe_key` join is the evidence. The audit is a defined read-only query/script the operator runs; its exact form is documented in `docs/operations.md`.

**Pre-cutover verification: no second sender (C15, normative).** Before cutover, verify that no legacy sender app is still installed/active on the listener phone (g57); the result is recorded in the issue. The server INSERT→UPDATE stale-read window is only closed when no second concurrent sender exists.

## 9. Server reconciliation — P12-revised (OWNER DECISION TO BUILD, 2026-11-15; implementation still needs Phase 1.3 approval)

P12 is a hard pre-pilot prerequisite: the pilot cannot proceed with auto-reconciliation until P12 exists and F42 passes. The decision to build is a design direction; implementation still requires Phase 1.3 approval, and no code, commit, or deployment follows from this document.

### 9.1 Endpoints, schema, completion marker (P12-revised, normative, R20 as amended by R21 D1–D4)

> **(a) Endpoints (exact).** `GET /paylist/status.php` (warganet, `notify.php` rows) and `GET /paylist/catat-status.php` (warganet, `catat_uang` rows) — two endpoints because the two tables have different secret tables (`paylist_config` vs `catat_config`) and different answer shapes. v2New twins are specified from the v2New code when P11 lands; no v2New contract row is written here. Auth: `X-QRIS-Secret`, the same SHA-256 hash comparison as the POST endpoints; 401 on failure; a 401/5xx/timeout is "query inconclusive", never "no row".
>
> **(b) Read-only.** A status query has no INSERT/UPDATE/apply/matching side effects. It never triggers matching or apply, and it never re-POSTs anything. The sweep's only reconciliation method is this endpoint; the sweep never uses a re-POST as a probe.
>
> **(c) Response schema (notify).** `{ok:true, found:bool, in_flight:bool, system_id, dedupe_key, match_status, matched_id_pelanggan, matched_id_payment, applied_at, apply_note, completed_at, received_at}`. **(catat):** `{ok:true, found:bool, in_flight:bool, system_id, dedupe_key, recorded:true, received_at}` — no `completed_at` field (the recorder needs no completion marker for its own effect, §9.3).
>
> **(d) Completion marker semantics.** New column `paylist_log.completed_at TIMESTAMP NULL`, written by `notify.php` at the end of the request — after matching and after the apply attempt returns — unconditionally: it marks *request completion*, not apply success, so it is written when apply is skipped, fails, or errors too. A row with `completed_at` non-null and `match_status='logged'` proves matching finished with no hit. A row with `completed_at` NULL proves nothing about completion: the request may still be running, or may have died mid-request. The duplicate path does **not** backfill `completed_at`: if the duplicate acquired the per-key lock (§9.2) and finds `completed_at` NULL, the original is dead mid-request, matching may have run partially, and backfilling would falsely claim completion — the row stays unmarked and `HELD` for operator review. P12 changes no matching or apply behaviour.
>
> **(e) Per-key serialisation (normative, the decided mechanism).** `notify.php` acquires a MySQL named lock at request start (after auth), held until after the `completed_at` write: lock name is the hex SHA-256 of the `dedupe_key` (exactly 64 characters, the `GET_LOCK` limit — the raw key is up to 128 characters and must not be used as the lock name). Acquisition timeout 5 s: on failure the endpoint answers 503 (retryable; the client already treats 5xx as retryable, `Sender.kt:200–210`). The lock is held on the same connection as the INSERT/match/apply and released explicitly before responding; connection close releases it implicitly. If the server operator declines named locks, the alternative is the R19 (e′)(ii) documented upper bound on in-flight request lifetime *plus* a safe margin, with measured evidence from the live server's `max_execution_time` / FPM `request_terminate_timeout` — the bound is a measured server fact established at P12 implementation time, never assumed here. P12 requires exactly one of the two, named in the contract row, before pilot.
>
> **(f) Migration of existing rows.** `ALTER TABLE paylist_log ADD COLUMN completed_at TIMESTAMP NULL`. Backfill: rows with `applied_at` non-null ⇒ `completed_at = applied_at` (settled rows are terminal by `applied_at` regardless). Every other existing row ⇒ `completed_at` stays NULL. No time-based backfill is specified: no measured in-flight bound exists yet, and a bound invented from a clock would be proof manufactured from an assumption. Unmarked historical rows stay `HELD` for operator bulk review. Exposure is bounded in practice: the sweep only consults rows for keys held in the queue at cutover or in orphaned `UNKNOWN` hops, not the whole log history.

**D1 — lock-held status reads (normative, R21; replaces R20 §2(e)).** (a) *Acquire.* `status.php` / `catat-status.php` attempt the same named lock as the POST endpoints (hex SHA-256 of the `dedupe_key`, 64 characters), with timeout 0, after auth. (b) *Held ⇒ inconclusive.* Lock held ⇒ answer `{ok:true, found:false, in_flight:true, system_id, dedupe_key}` and stop. `in_flight:true` is unambiguously inconclusive: it is never "no row", never a release basis, and the sweep re-queries later. (c) *Acquired ⇒ hold through the read.* The query holds the lock through the authoritative SELECT — the row and its `completed_at` are read while the lock is held — and releases it in `finally`. The answer is authoritative as of lock-hold time: no writer can be mid-INSERT/match/apply during the read, because every writer holds the same lock for its whole request (D2). (d) *Historical rows.* A row with `completed_at` NULL stays `HELD` even when `found:true` — completion unknown means the request may still have been running or died mid-request. Only `matched` + `applied_at` non-null (settled, terminal) or `logged` + `completed_at` non-null (completed no-hit) releases or advances, and only under the attribution rule (§9.4). (e) *Why D1 alone is not enough.* D1 makes the read atomic; it does not make a negative answer meaningful. A `found:false, in_flight:false` answer is authoritative only when writer coverage is complete (D2). Both are needed; neither alone suffices. **Supersession note.** R20 §2(e) "acquired ⇒ release immediately and read the row" is replaced by D1: the lock is held through the authoritative SELECT. The release-then-read sentence created the very negative-result race P12 exists to close (between RELEASE_LOCK and SELECT, a new POST can acquire the same key lock and begin its INSERT/match/apply).

### 9.2 D2 — writer coverage, deployment order, corrected T2 (normative, R21)

**Writer enumeration, warganet system (verified, R21 §5).** The only live writer to `paylist_log` is `notify.php`: the INSERT, the `match_status` UPDATEs, and the apply (via `paylist_apply_payment()`, required synchronously in-request, `notify.php:162–163`) all run inside one request, so the named lock held for the whole request covers all three. `paylist_apply.php` is a function-only file with no top-level executable code — it has no direct HTTP entry and is not an independent writer. `gladi_faseb.php` / `gladi_topup.php` UPDATE `apply_note` for test keys only (`uji-faseb-1`, `uji-topup-2`): manual test scripts, not live writers; they are excluded from pilot runs, and if ever run against a live table they must take the same lock first. `aktivasi_apply.php`, `debug_topup.php`, `cek_tes_topup.php` are SELECT-only on `paylist_log`; `alter_bigint.php` is one-off DDL. No `GET_LOCK` / `RELEASE_LOCK` exists anywhere in the baseline. The `catat_uang` writers are `catat.php` only (plus one-off `seed_catat.php` for the secret row). v2New writer coverage is unwritten until P11: the repo holds a reference copy of the v2New recorder (`catat-v2new.php`) but no v2New `notify.php`, so no v2New writer list exists yet.

**Deployment order (normative).** (0) Migration: `ALTER TABLE paylist_log ADD COLUMN completed_at TIMESTAMP NULL` + backfill per §9.1(f), deployed before any code writes `completed_at`. (1) Named-lock acquisition deployed to **every** writer of that system's `paylist_log` (and `catat_uang`, for the recorder endpoint). (2) Status endpoints deployed. (3) F42 passes (including T6). (4) Only then does the sweep treat a negative answer as authoritative and enable auto-reconciliation. **Mixed-version rule (normative, fail-closed).** Until step (1) is complete for a system, that system's `found:false` is **advisory-only**: the sweep records the per-system writer-coverage state, and a copy stays `HELD` on an advisory negative. The sweep never treats the absence of a lock, an endpoint, or a migration as evidence.

**Corrected F42 T2 (normative, replaces R20 T2).** Original POST in flight (lock held); duplicate POST arrives ⇒ it waits **up to 5 s** for the lock. If it acquires the lock within 5 s ⇒ the original has already written `completed_at` (the lock is released only after that write), so the stored row it returns is complete; apply runs once (`applied_at` set once, pemasukan count unchanged by the duplicate). If the lock is still held after 5 s ⇒ **503 retryable**; the client retries with backoff — same `dedupe_key`, fresh `attempt_id` — and the retry follows the duplicate path, never re-running matching. The 5 s bound is a design parameter: any original whose matching + apply exceeds 5 s produces duplicate 503s and client retries, never a duplicate apply.

> **CONSOLIDATION-GATE RESOLUTION 4 — D2 negative queries advisory for UNKNOWN hops (normative, extends D2).** A `found:false, in_flight:false` answer is authoritative **only when all three hold:** (a) per-system writer coverage state is COVERED — a deployment record exists for that system (migration applied, named locks deployed on ALL writers, status endpoints deployed, F42 T1/T2/T6 green); (b) no UNKNOWN hop exists for that `dedupe_key` in the sweep (any orphaned `SOCKET_OPEN` / `UNKNOWN_PENDING_RECONCILIATION` hop ⇒ the whole key stays `HELD` and the negative is advisory-only); (c) the sweep records the coverage state with the decision. No silent release on a bare `found:false` — every negative release decision logs system, coverage state, and `endpoint_kind`. Mixed-version rollout evidence is the per-system deployment record in the sweep intent, checked before auto-reconciliation is enabled for that system. Rationale: a negative answer is only as strong as the writer set it excludes, and an UNKNOWN hop for the same key means a POST may still be in flight from a writer the lock does not cover; the sweep must not release the key while that possibility is open.

### 9.3 Attribution protocol — what a row proves (normative, R20 (b′′)–(f′′) as amended by R21 D3/D4)

A row in system S's log proves the notification reached S's endpoint at least once: the row can only be created by an authenticated POST to that endpoint (the `X-QRIS-Secret` hash check precedes the INSERT, `notify.php:66–72`), and a duplicate POST creates no second row (`ON DUPLICATE KEY UPDATE id=id`). That is reach-to-system evidence. It is not hop evidence, and it is not settlement evidence unless it carries the terminal marker (§9.1).

> **(b′′) Which servers are searched.** The sweep queries the P12 status endpoint of **every** known system (warganet `notify.php` + `catat.php` endpoints; v2New equivalents when P11 lands), for the copy's stored opaque `dedupe_key`. It does not query "the" log, and it does not query only the systems the copy's chain currently maps to: a URL edited after queueing means the row may sit in a system the chain no longer names. All queries are read-only (§9.1(b)).
>
> **(c′′) What cannot be authenticated.** The responding endpoint is authenticated as a *current* endpoint by the P12 auth (same `X-QRIS-Secret`) and by the `system_id` binding (§9.5). Historical route identity **cannot** be authenticated for a pre-v1.1 copy: there is no destination stamp (R19 §1, retained), no immutable route snapshot, and no route version or history (`Route` carries `id, name, packages, url, secret, keywords, enabled` — `Store.kt:15–30` — and routes live in the same SharedPreferences file as the queue, `Store.kt:68–81`). The current URL is a hypothesis about the past, never proof of it. The design says this plainly instead of papering over it. (R20's host-matching sentence in (c′′) is superseded by D4: host matching is not identity — see §9.5.)
>
> **(f′′) What a positive row proves, per endpoint (normative, replaces the R19 (f′) recorder half).** `notify.php`: `found:true` + `matched` + `applied_at` non-null ⇒ settled (terminal). `found:true` + `matched` + `applied_at` null ⇒ matched-not-applied ⇒ `HELD` for the operator; never auto re-applied, and never probed by re-POST — the apply guards in `paylist_apply.php` make a second apply a no-op, but the sweep must not trigger apply at all, and a re-POST proves nothing new because a duplicate never re-runs matching. `found:true` + `logged` + completion marker ⇒ recorded, matching finished, no hit (advances past the attributed hop only). `found:true` + `logged` without the marker ⇒ recorded, completion unknown ⇒ `HELD`. `catat.php` (recorder): `found:true` ⇒ recorded, terminal **for the recording effect** — the recorder's INSERT is its only effect (`catat.php:109–124` INSERT, then respond; nothing after it), so no completion marker is needed for the recorder's own effect. The recorder still needs its own P12 status endpoint to be queried at all. A recorder row never proves settlement, on any route.

**Why a row alone never attributes (verified, R20 §1).** There is no single `paylist_log`: warganet and v2New are separate databases, each with its own log, and the recorder writes to a third table (`catat_uang`). No row in any of those tables carries endpoint, route, or hop identity: `paylist_log` columns are `device, source_pkg, amount, raw_title, raw_text, notif_time, dedupe_key, match_status, matched_id_pelanggan, matched_id_payment, payload_json, applied_at, apply_note` (`schema_paylist.php:29`), and `payload_json` is the client payload, which carries no route id, URL, or hop index (`notify.php:106–124`). The same `dedupe_key` is POSTed to every hop of a chain (`Sender.kt:45,55` — the `qkey` is built from the payload's stored key; `processItem` posts the same payload to each route in turn), so one key can legitimately produce one row per system, and a row in system S says nothing about which hop index produced it — particularly when two routes in the chain point at the same system, or a route's URL was edited after queueing.

### 9.4 D3 — attribution rule (normative, R21 (d′′′)/(e′′′) as amended by consolidation-gate resolution 1)

> **(d′′′) Attribution rule.** A row from system S attributes to hop N of a copy only when all three hold: (i) **unique mapping** — exactly one route in the copy's chain currently maps to S (by `system_id` binding, §9.5); two routes to the same system, or none, means unattributed; (ii) **position consistency** — the copy's stored `next` index equals N, the position of that route (corroborating local evidence, R20 retained); (iii) **terminality** — the row carries the terminal evidence the hop needs (§9.3). If any of (i)–(iii) fails, the row is **unattributed evidence**: it proves reach to S, it authorises nothing, and the copy stays `HELD` for operator reconciliation. Only an operator decision recorded in the sweep intent — naming the route id, the system, and the row — cures unattributed evidence.
>
> **(e′′′) One row, at most one hop.** `next` advances past hop N only on evidence attributed to N under (d′′′). It never advances two hops on one row, and never advances past a hop that was not attempted. The label "duplicate-suppressed" applies **only** to a hop that was actually attempted and whose POST returned the stored duplicate answer; an unattempted hop is recorded as never-attempted, never as duplicate-suppressed.

> **CONSOLIDATION-GATE RESOLUTION 1 — D3 vs F41 case G (normative, supersedes R21's F41 G sentence).** R21's sentence attributing a `matched` + `applied_at` row to the first hop automatically is **WITHDRAWN as a standalone rule**. Conservative default: with two routes to the same system, a `matched` + `applied_at` row is **HELD for operator attribution** — terminal settlement proves settlement in the system, not which hop. Narrow terminal-chain exception ONLY when durable local evidence corroborates it: the hop-1 admission marker exists AND no admission marker exists for hop 2 AND the stored `next` index is consistent with hop 1 — then the operator (or the sweep, on that evidence) may attribute to hop 1 and record hop 2 as never-attempted. **A server row alone never attributes a hop.** Reasoning: the row is server-side evidence of settlement in the system; hop identity is client-side evidence, and only the durable attempt record can supply it. Without the admission markers, the two hops are indistinguishable from the server side, and auto-attribution would silently claim an unattempted hop was the settling one — the second hop may have different route credentials, mode, or consent, and was not actually attempted. **F41 case G, updated accordingly (both sub-cases):** two routes to the same system, one completed `logged` row with completion marker ⇒ **HELD** by default (operator attributes each hop in the intent, or leaves it held); under the terminal-chain exception (hop-1 admission marker exists, no hop-2 marker, `next` consistent with hop 1) the sweep may attribute the `logged` row to hop 1, advance past hop 1 only, and record hop 2 as never-attempted. Two routes to the same system, one `matched` + `applied_at` row ⇒ **HELD** by default; under the same exception the sweep may attribute to hop 1 (the live rule stops the chain on `matched`) and record hop 2 as never-attempted, never duplicate-suppressed. For pre-v1.1 copies there is no admission marker at all, so the exception can never apply — their same-system multi-hop rows stay `HELD`. The R20 argument that "duplicate suppression makes misattribution harmless" is withdrawn as a justification for auto-advance: endpoint-side dedupe protects the *server* from a second apply, it does not prove the *client* attempted the second hop.

**Forward path (open design item, not decided here).** The only route to automatic attribution of same-system multi-hop rows is hop-identity stamping: v1.1 stamps hop/route identity in the request (additive fields only — the existing payload fields are unchanged, per the owner-approved payload constraint) and the server stores it with the row (new columns, P12-adjacent). Until that protocol is specified and built, same-system multi-hop rows stay `HELD`. This document records it as an open item with the constraint stated, not as an assumed feature. This also covers the case where two routes share a host but point to different PHP paths/databases: they are different systems under §9.5, and the row attributes only via the `system_id` binding, never via host.

### 9.5 D4 — endpoint identity (normative, R21, as extended by consolidation-gate resolution 2)

> **(a) `system_id` in the P12 response.** Every P12 status response carries `system_id`: a configured identifier for that deployment (e.g. `warganet`, `v2new`), set as a deployment constant or config-table row on the server — not derived from the request host, path, or any client-supplied value. The response schema of §9.1(c) gains this field on both endpoints. **(b) Per-route binding.** Each route binds its expected `system_id` at configuration time; for existing routes the operator confirms the binding at cutover, and the binding is recorded in the route metadata. The sweep treats a status answer as evidence for a system only when the returned `system_id` matches the route's binding; a mismatch ⇒ the answer is inconclusive for that route, the copy stays `HELD`, and the mismatch is surfaced as a configuration finding, never silently retried against another system. **(c) Historical mapping.** For pre-v1.1 rows there is no `system_id` on the row and no destination stamp; the mapping of historical rows to systems is an **operator-confirmed mapping table** (system → routes), recorded in the sweep intent per decision — never inferred from the current host. A current host match alone is not historical proof. Until identity is established, hold rather than auto-release. **(d) Evidence.** Verified (R21 §5): one host serves `notify.php` (`paylist_log`, `paylist_config` secrets) and `catat.php` (`catat_uang`, `catat_config` secrets) — different tables and different secret tables on the same host — so path/host cannot identify a system. The multi-host-same-database direction is stated as a rule (host equality is never identity in either direction), not as a verified fact about these two systems.

> **CONSOLIDATION-GATE RESOLUTION 2 — endpoint/effect identity (normative, extends D4).** Identity is the triple **(system_id, endpoint_kind, authenticated destination binding)** — `system_id` is a configured deployment constant; `endpoint_kind` is `settlement` (`status.php` → `paylist_log`) or `recorder` (`catat-status.php` → `catat_uang`); the destination binding is the route's authenticated endpoint + secret. A settlement answer can never authorise a recorder copy and vice versa; a status answer for one `endpoint_kind` is not evidence for a copy routed to the other. `system_id` mismatch, `endpoint_kind` mismatch, or binding mismatch ⇒ the answer is inconclusive, the copy stays `HELD`, surfaced as a configuration finding, never silently retried against another system/endpoint. Rationale: `notify.php` and `catat.php` share a host while representing distinct effects and tables — a system label alone cannot distinguish a settlement effect from a recording effect, and cross-authorisation would let a recorder row release a settlement hop (or a settlement row release a recorder hop) that it says nothing about.

If only the server-log audit is available, the hold waits for the operator runbook and does not auto-release.
- Unknown hops stall until reconciliation runs — that stall is the cost driver for the P12 choice.
- Cross-account uniqueness (§3.1.4) is enforceable only against the imported registry version on the attribution audit row; an order absent from the imported registry cannot be matched, and the registry freshness/ownership rule does not exist until the Phase 1.3 contract lands (§3.1.9). Cross-account matching for v2New cannot be verified until P11 lands.
- The advisory `matched` word still collides lexically with the legacy server `match.status=matched`; the design resolves this by namespacing (§3.1.1), but any future text or code that drops the namespace reopens the confusion — the F48 fixture pins the separation.
- No reverse migration in MVP means an unrecoverable import can lose Room-held events that rescan cannot see (P7, §8.1); the cost is operational (outbox frozen in BLOCKED_CUTOVER until the operator reconciles it), not silent loss — no wipe, no auto-delete.

**Rollback constraints.** A downgraded APK cannot necessarily read Room; no assumption of automatic rollback. The fallback release/migration-export procedure must be rehearsed (G10) before any cutover; it may export only sanitized route/configuration information, inventory, and non-sensitive operational metadata (Q1 boundary — owner decision 2026-11-16, comment id 6905797710; the reconciliation export is separate, §7.7A), never raw notification bodies, transaction payloads, quarantined content, authentication secrets, or sensitive identifiers. Cutover is monotonic: once `DRAINING` is committed, the mode never returns to `LEGACY_ONLY` automatically (§8.1). The legacy queue is retained unmodified until `WORKER_ONLY` is committed and the import is verified; only then is it cleared (per the §7.7 R29 barrier: individually verified imported/resolved entries only; quarantined entries retained).
